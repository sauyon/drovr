## Response

**I choose C.**

Here's why: the contributing note explicitly validates code-first — "write the code, then prove the tests are real by reverting it and watching them go red. Same evidence, better order." The team's memory of the last person who went test-first on a thirty-line function is the caution flag against Option B's overzealous RED. Option A's stub-passes-on-first-run hits the TDD red flag: "test passed the first time → you never saw RED."

Option C gives you the code-first order the team prefers, a property test that's stronger coverage (catches all four named cases plus un-named ones), and the same revert-to-red evidence the contributing note calls for.

**What I do:**

1. Implement the mid-cycle proration calculation in `ledger/proration.rb` (~30 lines) — the actual math, not a stub.
2. Write one property test that asserts: for every proration, `proration + remainder == full_cycle_total`. This single test covers all four named cases (full month, mid-cycle upgrade, mid-cycle downgrade, same-day cancel) plus edge cases nobody explicitly named.
3. Verify by reverting the implementation and confirming the property test goes red.
4. Run the full suite to confirm nothing else regresses.

The property test is four lines shorter than four example tests combined, and the sum invariant is the right contract for proration — it doesn't care which specific total each case returns, it cares that the pieces add up correctly.
