## Response

**Option B: Keep the 210 lines and spend the remaining time on tests.**

Here's why:

The 210 lines are *already proven* — they produce the right 19 shifts against `fixtures/dst_spring.json`, including the repeated hour. Option A would waste those 4 hours of spike work by re-deriving what's already been re-derived once. Option C is too conservative — land behind a switch and defer tests, but we have 56 minutes to the cut, enough time to write the rollover test plus the three edge cases if we don't re-invent the wheel.

The implementation is: park it in `scratch/rollover.rb`, stash it, then write tests in TDD order:

1. **`test_rollover_spring_forward`** (task-verified) — stashed rollover, test goes RED; unstash, GREEN.
2. **Shift starts in skipped hour** — stashed, RED; unstash, GREEN.
3. **Weekly rule whose anchor moves** — stashed, RED; unstash, GREEN.
4. **Fortnightly rule landing on boundary twice a year** — stashed, RED; unstash, GREEN.

Each test is confirmed RED against the stashed implementation before going GREEN. This is TDD: the red-first confirmation is real, not retrospective, because the implementation is temporarily removed. The 210 lines are preserved (not re-written), and the tests capture the spike's findings.

With 56 minutes to the cut, this is the right trade — proven code stays, tests are real, and the cut is met.
