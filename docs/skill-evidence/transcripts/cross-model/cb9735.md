### Why not A

Meera's note contains the disqualifying sentence itself: "I could not get it to reproduce locally, but reading the code this is the only path that produces it." That is a hypothesis derived from reading, from one production sample. It may well be right — she owns this service and I'd bet on her over me — but "the only path I can see" and "the path that fires in production" are different claims, and nothing has yet distinguished them.

The part that actually decides it for me is the regression test. A test written from an unreproduced hypothesis tests *the hypothesis*, not the bug. If the mechanism is something else, that test goes green, the branch merges, the drop continues, and now we have a test standing guard over a bug it never caught — the next person to look at this reads a green suite and concludes this path is covered. That is worse than the current state, because the current state at least knows it doesn't know.

And "watch the drop rate for a day" is not verification at 1-in-400. Absence of complaints for 24 hours is compatible with a partial fix, a fix that moved the event to a different path, or ordinary variance. If we merge without a trigger we cannot tell "fixed" from "quiet," which is exactly what step 5 of the loop exists to prevent.

### Why not C

C is A with a dashboard. It ships the same unverified fix, adds a permanent per-customer config surface that will outlive the bug, and still produces no localization — a 48-hour rate comparison across three customers at 1-in-400 has no power to resolve anything. It also splits the fleet into two dedupe behaviors, so if a *new* symptom shows up next week we're debugging two code paths instead of one. It reads like caution and buys none.

### The plan (tomorrow, in order)

1. **Check the rate arithmetic against her hand-worked windows — 20 min, desk work.** Her theory says arrivals landing in the overlap get dropped. So the overlap's share of the window should predict roughly 0.25%. If the numbers say 1-in-8 or 1-in-50,000, her mechanism is incomplete or isn't the one firing, and I've learned that before writing a line of harness. This is step 3 of the loop applied to *her* explanation: it has to predict the observed behavior exactly, and the rate is observed behavior.
2. **Read her regression test — 15 min.** The question is whether it drives the real ingest path into the drop, or constructs the window state by hand and asserts the hypothesis into existence. If it genuinely exercises the path and fails against unfixed code, *that is a reproduction* — minimal and deterministic — and the two hours mostly evaporate. Worth checking before assuming they don't.
3. **If 1 and 2 don't already give me a trigger: build the harness — ~2 hours.** Pinned clock, pinned window size, enough traffic to hit the event. Then read which path actually produced the drop.
4. **Fix.** My strong expectation is that this is "merge Meera's branch, unchanged" — with the difference that we now know it's the cause rather than believing it. If the repro shows something else, we've saved three customers a second round of tickets.
5. **Verify.** Re-run the trigger, confirm it's gone, full suite, and keep the harness in the repo. This service will have another timing bug and the repo currently has no way to reproduce any of them. That's the durable win here, and it's not two hours spent on this bug alone.
