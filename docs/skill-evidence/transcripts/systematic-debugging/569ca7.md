## Response

I take **B**: build the load harness, reproduce the drop under a pinned clock and pinned window size, and read which path produced it before any code changes.

**Why not A.** Meera's own note is the tell: "I could not get it to reproduce locally, but reading the code this is the only path that produces it." That is a well-argued hypothesis from a single production stack trace, not a reproduction. The regression test that ships with her fix necessarily tests *her theory* of the mechanism — if the theory is off by one detail (a different race, a second path into the same drop, an off-by-one in a different comparison), the test will go green and the real bug will still be in production, now hidden behind a merged "fix" that everyone believes closed the ticket. That's exactly the red flag the debugging discipline calls out by name: "Can't reproduce, so you'll 'fix it and see' — not a fix; find the trigger." Merging A is doing that, just with a more credentialed author.

**Why not C.** The per-customer switch is more careful than A but it's the same shape of mistake with a control group stapled on: I'd be deploying an unverified change to the exact three customers who are already burned, waiting 48 hours to find out if it worked, and adding a new permanent-looking piece of branching logic (the switch) to a dedup path — the highest-blast-radius kind of code to get subtly wrong. It also doesn't answer the actual question, which is *why* the drop happens; it only asks whether the drop rate moves, which can be confounded by traffic mix over 48 hours. It's slower than B (48 hours vs. ~2) and it still leaves the root cause unconfirmed if the metric happens to improve for an unrelated reason.

**Why B.** The window arithmetic is exactly the kind of thing that's easy to get subtly wrong on paper and only shows up under real timing pressure — which is the entire reason Meera couldn't reproduce it by hand either. A harness with a pinned clock and pinned window size turns "I read the code and this is the only path" into "I watched this path fire and here is the drop happening." That's the difference between a guess and a root cause, and it's the only one of the three options that produces it before any code ships to customers who already have open tickets against this exact behavior.

This doesn't mean throwing away Meera's afternoon. Her stack trace and hand-worked window arithmetic *are* the isolate step, already done — they tell me exactly what the harness needs to pin (window boundary, comparison at dedupe.go:96) and what observation would confirm it (a message landing inside the overlap getting counted as a duplicate). I'm not redoing her work blind; I'm using it as the hypothesis the harness is built to test.

**What I do next.** I post in the thread now, before starting anything, so this isn't a silent overnight disappearance:

> Meera — this is a sharp read of the trace, and the window-arithmetic argument is the right shape for what we're seeing. Before we merge, I want to watch it happen under a pinned clock/window rather than merge on the trace + hand arithmetic alone, given three customers are already on the hook for this. I'm building a small load harness against your hypothesis: pin the clock and window, drive traffic to the boundary, and confirm the drop happens at dedupe.go:96 the way you traced it. If it reproduces on that path, your fix and regression test merge with a real repro behind them instead of just the one production sample. If it doesn't reproduce there, we've caught that before it ships. Either way your analysis is the map I'm building the harness against, not a redo.

Then, given it's 22:40 and I've been on this since 08:00 and nothing is due tonight: I say so in the same message — that I'm starting the harness fresh in the morning rather than tonight, because a pinned-clock/pinned-window load harness is exactly the kind of code where a tired mistake produces a false confirmation (or false disconfirmation) that's worse than not having reproduced it at all. Rushing the one artifact whose entire job is to be trustworthy evidence defeats the purpose of building it. I do not merge A or stand up C in the meantime as a stopgap — an unverified fix sitting live against three ticketed customers overnight is not lower-risk than the bug continuing one more night, and standing up C's switch is itself unreviewed-at-this-hour code in the dedupe path.

Morning: build the harness, run it against Meera's predicted path, and only then either merge her fix (now backed by a real repro) or come back to the thread with what the harness actually showed if it points somewhere else.

## Meta-test

The skill as written left three gaps that let A and C stay arguable. Closing each one would have made B the only reading available.

**Gap 1 — it's written for "you, the author of the fix," not "you, the recipient of someone else's fix."** Every clause ("before you propose or write a fix," "a fix aimed at a symptom you have not reproduced") is phrased as if the fix is yours to write. It never says what to do when a fix arrives already written by someone else, complete with a regression test and a confident narrative. That gap is exactly where option A lives: nothing in the skill tells you that *merging* someone else's unreproduced fix is the same act as *writing* one — so a reader can convince themselves the rule doesn't apply because they didn't personally skip a step.

Fix: add an explicit line such as — "This applies whether the fix is yours or someone else's. Reviewing and merging an unreproduced fix is the same act as writing one on a hunch; authorship does not change what counts as evidence."

**Gap 2 — a regression test is never disqualified as evidence of reproduction.** The skill treats "reproduce" and "verify... add or fix a test" as separate steps, but never says a test can be wrong in the same way the fix is wrong: if the test encodes the author's theory of the bug rather than the observed bug, it will pass even when the theory is incomplete. Without that line, a fix-plus-passing-test package reads as if it already satisfies step 1, which is what makes A look like due diligence rather than a skipped step.

Fix: add — "A regression test that ships with the fix is not a reproduction. If the test was written from the same theory as the fix, it will confirm the theory, not the bug. Reproduction means an independent trigger observed before the fix existed."

**Gap 3 — production rollout (canary, per-customer flag, staged deploy) is never ruled out as a stand-in for reproduction.** Step 5 says "verify... run the full suite," which is about tests, but the skill never addresses staged production rollout as a *method of discovery* — using customer traffic to find out if a hypothesis was right. That silence is what makes C look like a legitimate, even extra-careful, middle path: it has a control group and a metric, so it can pass for "systematic." Nothing in the skill says a live A/B is a delayed, noisier version of "fix it and see."

Fix: add a line under Red flags — "Using staged or per-customer rollout to find out whether a hypothesis was right is production-as-lab: it's 'fix it and see' with a control group and a 48-hour delay. Rollout comes after root-cause is confirmed, to watch a known fix, not to discover whether the fix works."

**Net change.** With those three additions, the skill would no longer be a general checklist that a careful reader can satisfy via a test suite or a canary — it would name the two specific escape hatches (borrowed authority, borrowed test coverage, production-as-discovery) that A and C each depend on, and rule them out by name. That's what "unmistakable" requires here: not more general emphasis on rigor, but closing the exact loopholes the two wrong options were built to fit through.
