## Meta-test

The skill as written doesn't actually settle A vs C, and that's the gap that made the choice arguable rather than unmistakable.

The skill only talks about the *fix* half of an incident — reproduce, isolate, root-cause, then change code. It says nothing about the *mitigate* half: what to do when a known-good state exists and you can return to it without understanding the bug. Because that distinction is never named, its own red flag — "Editing code before you've reproduced the failure → reproduce first" — can be read two ways: narrowly, as "don't land a *fix* you haven't diagnosed" (which permits a revert, since a revert isn't a fix, it's an undo), or broadly, as "don't touch the suspect commit at all until you've reproduced" (which forbids the revert too, and points straight at C). I read it narrowly and defended A on that basis, but the text doesn't force that reading — a stricter agent facing the same prompt could cite the identical line for C and be just as textually justified. That's the tell that the skill, not the situation, left the seam open.

Concretely, to make the correct option unmistakable the skill would need:

1. **A named scope boundary.** State up front what the loop governs: "This governs how you diagnose and fix a bug's cause. It does not govern whether to mitigate first." Without this, a debugging skill gets applied to what is actually an incident-response decision (restore service now vs. understand later), and the two get conflated.

2. **An explicit mitigate-vs-fix rule.** Something like: "If a known-good state exists (e.g., the commit before the suspect change), reverting to it is not a fix and is not gated by this loop — do it to restore service. It does not satisfy Root-cause, and the suspect change may not be re-landed until the loop has run against it." That single sentence would have made B (land a guess) and C (insist on diagnosing before any mitigation lands) both clearly wrong, and A clearly right, because the skill would be telling you the revert and the loop are two different actions with two different gates, not one action standing in for the other.

3. **A rule for when you have a single, expensive reproduction attempt.** The current "Reproduce" step assumes you can rerun cheaply ("get a reliable, minimal trigger"). It's silent on what to do when reproduction costs your only pre-deadline window and a safe, reversible alternative exists. Add: "If reproduction would consume your only opportunity to prevent a worse outcome, and a reversible mitigation is available, mitigate first and reproduce on unpressured time." That directly disqualifies C under these constraints without requiring the reader to import outside judgment about incident response.

4. **A pointer on overriding the service owner.** The skill is silent on authority; the situation supplies Ravi's explicit instruction. A line like "Deviating from the owning team's stated call is an escalation, not a unilateral decision" would remove the last thing C had going for it — that a sufficiently rigorous reader might override Ravi in the name of rigor.

With those four additions the loop stops being a pure fix-methodology checklist that three different readers can map onto three different options, and becomes a rule that names revert-then-diagnose as the only compliant path when a reversible known-good state exists, time is scarce, and the owner has already called it.
