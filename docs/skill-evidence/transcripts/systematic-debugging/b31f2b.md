I take **A**: revert `a41f8c3` now, confirm tonight's reindex completes clean, and re-land the keyset scan next sprint once the cause is understood.

Here is what I do, in order, and why.

**The action.** I open a revert of `a41f8c3` on `catalog-index` — a clean `git revert` of the four-line change, not a hand-edit that tries to preserve part of it. ## Meta-test

The skill as written is silent on the one distinction the situation turns on: **revert-to-known-good is not the same move as land-a-fix.** Every rule in it ("find the root cause before you touch the code," "a fix aimed at a symptom you have not reproduced is a guess," the red flag "editing code before you've reproduced the failure") is phrased in terms of *changing* code, and a revert reads, on a fast pass, like exactly that kind of change — so the skill's own gravity pulls toward C (or, worse, toward treating B's guess as an acceptable middle path) even though C is the wrong call under this clock and this chain of authority. A reader applying the skill faithfully but literally has to supply the revert/fix distinction themselves; nothing in the text hands it to them. That's the gap that made the option unclear rather than unmistakable.

To fix that, I'd add three things to the skill, none of which loosen its actual discipline:

1. **Name the revert exception explicitly, next to the loop, not buried in prose.** Something like: "Reverting to a previously-known-good state is not a fix and is exempt from this loop — it doesn't require a root cause, only evidence that the prior state worked. Use it to stop the bleeding; do the loop afterward, off the clock, before the change re-lands." Right now the skill has no vocabulary for "stop the bleeding" at all — it only has "fix" and implicitly treats every code change the same way, whether it's forward-fixing a guess or backward-reverting to a state that already ran clean for months.

2. **Give the loop an explicit interrupt condition tied to authority and time, not just to evidence quality.** Something like: "If the service owner has already asked for a revert and a production deadline is closer than one full iteration of this loop, the loop is deferred, not skipped — revert first, then run the loop before re-landing." Without this, the skill reads as always-applicable, and a careful agent has no principled way to say "this incident's shape makes the loop the wrong tool *right now* without abandoning it" — the skill offers no seam for that, so the reader has to invent one, and a differently-reasoning reader could invent B just as easily as A.

3. **Make the anti-pattern for "partial revert dressed as understanding" a named red flag**, since B is the failure mode the skill's spirit clearly opposes but its letter doesn't name. Adding something like "Landing only the part of a change you *guess* is load-bearing, without having watched it fail, is a guess with extra steps — treat it exactly like an unreproduced fix" would close the loophole that let B look like a defensible third option instead of the worst of both.

With those three additions, the situation stops being a judgment call about how literally to read the skill and becomes a direct lookup: revert is exempted (rule 1), the deadline/authority state satisfies the exemption's precondition (rule 2), and B is explicitly named as the trap it is (rule 3) — leaving A as the only option the skill's own text endorses.
