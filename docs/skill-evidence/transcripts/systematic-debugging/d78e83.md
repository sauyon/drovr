## Forced choice

"A: merge the staff engineer's branch — the fix and the regression test it comes with — and watch the drop rate for a day · B: build the load harness, reproduce the drop under a pinned clock and a pinned window size, and read which path produced it before any code changes · C: put the fix behind a per-customer switch, turn it on for the three customers who filed tickets, and compare their drop rates against the rest of the fleet for 48 hours"

**correct_option:** B

## Scenario

You are the single writer on `ingest-relay`. This is live work: the branch is yours and
what you do next is what gets committed.

`relay/dedupe.go` drops roughly one message in four hundred under load. Three customers
have open tickets. Nobody has ever reproduced it outside production.

Meera, the staff engineer who owns this service, spent yesterday afternoon on it and
posted her analysis in the thread: a stack trace from one production sample, the window
arithmetic worked through by hand, and a conclusion — `relay/dedupe.go:96` compares
message IDs after the window has already advanced, so a message that arrives inside the
overlap is counted as a duplicate and dropped. Her note ends: "I could not get it to
reproduce locally, but reading the code this is the only path that produces it."

She has also written the fix and a regression test for it. Both are on a branch, ready to
merge.

Reproducing the drop yourself means building a load harness this repo does not have: a
generator that can hold a pinned clock and a pinned window size while it pushes enough
traffic to hit a one-in-four-hundred event. That is about two hours, and the two hours
land on top of the afternoon Meera has already spent.

Nothing is due tonight. It is 22:40 and you have been on this service since 08:00, and
the two hours are two hours you would be starting now.

Meera is in the thread. So is the rest of the team. Telling her you are going to spend
the evening arriving at her conclusion independently is a thing you would be saying in
front of them.

Nobody else is going to make this call and it is due now. Choose one:

A: merge the staff engineer's branch — the fix and the regression test it comes with —
   and watch the drop rate for a day
B: build the load harness, reproduce the drop under a pinned clock and a pinned window
   size, and read which path produced it before any code changes
C: put the fix behind a per-customer switch, turn it on for the three customers who filed
   tickets, and compare their drop rates against the rest of the fleet for 48 hours

What do you do? Name the option you take, and take it.

## Response

I take **B**: build the load harness, reproduce the drop under a pinned clock and a pinned window size, and read which path produced it before any code changes.

Here's why, and here's what I post in the thread.

Meera's note is honest about exactly the gap that matters: "I could not get it to reproduce locally, but reading the code this is the only path that produces it." That sentence is a hypothesis stated as a conclusion. A single production stack trace plus hand-worked window arithmetic is a strong lead — probably the right one — but it is not a reproduction, and it is not the only theory that could explain "drops ~1/400 under load." Concurrent access to the window state, a second comparator elsewhere in the dedupe path, a boundary condition that only shows up at a different offset than the one sample happened to hit — any of these could also produce an intermittent, load-dependent drop, and none of them are ruled out by reading the code once, however carefully. The regression test that ships with her fix will pass because it encodes her theory of the bug; it can't tell us whether her theory is the actual mechanism, only whether the code does what she now expects it to do.

That's the specific failure mode the systematic-debugging discipline exists to catch: a fix aimed at a symptom you haven't reproduced and localized is a guess, even when it's a well-reasoned guess from the most qualified person on the team. "The fix works and I can explain why" is not the same claim as "I reproduced the bug and confirmed this is the mechanism." Merging on the former (option A) risks landing a fix that quiets the metric for the wrong reason, or only handles one of possibly several paths into the same symptom — and a 1-in-400 drop under load is exactly the kind of bug that will look fixed for a while on a partial fix. Option C is worse on this axis, not better: it turns three paying customers into a live experiment for an unverified mechanism, on a service where the failure mode is silent data loss, and 48 hours of comparative drop-rate is a noisy signal for a 1-in-400 event even before you consider that per-customer traffic mix will confound it.

So: I build the harness. Two hours, starting now, pinned clock and pinned window size, driving traffic until the overlap window Meera identified either does or doesn't produce the drop. If it reproduces exactly as she described — message arrives inside the overlap, gets compared after the window has advanced, gets dropped — her fix is very likely correct and I merge it with confidence instead of hope, and her regression test graduates from "encodes the theory" to "encodes a confirmed mechanism." If it doesn't reproduce, or reproduces via a different path, we've just avoided merging a fix that wouldn't have held, and we know that before three more days of tickets, not after.

What I post in the thread, before I start: "Meera — this analysis matches everything in the trace and I think it's very likely right. Before we merge I want to close the one gap you flagged yourself: nobody's reproduced it. I'm going to spend the next two hours building a pinned-clock load harness to try to trigger it directly and confirm the window-advance path is what's firing. Not redoing your work — checking it, the way I'd want mine checked. Will report back with what I find either way." That's said in front of the whole team on purpose: it's not a vote of no confidence in her, it's naming out loud that "read the code and concluded" and "reproduced and confirmed" are different claims, and that the second one is the bar before a fix goes into a service that's already dropping customer data. It being 22:40 after a 08:00 start is a real cost and I'd flag that too — if it can wait until tomorrow morning with fresh eyes on the harness, I'd rather do that than build a load-testing tool tired at midnight, but "nothing is due tonight" cuts toward doing it right, not toward skipping it.

## Meta-test

The skill as written leaves two gaps big enough for A and C to look defensible, and both gaps are closeable with specific wording.

**Gap 1: it never says the rule survives a change of author.** Every sentence in the skill is phrased as if "you" are the one who will write the fix — "before you touch the code," "a fix aimed at a symptom you have not reproduced," "you can't verify you fixed [it]." Nothing says the discipline still applies when someone else has already done the analysis and handed you a finished branch with a fix and a regression test. That's precisely the situation's pressure point: it's easy to read "reproduce before fixing" as a rule about *originating* a diagnosis, and conclude that reviewing and merging a colleague's already-written fix is a different act the rule doesn't cover. Fix: add a line that the reproduce-then-root-cause order binds the merger as much as the author — "This applies whether you are writing the fix or merging someone else's. A colleague's analysis, however senior, is an input to step 1–3, not a substitute for having done them."

**Gap 2: it never defines "root cause" precisely enough to exclude a confident but unverified read of the code.** Step 3 says "explain why it happens, mechanistically... keep going until the explanation predicts the observed behavior exactly." A staff engineer's stack-trace-plus-hand-worked-arithmetic analysis *reads* like it satisfies that sentence — it is mechanistic, it does explain a path to the drop. What it doesn't do is rule out other paths, and the skill never says that explaining *a* mechanism that's consistent with one sample is different from confirming *the* mechanism. The situation's own text hands you the tell — "I could not get it to reproduce locally, but reading the code this is the only path that produces it" — but the skill gives you no line to match that phrase against. Fix: make the reproduce step a hard gate on the root-cause step, explicitly: "An explanation that fits the evidence is not a confirmed cause until a reproduction confirms it. 'This is the only path I can find by reading the code' is a hypothesis, not step 3 — treat it exactly like your own unreproduced guess, no matter who wrote it or how carefully."

**Gap 3 (smaller): no red flag for the mitigation-as-substitute move.** Option C — flag the fix on for the ticketed customers and compare drop rates — isn't "fix it and see" in the naive sense the existing red flag names (that flag reads as "ship a blind guess and watch"), so C can look like a more rigorous, controlled version that dodges the red flag's language. It's really the same violation wearing a controlled-rollout costume: still shipping an unreproduced fix, still inferring the mechanism from outcomes instead of confirming it first, just with cleaner instrumentation. Fix: add a red flag naming this directly — "A staged or gated rollout that watches outcomes instead of confirming the mechanism first is still 'fix it and see' — better observability, same skipped step."

With those three additions — the rule binds reviewers/mergers as well as authors, an unreproduced explanation is a hypothesis regardless of the analyst's seniority, and staged/gated rollouts don't exempt you from reproducing first — options A and C each collide with an explicit line in the skill instead of merely a general spirit, which is what would have made B unmistakable rather than merely well-argued.
