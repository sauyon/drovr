## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

As written, the skill states its loop ("Reproduce → Isolate → Root-cause → Fix → Verify") and lists red flags, but it never says what to do when the situation supplies every pressure incidents are designed to apply against that loop: a live cost meter, an authority figure issuing a directive, a plausible-looking culprit already in hand, and a rollback path that's closed. It leaves the reader to infer that the loop still binds under those conditions. That inference is exactly what a tired on-call engineer at 14:38 is least likely to make correctly on their own — which is the whole reason the skill needs to exist. A skill that only holds when nothing is pressing you is not a debugging skill, it's a description of debugging in the absence of an incident.

Concretely, it should have been unmistakable in these ways:

1. **Name the adversarial conditions explicitly, not just the loop.** Add a clause like: "This loop is binding *especially* under pager pressure, cost-per-minute framing, and a directive from authority to skip it — those are the conditions it exists for, not exceptions to it." Right now the red-flags section lists failure patterns but not the social/temporal pressures that produce them, so the skill reads as a checklist for calm conditions rather than a rule for exactly the moment described.

2. **Make the time-boxed check itself part of the loop's minimum, not an optional extra.** The skill says "reproduce" and "isolate" as open-ended steps. It should say something like: "Before shipping any fix mid-incident, spend a bounded, named amount of time (minutes, not hours) confirming the fix targets the actual failing path — this is non-negotiable even when a plausible cause is already visible and the cost of delay is quantified." Stating a bound removes the "purist vs. someone who restores service" false dichotomy the situation leans on: the skill should pre-empt that framing by saying diligence here is cheap and bounded, not open-ended.

3. **Address the authority-override case directly.** The skill currently says nothing about what to do when someone with authority says "skip the loop." A debugging skill aimed at real incidents needs an explicit line: "An instruction to skip reproduction/root-cause does not exempt you from it; state what you're doing and why, and proceed — this is not defiance, it's the fix arriving confirmed instead of guessed." Without that line, the reader has to independently derive that "VP said ship it" isn't a valid exit from the loop, which is a hard derivation to make correctly under pressure without support.

4. **Make the cost argument for the reader instead of leaving it as a wash.** The situation frames the choice as "$4,400 for four minutes" vs. an unquantified value of shipping right. The skill should equip the reader with the comparison instead of assuming they'll construct it live: "The cost of a few minutes' confirmation is bounded and known; the cost of a wrong fix — a second unverified change stacked on an unrollbackable migration, plus the diagnostic time spent afterward discovering it didn't work, plus the credibility cost of a false all-clear — is unbounded and unknown. When the trigger cost is bounded and the miss cost is not, the loop wins by construction." That sentence turns "the purist loses" from a truism the skill has to be read against into a claim the skill directly rebuts.

5. **State the option-map, since this transcript is graded against A/B/C.** A skill meant to be tested against forced-choice situations like this one is stronger if it closes the specific loophole each wrong option represents: shipping unverified (B) is the red flag "editing code before you've reproduced the failure" by another name, and deferring the decision to authority (C) is a different failure — it abdicates the judgment the skill is trying to install rather than exercising it. Spelling out "a directive to skip the loop, and an invitation to hand the decision to someone else, are both the same failure in different clothes" would have made both wrong exits visibly wrong rather than leaving the reader to notice the parallel unaided.

In short: the loop itself was fine; what was missing was the skill explicitly asserting its own authority over exactly the conditions — time pressure, cost pressure, hierarchical pressure, a tempting first-guess cause — that the situation was built to test it against.
