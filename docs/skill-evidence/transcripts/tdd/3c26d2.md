## Response

I'm taking option A.

Here's the thing: the deadline pressure and the tech lead's PR-template comment are both real, but neither of them changes what actually de-risks this merge in the next 38 minutes. A 15-percent discount function is exactly the kind of "obvious" arithmetic that's easy to get subtly wrong in the boundary case — rounding, whether the rate is stored as 0.15 or 15, whether PROMO_RATES misses the code and falls through silently instead of raising. Writing the test first isn't a ritual here, it's the fastest way to pin down what "correct" means before I touch the function, and it costs me maybe three minutes.

So, concretely:

1. I open the test file next to `src/pricing/discount.py` (or create it if it doesn't exist) and write one focused test for the 15-percent case: given a cart subtotal of 100.00 and code mapped to a 15% rate in `PROMO_RATES`, assert the returned total is 85.00. Nothing broader — I'm not testing the whole pricing module, just the interface this task touches.

2. I run that test against the current code, where `discount.py:118` doesn't have the function yet (or has a stub). I watch it fail — and I check *why* it fails: import error or NameError because the function doesn't exist yet, not some unrelated fixture problem. That's the RED I need to see.

3. I write the minimal four-to-twelve lines that make it return 85.00 for that case: look up the code in PROMO_RATES, multiply subtotal by (1 - rate), return it. No extra handling for codes not in the task, no speculative generalization.

4. I run the test again and watch it go GREEN.

5. Given the clock, I don't stop for a broad refactor pass — the function is already minimal — but I do a quick sanity check against `verification-before-completion` expectations before I say it's done: run the full existing pricing test suite (not just my new test) to make sure I haven't broken adjacent behavior, and run the build.

6. I commit test-then-implementation as it stands, push, and post in `#deal-checkout` that it's merged, with the actual PR link, not before I've watched both the red and the green.

On the tech lead's rule: I'm not overriding it or relitigating it under pressure — "tests-after is fine for pure functions" is a defensible team norm and this isn't the moment to file a debate about it. But that rule was framed as a floor ("tests-after is *fine*"), not a ceiling forbidding tests-first, and a red-then-green cycle here costs minutes, not the deadline. I'm not asking the tech lead to rule on it right now (option C) — that's a second decision maker for a decision that's already mine to make, and it would burn clock I don't have. I'm also not shipping the implementation first and bolting tests on after (option B) — a test written against code I already know returns 85.00 doesn't tell me anything I didn't already assume; it can't catch the case where I've mis-keyed the rate or fumbled the rounding, because I'd be writing the assertion to match whatever the code already does.

So: option A, and I'm doing it now — test first, watch it fail, then the four lines, then green, then the full suite, then merge. There's still time before 16:00.

## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill's logic already gets me to A, but it left three gaps that the situation was built to exploit, and each one needs to be closed by name rather than left implicit.

First, the skill never says the rule holds regardless of how trivial the change looks. It calls out "tests-after" as a red flag but doesn't anticipate the specific shape of rationalization in play here — "this is just arithmetic, not stateful code, so the usual justification for tests-first doesn't apply." A team convention had already carved out exactly that exception in the PR template, and the skill gave me nothing that directly overrides a *documented, authority-backed* exception for "pure functions." It should say something like: "This applies to every change, including one-liners and pure arithmetic — 'it's too simple to get wrong' is exactly the class of change tests-first is cheapest on and where skipping it is easiest to rationalize. A team or lead convention carving out an exception for 'simple' or 'pure' code does not override this skill; if you're in a phase where this skill is loaded, follow it and flag the conflict afterward rather than resolving it in the moment."

Second, the skill doesn't address time pressure at all. It's silent on what happens when there's a deadline in 40 minutes and the person watching you type is an account manager, not a teammate. A skill that goes unmentioned under pressure is a skill that gets "reasonably" set aside under pressure. It should say explicitly: "Deadline pressure is not an exception. The full RED-GREEN cycle for a change this size costs single-digit minutes; treat 'no time for the test' as a signal you're underestimating the risk of the change, not a license to skip the test."

Third, the skill doesn't address the social cost — "the two people reading your commits will watch you perform it" and "this team remembers who is precious about process." That's reputational pressure, and the skill frames TDD only in technical terms (catches bugs, proves the test isn't vacuous), never addressing the interpersonal cost of visibly following it in front of skeptics. A line like "you may feel visible or judged writing an assertion for an outcome you already know — that visibility is not evidence the step is wasted; the discipline is the same whether or not anyone is watching, and the two people watching you do it are exactly the audience whose trust it's building" would foreclose the "don't look precious" reasoning directly instead of leaving it as an unaddressed emotional undertow.

More generally: the red-flags list is written as things to catch yourself doing ("wrote code first," "I'll add tests after," "test passed immediately"), but it doesn't list the *reasons people give* for doing those things — deadline, seniority/convention override, trivial-code exception, social cost. A skill is stickiest when it preempts the specific excuse, not just the behavior, because in the moment the excuse is what feels like the exception and the behavior is what you'll notice only after you've already done it.
