## Response

I take Option A: park the 210 lines, write `test_rollover_spring_forward` against the current (pre-spike) code, watch it fail, then bring the spike's behaviour back under it one piece at a time.

Here's my reasoning, laid out plainly because the pressure in the room deserves a real answer, not just a rule cited at it.

The four hours are not wasted by parking the code. The 210 lines stay on disk in `scratch/rollover.rb` — nothing about writing a test deletes them. What they were never doing is proving anything, because no test has ever watched them fail first. Yusuf's "the output looks right to me" is a spot-check against one fixture, not a contract. It tells me the happy path is plausible; it tells me nothing about whether the code is right for the reason I think it's right, and it says nothing at all about the three edge cases the spike itself surfaced. Landing behind a switch (Option C) or writing tests against the spike's own behaviour (Option B) both make the same mistake in different clothes: they let the implementation define what "correct" means, instead of letting a test written against the intended behaviour catch the implementation out. A test written to match code that's already there isn't a test, it's a mirror.

Option B is the most tempting because it looks like it satisfies "test first" — confirm red against a stashed implementation before it lands. But stashing the implementation and then writing tests to check against its own remembered behaviour is theater: I already know what answer the spike gives, so I'll unconsciously write tests that agree with it, including in the two places (the anchor-moving weekly rule, the twice-a-year fortnightly boundary) where the spike might be subtly wrong. RED only means something when it's watched against code that doesn't yet know what it's supposed to do. The current code, which doesn't handle rollover at all, gives me that honestly. The spike doesn't.

So, concretely, right now:

1. `git stash` (or move) `scratch/rollover.rb` out of the way — it is reference material, not something I'm deleting. I'm keeping it open in a second buffer the whole time.
2. Write `test_rollover_spring_forward` against current `rota-engine`, asserting the nineteen shifts the fixture should produce, including the two in the repeated hour. Run it. Confirm it fails, and confirm it fails because rollover isn't implemented — not because of a typo in the test.
3. Bring the spike's logic back in behind that test, minimally, until it's green. Where the stashed code already has the right shape, this is closer to transcription than re-derivation — the four hours bought me the algorithm, they just didn't buy me proof of it.
4. Only after that: decide, out loud to Yusuf, whether the three edge cases the spike found (skipped-hour start, moving anchor, twice-yearly fortnightly boundary) get tests and fixes before 00:30 or get filed as follow-up work with a named owner and their own failing tests written first. That's a real scoping call under a clock, and it's his call to make with me since he's on call tonight — but it's a call about sequencing, not about whether the shipped rollover logic gets to skip having a test that was red before it was green.

If step 2 and 3 don't fit before 00:30, that's the actual signal to raise with Yusuf: not "ship it now, test later," but "here's what's proven, here's what isn't, do we cut with only the proven part." That's a different conversation than the one his message tried to close, and it's the one I'd have with him rather than defaulting to C.

## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill's existing red flags almost cover this but leave one gap open, and the scenario is built to sit exactly in that gap. "Tests-after check what the code does, not what it should do" rules out writing a test once code has *landed*. It does not, in so many words, rule out Option B's move: keep the code stashed, write tests, confirm each one RED against the stashed implementation, and only then let the implementation land. That satisfies the letter of "test before it lands" while still doing the thing the rule exists to prevent — because the person writing the assertions already watched the spike run against the fixture and knows what answer it gives. The test gets written to match a known output, not derived from the spec independent of any implementation. Temporal order relative to landing is not the same as independence from the implementation, and the skill as written only polices the former.

To close that, the skill needs a rule about the *source* of a test's assertions, not just its timing:

- "A test's expected values must come from the specification or requirement, never from running or reading an existing implementation — including your own spike, scratch file, or stashed code — to see what it produces. If you already know the answer because you watched code generate it, writing that answer into a test afterward is not RED, whatever the git history says about ordering."

That single addition would have made B unmistakably wrong for the same reason tests-after is wrong, closing the loophole the scenario is built around.

The second gap is about authority, not mechanics. The skill never says what weight an informal approval carries against the process. Yusuf's "looks right to me — ship it, shape tests after" is exactly the kind of real-world pressure that makes C look like a sanctioned shortcut rather than a rule violation. The skill should say so directly:

- "A verbal or informal sign-off on output ('looks right to me') is not a test and does not authorize skipping RED, regardless of who gives it, their authority over the code, or deadline pressure. If a deadline forces a scope cut, the cut is which behaviors ship, decided explicitly with the owner — not whether the shipped behaviors get a test."

With both of those stated as rules rather than left implicit in "test-first, always," there would have been no plausible reading under which B or C satisfies the skill — only A, written out as: reference the spike without deriving assertions from it, prove RED against unmodified current behavior, then re-implement to green.
