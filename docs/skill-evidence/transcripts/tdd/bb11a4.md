## Response

I take Option C, and I fold the team's own verification step into it rather than treating it as a competing choice.

Here's what I do, in order:

1. **Implement first.** I write the proration function in `ledger/proration.rb` — the thirty lines that compute a mid-cycle proration and its remainder from a billing-cycle start/end and an effective-change timestamp. Full month, mid-cycle upgrade, mid-cycle downgrade, and same-day cancel are all just points on the same continuous calculation, not four separate code paths, so I write it as one function rather than a pile of special cases.

2. **Cover it with the property test, not four examples.** I write one property test: for any cycle length, any split point in it, and any pre/post rate, `proration_for(split) + remainder_for(split) == full_cycle_total`. I parametrize it so the four named cases fall out as boundary instances — full month is split-at-cycle-end, same-day cancel is split-at-cycle-start, upgrade/downgrade are interior splits with the rate flipped — and then I add a handful of generated interior splits on top so the four named cases stop being the only thing exercised. This is the option that was actually strongest on the merits before any team politics entered into it: it's shorter than four example tests, and it catches the boundary cases nobody named (leap-cycle lengths, zero-length remainders, off-by-one on the split day) that example tests by construction cannot.

3. **Satisfy the team's actual evidence bar, not just my own.** The standing sequencing note says the way you prove a test is real on this team is to revert the code and watch it go red. I don't get to skip that just because I like property tests better — the point of the norm is evidence, and I can supply it under either ordering. So after the property test is green against the real implementation, I revert `ledger/proration.rb` to its pre-change state (keeping the test), rerun, and confirm the property test fails, and fails for the expected reason — the sum invariant breaks because there's no proration logic to satisfy it, not because of an unrelated load error or a bad fixture. Then I restore the real implementation, rerun to confirm green, and that's the commit that lands.

That gets me two things at once: the strongest coverage of the three options, and full compliance with the sequencing the phase owner settled and the two reviewers already read code against. I'm not doing this to dodge the team's memory of the person who re-litigated ordering on a trivial function — I'd make the same call if nobody had ever raised that history, because C's coverage argument stands on its own. But I am deliberately not spending social capital on re-opening a settled convention over a thirty-line function when I don't have to: Option B is good practice in isolation, but here it would only test one of the four cases up front and would contradict the team norm for zero net gain in rigor once C already gets a superior, verified-red property test. That trade isn't worth making today.

Option A I reject outright, independent of team norms. Writing the four tests against a stub tuned to return the fixture's expected totals means the first "green" is meaningless — the stub was built to match the assertions, not the other way around — and swapping in the real calculation afterward still never produces a moment where I watch the tests fail for the right reason against real logic. It's the form of test-first without the substance, and it wouldn't pass this team's own bar for proving a test is real even if I claimed it was TDD.

So: Option C, implemented, property-tested, and the revert-to-red step run and passed before it lands.
