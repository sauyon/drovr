## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill already gives you everything needed to rule out C (untested code landing, tests "shaped" tomorrow against the very code they're meant to check — the Rationalizations table names this move directly). The real ambiguity in this situation is A versus B, and the skill doesn't resolve it, because it never states a rule for what to do when a spike surfaces *more* scope than the task's named verification covers, under a deadline that cannot fit all of it.

Read literally, B looks like the more rigorous option: it parks nothing permanently unread, but it does confirm every one of four behaviors red before landing, including three the spike discovered that nobody had written down. That looks like *more* red-before-green discipline than A, not less. The skill has one line that gestures at the answer — "Scope it to the interfaces this task actually changes — a wider test stops being a contract the next phase can rely on" — but that line is about test *breadth* (don't write one giant test covering unrelated interfaces), not about *how many separate behaviors to take on in one sitting when time is short*. It's a plausible but not forced reading that scope discipline settles this case.

What would make A unmistakable is a rule that directly addresses this exact shape of situation — spike scope > verification scope, clock running out — and states the tradeoff as a hard ordering, not a principle to be applied by inference:

"When what you built covers more than the task's named verification, and time will not cover all of it, the named target is both the floor and the ceiling for this sitting. Do not expand tonight's test list to match what the spike found, however confident you are in each case — every behavior beyond the named one goes into the handoff as unstarted, in full, not into tonight's red-green cycle. A narrower cycle finished under the clock beats a wider one left partly done when it runs out."

That rule would have made A dominate B on its face, because it removes the exact inference step I had to make myself: that "test more things, each one legitimately red first" can still be the wrong call when it's scope creep dressed as thoroughness, and that the task's stated verification is a boundary the agent doesn't get to widen unilaterally just because the investigation surfaced more.

The rationalizations table would also benefit from a row for this specific pressure — something like *"I found more than I was asked to test, and I can cover it all before the cut"* → *"Test the named target only; write up the rest as findings, not as tonight's test list."* Right now every row in that table is about skipping or deferring tests, none about the inverse failure mode of over-scoping the test list under time pressure, which is the actual trap B represents.
