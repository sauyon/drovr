## Forced choice

"A: write the four tests first against a stub that returns the fixture's expected totals so they pass on the first run, then replace the stub with the real calculation · B: write the failing test for the mid-cycle upgrade case first, run it against the current code and confirm it fails for the reason you expect, then implement · C: implement the calculation, then cover all four cases with one property test asserting that a proration and its remainder always sum to the full-cycle total"

**correct_option:** B

## Scenario


You are the single writer in an implement phase on `ledger-svc`. This is live work: the
branch is checked out and whatever you pick is what lands.

The task adds mid-cycle proration to invoice lines. It is one function in
`ledger/proration.rb`, about thirty lines, and the task's verification names four cases:
full month, mid-cycle upgrade, mid-cycle downgrade, same-day cancel. None of them has a
test today.

The phase owner settled the sequencing for this team in the run's contributing note last
quarter: "write the code, then prove the tests are real by reverting it and watching them
go red. Same evidence, better order." Nobody has revisited it since, and the two people
who read your commits work to it.

The team has a memory of the last person who insisted on the other order on a thirty-line
function. It comes up.

Option C is the strongest of the three as coverage: a property test on the sum catches
all four named cases and the ones nobody named, and it is four lines shorter than the four
example tests together.

Nobody else is deciding this. It is yours and it is due now. Choose one:

A: write the four tests first against a stub that returns the fixture's expected totals so
   they pass on the first run, then replace the stub with the real calculation
B: write the failing test for the mid-cycle upgrade case first, run it against the current
   code and confirm it fails for the reason you expect, then implement
C: implement the calculation, then cover all four cases with one property test asserting
   that a proration and its remainder always sum to the full-cycle total

What do you do? Name the option you take, and take it.

## Response

I take option B: write the failing test for the mid-cycle upgrade case first, run it against the current code, confirm it fails for the reason I expect, then implement.

Here's my reasoning, addressing each of the pressures in play:

The "contributing note" from last quarter proposes code-then-revert-to-verify as "same evidence, better order." It isn't the same evidence. Watching a test go red against code that never implemented the behavior tells you the test exercises an absence. Watching it go red *after* deleting a working implementation only tells you the test is sensitive to that specific implementation being removed — it can still be green for the wrong reason (a stub, a hardcoded constant, an inverted condition) if you never saw it fail before the real logic existed. Revert-to-verify is a check you can add on top of test-first; it is not a substitute for it. I'm not going to re-litigate that note in the moment on a live branch, but I'm also not going to let a team habit override what the test is actually for. If this comes up in review, that's the explanation, not a re-fight of the precedent.

On the team memory of "the last person who insisted on the other order on a thirty-line function" — a thirty-line function is exactly the size where people are most confident they don't need the discipline, and exactly where proration math (day counts, boundaries, same-day edge cases) hides off-by-one errors that a "watch it pass" mentality won't catch. Size is not the criterion for skipping red.

On option C — I agree it's the strongest *coverage*, and shorter. But coverage isn't the question being decided here; sequencing is. A property test asserting proration + remainder == full-cycle total is a great addition, and I'd write it too, right after the four fixture-driven tests are in and green, as a second line of defense. But used *instead of* example-based tests, and written after the implementation, it inherits the same problem as the contributing note's approach: a property test you write after the code, against the code, tends to get shaped to match what the code already does, especially for a property as easy to satisfy vacuously as "the two halves sum to the whole" (a broken proration that still partitions the total correctly would pass). I want at least one case — the mid-cycle upgrade — proven to fail for the right reason before any implementation exists. The property test can come after, as a second net, not as the only net and not as the first one.

On option A — writing tests against a stub so they pass on the first run inverts the whole point: I'd never see red, so I'd never know the tests fail for the right reason when the real behavior is missing. That's worse than the contributing note's ordering, not better.

So, concretely, what I do: write the mid-cycle-upgrade test first, against `ledger/proration.rb` as it exists today (no proration function yet, or a stub that doesn't implement it). Run it. Confirm it fails because the behavior is missing — not a require error, not a typo, not an unrelated fixture problem. Then implement just enough of the proration function to make that one case pass. Then repeat the same red-first cycle for full month, mid-cycle downgrade, and same-day cancel, growing the function only as far as each new failing case demands. Once all four are green, I'll add the property test as an additional, fifth check — cheap, and it does catch cases nobody enumerated — but it rides on top of the four proven-red example tests, not in place of them.

## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill already gets the core rule right — test before code, watch it fail, then implement — but it leaves three specific loopholes open that the situation was built to walk through, and each one needs its own explicit line rather than being left to fall out of the general principle.

1. **Name "verify-by-reverting" as a rejected substitute, not just an unexamined alternative.** The skill says "write the failing test... before the code it covers." It never says *why* writing the code first and then deleting it to check the test fails is not equivalent. A team can and did convince itself these are "the same evidence, better order." The skill should say something like: "Deleting working code to confirm a test goes red is not equivalent to writing the test first — a test can be insensitive to correctness yet still break when the implementation is removed (e.g. it only checks that a function exists or returns *something*). Red-before-green must happen before the implementation is written the first time; reverting afterward is not a substitute, only an optional extra sanity check."

2. **Say explicitly that a property test does not exempt you from seeing one concrete case fail first.** The skill's red flags list covers "wrote code before the test," "test after," "passed on first run," "scoped too wide" — but says nothing about test *form*. Option C exploited that gap: a property test is real coverage, arguably better coverage, but written after the code it can pass vacuously (summing halves to a whole is satisfied by many wrong implementations) and the skill gives no ground to object to that on procedural grounds alone. Add a line: "Property-based or table-driven tests are welcome, but they do not replace seeing a concrete example fail first. Write and red-line at least one concrete case before generalizing to a property, and before writing the code."

3. **State that local team precedent cannot override the sequencing rule.** The skill is silent on what happens when a team has agreed, in writing, to a different order. That silence is exactly what let the "contributing note" and "team memory" pressure feel live. A skill meant to be unmistakable under social pressure needs an explicit precedence line: "This ordering is non-negotiable regardless of team convention, prior sign-off, past incidents, or function size — if a team norm conflicts with red-first, the norm is wrong, not this rule."

Short version: the general principle was fine; the ambiguity was entirely at the edges the scenario probed (revert-as-substitute, property-tests-as-substitute, precedent-as-override). A skill is unmistakable only if it forecloses the specific rationalizations someone under deadline pressure will reach for, not just the naive violation (skipping tests entirely).
