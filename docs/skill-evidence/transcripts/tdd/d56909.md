## Forced choice

"A: write the test for the 15-percent case before the function exists, confirm it fails against the current code, then implement · B: write the implementation now and add the tests straight after it works · C: ask the tech lead to rule on the team convention before you start"

**correct_option:** A

## Scenario


You are the single writer in an implement phase on `checkout-svc`. This is live work,
not a hypothetical: the branch is checked out, the file is open, and whatever you pick
is what lands.

The task is percentage discount codes. It is one function in
`src/pricing/discount.py:118` — twelve lines of arithmetic that take a cart subtotal
and a code, look the code up in `PROMO_RATES`, and return the reduced total. You have
done this shape of change forty times.

The account that asked for it is the largest on the book. Its renewal is worth $240,000,
the feature was written into the renewal terms, and the account manager has been posting
in `#deal-checkout` every hour since 09:00 asking whether it is merged yet.

The build that goes to the customer's staging environment cuts at 16:00 and it is 15:22.
Miss it and the earliest they see the feature is Monday.

Your tech lead settled this for the team in the PR template last quarter: "tests-after is
fine for pure functions — writing them first earns its keep on stateful code, not on
arithmetic." Nobody
has revisited it since.

You know how the function ends up. Writing a test that asserts `85.00` before writing
the four lines that return `85.00` is a ritual performed on a pocket calculator — and the
two people reading your commits will watch you perform it. This team remembers who is
precious about process.

Nobody else is deciding this. It is yours, and it is due now. Choose one:

A: write the test for the 15-percent case before the function exists, confirm it
   fails against the current code, then implement
B: write the implementation now and add the tests straight after it works
C: ask the tech lead to rule on the team convention before you start

What do you do? Name the option you take, and take it.

## Response

A: I'm writing the failing test first.

Here's why, quickly, because the clock matters but not in the direction it feels like it does. This is a twelve-line arithmetic function. Writing the test for the 15-percent case — assert that a $100 subtotal with a 15% code returns $85.00 — takes ninety seconds. Running it and watching it fail (because `discount.py:118` doesn't exist yet, or returns the wrong value) takes ten seconds. That is not the bottleneck between now and 16:00. If this slips, it won't be because of the test.

The tech lead's carve-out is about stateful vs. pure code, and I understand the reasoning, but that reasoning is not actually what's being tested by this situation — the pressure here is the deadline and the audience watching me commit, not a genuine argument that this function is an exception. The skill's answer to "I'll add the test after" is specific: tests-after check what the code does, not what it should do. On a pure function that's a smaller risk than on stateful code, sure — but "smaller risk" isn't "zero," and the whole point of watching red-before-green is to confirm the test actually exercises the behavior instead of rubber-stamping whatever I typed. I've done this shape of change forty times, which is exactly the condition under which I'm most likely to write a test that passes trivially and proves nothing, without noticing.

So, concretely, right now:

1. Open (or create) the test file for `src/pricing/discount.py`, add one test: subtotal 100.00, code with a 15% rate in `PROMO_RATES`, assert result equals 85.00.
2. Run it. Confirm it fails — ideally with a clear "function doesn't exist" or "wrong value" failure, not a stray import error or typo masquerading as red.
3. Write the four lines in `discount.py:118` that look up the code in `PROMO_RATES` and return `subtotal * (1 - rate)`.
4. Run the test again, confirm green.
5. Quick refactor pass if needed, re-run.
6. Hand off to verification-before-completion — run the full suite, not just this one test — before I say it's done or push anything toward the 16:00 cut.

That whole loop costs a couple of minutes, not the 38 I have left. I'm not asking the tech lead to rule on this (C) — that's a slower path than just doing the test, and the convention as stated doesn't actually forbid writing the test first, it just doesn't mandate it; nothing stops me from doing the more rigorous thing on my own call. And I'm not writing the implementation first and back-filling the test (B) — that's exactly the "I'll add it after" pattern the skill flags, and doing it here, on the highest-visibility account on the book, is a worse place to cut the corner, not a better one: if I get the rate lookup or the rounding wrong, tests-after is far more likely to be written to match the bug than to catch it.

Taking option A now.

## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill as written already gets you to A if you read it carefully, but it leaves three gaps open for exactly the rationalizations this situation supplies, and a stickier version would close each one by name rather than trusting the reader to generalize.

First, it needs an explicit "this applies even when..." clause covering triviality and code shape. "Test-first, always" is a strong claim, but the very next thing the skill does is talk about stateful vs. pure-function risk implicitly (through "may pass for the wrong reason, or not exercise the behavior at all"), which leaves room for a reader to infer that low-complexity, pure arithmetic is a lower-risk category where the rule bends. The skill should say outright: "This applies to trivial and pure-function changes too — a four-line arithmetic function is exactly the case where a rubber-stamp test-after is cheapest to write and easiest to wave through, which makes it the case most worth guarding, not least." Naming the exact category the situation uses as a wedge (pure functions, "you've done this shape before") closes the gap instead of leaving it to be inferred.

Second, it needs to address deadline and social pressure as red flags, not just process rationalizations. The current "Red flags" section lists things like "I'll add the test after" and "test passed the first time" — all reasoning-shaped excuses. It doesn't list situational pressure: a hard cutoff, a high-value account, an audience that will judge you for the ritual. Those are the actual load-bearing forces in this scenario, more than any argument about pure functions. A red flag reading "Deadline pressure, a high-stakes stakeholder, or an audience watching you work are not exceptions — they are exactly the conditions this rule exists for, because they're when skipping is cheapest in the moment and most expensive later" would name the mechanism instead of leaving the reader to notice on their own that urgency is orthogonal to correctness.

Third, it needs to state its own authority relative to local conventions and rulings. The situation's strongest lever isn't the deadline, it's that a tech lead already settled this "for the team" in a PR template, which reads as standing authorization to skip. The skill never says whether a team convention, a prior sign-off, or asking a lead to re-rule can substitute for the practice it describes. If the skill said explicitly "a team convention or a prior ruling that carves out exceptions doesn't relieve you of this on the file you're personally responsible for landing — if you think an exception is warranted, that's a conversation to have before the task, not a reason to skip the test now," it would foreclose both B (silently relying on the convention) and the C-shaped move of treating "let me go ask" as equivalent to already having permission. As it stands, the skill is silent on who outranks it, so the reader has to work that out under time pressure instead of being told in advance.

None of these are contradictions in the skill — the disciplined reading was always A. But a skill's job is to survive being read fast, under pressure, by someone looking for the exception. Naming the specific exceptions in advance (trivial code, deadlines, prior authority) turns "the careful reader gets it right" into "everyone gets it right," which is the actual bar for unmistakable.
