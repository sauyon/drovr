## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill actually contains everything needed to rule out A vs B correctly, but it's spread across two separate principles that the reader has to notice apply *together* to this exact scenario, rather than being fused into one rule that names it directly. That's what left room for B to look like the more rigorous choice instead of the wrong one.

Specifically:

1. **Scope-under-pressure isn't stated as a single rule.** Step 1 says "scope it to the interfaces this task actually changes"; the rationalizations table separately says "there isn't time — write the RED test for the one behavior you can finish, put the rest in the handoff as unstarted." Both point at Option A, but nothing in the skill says the two combine into: *when a spike surfaces more failing behavior than you have time to cycle through, that is not a reason to widen tonight's test set — it's a reason to test only the named behavior and hand off the rest untested.* Without that fused rule, B reads as the more disciplined answer (it still watches everything go red) rather than as scope creep wearing TDD's clothing. A dedicated rationalization row would have closed this — something like: *"The spike also proved three more things, might as well test those too."* → *"Test the one behavior the task named. Everything else is a finding, not tonight's scope — write it down, don't test it under the clock."*

2. **Nothing distinguishes a specified requirement from an assumed one.** Step 3 says "write the test against the requirement as stated, not against anything you have already built," which is meant to stop a test from being reverse-engineered off code. But it doesn't say what to do when the "requirement" for an edge case has never been stated by anyone — no one has agreed what correct behavior *is* for the fortnightly-boundary-twice-a-year case. A red test written against the spike's own guess for that case fails the same way a test written after the code does: it enshrines what the code happens to do as the spec. The skill needed an explicit line: *a red test is only evidence if someone other than the spike agreed on the expected behavior first; if no one has, that's a spec gap to report, not a test to write tonight.*

3. **The rationalizations table frames pressure as internal monologue, not external authority.** Every row is phrased as something *you* think ("I already validated it," "there isn't time"). Yusuf's message is a different shape — a named owner, on call, explicitly telling you to ship and defer tests. The underlying instruction (cite the named test, don't let approval substitute for verification) still applies, but the reader has to map an external directive onto a table of first-person rationalizations to see that. One row written as *"someone with authority told you to ship it and test later"* → *"their sign-off is data about the output, not evidence about the code; give them the choice with the test's actual state attached, don't let the instruction stand in for the run"* would have made that mapping automatic instead of inferred.

In short: the skill should have had one explicit rule collapsing "deadline pressure" + "scope discipline" + "discovered-but-unspecified behavior" into a single sentence naming this exact shape of situation, plus a rationalizations-table row for third-party authority overriding the test, rather than leaving both as separate principles the reader has to combine correctly under time pressure.
