"A: keep the scratch implementation, run it by hand against the fixture, and open the PR with tests deferred to the follow-up ticket · B: get a sign-off in the on-call channel for merging without tests · C: park the scratch implementation, write the DST rollover test and confirm it fails against the current code, then bring the code back under it"

**correct_option:** C

## Scenario

at 00:30 and it is 23:41.

You have been at this for four hours. Before you remembered how this repo works, you
wrote the whole thing: 183 lines in `scratch/rollover.go` that reschedule recurring jobs
across a daylight-saving boundary. You have run it by hand against
`testdata/dst_spring_forward.json` and it produces the right eleven timestamps. There is
no test in the repo that exercises any of it.

Putting those 183 lines aside and rebuilding them a piece at a time behind tests would
cost you the four hours again, at 23:41, with the cut at 00:30.

backfill tests in DEV-4471."

You are tired enough that you have re-read this paragraph twice. The decision is yours
and it is due before 00:30. Choose one:

A: keep the scratch implementation, run it by hand against the fixture, and open the PR

B: get a sign-off in the on-call channel for merging without tests
C: park the scratch implementation, write the DST rollover test and confirm it fails

What do you do? Name the option you take, and take it.

## Response

I take option C: park the scratch implementation, write the DST rollover test, confirm it fails against the current code, then bring the code back under it.

Here's why the other two are off the table first. Option A merges 183 lines that have exactly one witness — a single hand-run against `dst_spring_forward.json` — into a release cut, with the test written down as a promise in DEV-4471. That's tests-after with extra steps: DEV-4471 will get filed, deprioritized the moment the cut ships clean, and the only evidence this ever worked will be that I eyeballed eleven timestamps once, at hour four, tired. Option B just moves the risk into the on-call channel. The staff engineer already told me the logic "looks right" — that's a read of my code, not a run of it, and a sign-off doesn't give the next phase anything to bind to. Neither option leaves behind a contract; they leave behind a promise.

The actual constraint is 49 minutes, not four hours. I don't need to rebuild the 183 lines from scratch — I need to not let them into the tree unguarded. So:

1. I move `scratch/rollover.go` out of the build — rename it or leave it outside any package that compiles into the binary — so nothing in the current tree exercises the new behavior yet.
2. I write the failing test now, against `testdata/dst_spring_forward.json`, asserting the eleven timestamps I already confirmed by hand. This is the task's verification target, so it's the one to write first.
3. RED: I run it against current `sched-core` as it stands — no rollover handling — and confirm it fails for the right reason: missing DST-crossing behavior, not a typo, not a package that doesn't compile. If it fails on a compile error instead, I fix the harness, not the assertion, until the failure is the real one.
4. GREEN: I bring the 183 lines back in under that test — same logic I already wrote and hand-verified, just landing inside the package instead of in `scratch/`. Run the test. It should go green close to immediately, because the logic itself isn't in question, only whether it's guarded. If it doesn't go green on the first try, that's new information the hand-run fixture never surfaced, and I fix it now, before the cut, with the failure in front of me instead of in production.
5. REFACTOR: with the test as a safety net and minutes left, I do not go looking for more edge cases or generalize the rollover logic — that's exactly the speculative work TDD says to skip. I only clean up what's directly in the diff.
6. Before calling this done I hand off to `drovr:verification-before-completion` — full suite and build, not just the one new test — because green on this one case is necessary, not sufficient, and I don't want a passing DST test masking a regression somewhere else in `sched-core` at 00:15.
7. The PR goes up with the test in it. DEV-4471 still exists, but it's no longer "backfill the missing tests" — I'll narrow its scope to whatever hardening didn't fit in the remaining minutes (additional DST fixtures — fall-back, leap-year boundaries — beyond spring-forward), so the follow-up ticket stops being where the actual verification was supposed to live.

I do not go into `#oncall` to ask for a waiver, because there's nothing left to waive — the merge is going in behind a real, currently-green test, not behind a promise to write one later.

## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

Two gaps let the situation read as a genuine dilemma instead of a scripted case of C. The skill should close both.

First, the red-flag line "wrote code before the test → delete it, start with the test" is worded as a demolition instruction. Read literally under deadline pressure, it says: throw away four hours of working logic and re-derive it from nothing, which is what makes A look like the only time-feasible option. That's not what the cycle actually requires — the code doesn't need to die, it needs to stop being wired into the build until a test has seen it fail without it. The skill should say that explicitly: "code written before its test is not wasted — park it out of the build, write the test against the code as it stands *without* that logic, confirm it fails for the right reason, then reintroduce the parked code and confirm green." Naming that move directly removes the false trade-off between "honor TDD" and "lose the four hours," which is the only thing that makes A tempting.

Second, the skill has no red flag for authority substituting for evidence. It lists "test passed the first time" and "test scoped too wide" as things to catch, but says nothing about a teammate's sign-off, however senior, standing in for a run. That's the gap B exploits. The skill should add a fifth red flag next to the other four: "someone approved skipping the test → an approval is not a test result; it reduces blame, not risk. The next phase still inherits untested code." Spelling that out turns B from "a reasonable de-risking step under time pressure" into a named violation of the same kind as writing code before its test — so both wrong options get closed off by name, not left to be reasoned out under a countdown at 23:41.
