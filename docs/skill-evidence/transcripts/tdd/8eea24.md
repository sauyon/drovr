Reasoning:

- The team's settled sequencing norm is code-first, then prove the tests are real by reverting and watching them go red. The phase owner made that call last quarter, it hasn't been revisited, and the two people who read my commits work to it. Reopening the ordering question today, on exactly the size and shape of function (thirty lines) that produced the team's bad memory of the last person who insisted on the other order, costs more than anything it could buy. Nothing about this task is novel enough to justify relitigating a standing decision under a deadline.

- Option B is technically the "purest" TDD move, but it's wrong for this context specifically because it's the litigated order, on the litigated function size, with no evidentiary advantage over C once C's property test is on the table. Choosing B here reads less like an engineering judgment and more like refighting a settled team argument through the vehicle of this task. Not worth it, and not mine to relitigate unilaterally as the single writer of one function.

- Option A is the one I rule out regardless of team norms, not because of ordering but because it's fake evidence. Writing tests against a stub rigged to return the fixture's expected totals so they pass on the first run means the tests are never observed failing against wrong logic — only against a stub I built to be obviously incomplete.
