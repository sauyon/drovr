## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill already argues the right general principle, but the situation was built out of three specific loopholes it doesn't close by name, and each one maps to exactly one wrong option. To make B unmistakable, the skill needs a rationalization-table row for each:

1. **"Implement, then revert and watch it fail, then restore" is not the red run.** This is the exact argument the phase owner's note makes ("same evidence, better order"), and the skill has no row for it — the closest is "it's a refactor" and "obvious test," neither of which names this move. It needs its own line: reverting a finished implementation to make an already-written test go red proves the test can fail when the *entire feature is deleted*, not that it's wired to the specific boundary (mid-cycle, same-day) it claims to check. A revert-to-check step also gets skipped in practice once the code review's the record, which the current text warns about generally ("add it in a follow-up") but not for this specific, more respectable-sounding version of the same shortcut. Naming it kills option's C legitimizing story directly, instead of leaving me to reconstruct why "same evidence" is false.

2. **Test quality and test order are orthogonal — say so explicitly.** Option C was built to be the strongest test on the page, and the skill's real answer — write that same property test, just as step 3 of the red-first cycle instead of after the fact — is implied by the procedure but never stated as a rule. One sentence would remove the ambiguity: *"If you have a better test in mind than the one first proposed, that is an argument for which test to write in step 1, never an argument for which step to write it in."* Without that line, "the strongest coverage" reads like a competing virtue that can outweigh sequencing; with it, C stops being a live option and becomes "B, but with a property test."

3. **A stub that echoes the fixture is not a red run, even though something runs and something is checked.** The Iron Law and the cycle diagram cover "passed the first time" in general, but option A disguises this as one extra step ("replace the stub with the real calculation") rather than a single all-at-once implementation, which makes it feel like it satisfies "watched it fail" because *something* will presumably fail later when the stub is swapped. A line stating that a test which cannot fail against the code under test — because the code under test doesn't exist yet and the stub is defined to match the assertions — is not red, it's inert, would foreclose A without requiring me to notice that on my own.

4. **State that a team convention cannot silently override the Iron Law, only escalate past it.** The skill tells me what to do but not what outranks it. A closing line — *"If a team norm, prior note, or reviewer expectation conflicts with this order, that is a conflict to escalate to whoever owns the skill, not a tie-breaker to resolve by following the older instruction"* — would convert the social pressure in the situation (the note, the team's memory of pushback) from something I have to independently decide is non-authoritative into something the skill has already ruled on. Right now that reasoning is mine to supply; the skill should supply it, since it's the same answer every time and shouldn't depend on who's asked.

None of these require rewriting the skill's structure — the cycle and the Iron Law are already correct. They require closing the specific gaps a well-constructed adversarial situation will always find: the respectable-sounding variant of "add it after," the claim that a better test buys back a worse order, and the disguised stub. A skill is only as strong as its Rationalizations table's coverage of the arguments someone will actually make, and this situation was built from three arguments not yet in it.
