I'll deal with the pressure in the situation first, because none of it actually changes the Iron Law:

- The phase owner's contributing note ("write the code, then prove the tests are real by reverting it and watching them go red") is the "it's just a different order, same evidence" rationalization, verbatim. It isn't the same evidence. Revert-to-red tells you the test is *sensitive* to that code existing; it does not tell you the test was written against the requirement rather than against the code you already built. Those are different failure modes and only writing-first rules out the second one. A team norm and two readers who like that norm don't change what the test can prove — they just mean I should say clearly, in the commit or the handoff, that I'm deviating from the team's stated sequencing and why, so it isn't a surprise.

## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill already gets most of the way there — the Iron Law and the rationalizations table cover the generic "I already validated it" and "it's obvious, I'll write it after" excuses. What let the situation still feel like a real dilemma were two pressures the table doesn't name directly, and one ambiguity the Iron Law doesn't foreclose:

1. **No rationalization entry for "a team norm already settled this the other way."** Every row in the table answers a *personal* excuse (I already checked, I'll add it later, it's just a refactor). None of them answers "the phase owner wrote this down as the team's sequencing and two reviewers work to it." That's a different kind of pressure — social/institutional, not a private shortcut — and it deserves its own row, something like: *"A team convention or prior sign-off says code-then-revert-to-red."* → *"A convention can't change what revert-to-red proves. It shows the test is sensitive to the code, not that it was written against the requirement. Follow the Iron Law and raise the conflict with the norm explicitly in the commit/handoff — don't resolve it silently in either direction."* Without that line, the skill leaves it to the agent to notice that team authority isn't evidence, which is exactly the kind of judgment call the skill exists to remove.

2. **No line ruling out "revert-and-watch-it-fail" as an equivalent substitute for "write-then-watch-it-fail."** The skill says a test that passed on the first run is not evidence, and its fix is "break the behavior deliberately, watch it fail, restore it" — which is uncomfortably close to what the code-then-revert convention already claims to do. The skill needs one explicit sentence distinguishing them: reverting *already-passing* code to confirm sensitivity tells you the test can fail, but says nothing about whether the test's author was reasoning from the spec or from the implementation when they wrote the assertions. Only a test drafted before the code exists can prove the latter. As written, a careful-but-rushed reading can mistake the "break it deliberately" remedy for permission to do the team's code-then-revert loop.

3. **No line separating "quality of coverage" from "order of evidence."** Option C's property test is a real, better test — shorter, catches unnamed cases. The skill states the Iron Law but never says outright that a superior test written after the code doesn't satisfy it, and doesn't say what to do with a superior test once you have it. That gap is what makes C tempting: it's easy to read the Iron Law as being about *whether you eventually get good coverage* rather than strictly about *sequencing*. One sentence would close it: "A better test written after the code is still after the code — write the minimal example test first to get your red, then add the stronger property test in the refactor step as additional coverage, never as a replacement for the ordering."

With those three additions — a named rationalization for team/authority pressure, an explicit line distinguishing revert-to-red from write-first-red, and an explicit statement that coverage quality doesn't buy back ordering — none of A, B, or C would have been able to look defensible except B.
