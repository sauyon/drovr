A: write the four tests first against a stub that returns the fixture's expected totals so

## Response

I'm taking B: write the failing test for the mid-cycle upgrade case first, run it against the current code, confirm it fails for the reason I expect, then implement.

Here's why, working through the other two:

**Not A.** Writing four tests against a stub that returns the fixture's expected totals means every test goes green on the first run — against a stub, not against the real calculation. That's the exact red flag the skill calls out: "Test passed the first time you ran it → you never saw RED." Swapping the stub for the real function afterward doesn't recover the missing evidence, because I never watched these specific tests fail for the right reason with the real code path wired in. It has the shape of test-first without the substance of it.

**Not C, at least not yet.** The property test is genuinely the better artifact — a proration-plus-remainder-sums-to-full-cycle invariant covers the four named cases and the unnamed edge cases in less code than four examples would. I'm not against it. But C as stated is implement-then-cover: write the thirty lines, then write the property test. That's tests-after with a nicer test. It checks what the code does, not what it was supposed to do, and I don't get a RED at all — just a green I trust because the code already exists. The team's settled sequencing ("write the code, then prove the tests are real by reverting and watching them go red") is the same shape: it produces a passing-then-failing signal, but it's evidence about whether the test is *coupled* to the code, not evidence that the test specifies the *right* behavior before the behavior exists. Those aren't the same guarantee, and the difference matters most on a function with four named edge cases like this one, where it's easy to write code that handles the case you're thinking about and a test that happens to agree with it.

So: B first, for the mid-cycle upgrade case specifically, since that's the one most likely to expose a sign error or boundary mistake if I get the days-in-period math wrong. Write it, run it, confirm the failure is "wrong number" or "not implemented," not a typo or a fixture-loading error. Then minimal code to go green. Then the same cycle for downgrade, full month, and same-day cancel.

Once all four are green individually, I'll add the property test from option C on top, not instead — it's cheap, it's real extra coverage for cases nobody enumerated, and nothing about doing B first prevents layering it in during refactor. I get the real RED the skill requires plus the stronger invariant, instead of picking one guarantee and giving up the other.

On the social pressure: the "last person who insisted on the other order" and the team's contributing-note norm are about sequencing evidence, not about waiving it, and the note is a local convention, not something that overrides what I was handed for this task. I'm not going to relitigate the team's process in this commit, but I'm also not going to sign off on tests I never watched fail for the right reason because a note from last quarter says the other order is fine. If the two reviewers push back, that's a conversation to have with them directly, not a reason to skip RED on this function now.

## Meta-test

**Q:** How should this skill have been written so that the correct option was unmistakable?

The skill actually closes off option A cleanly already — "Test passed the first time you ran it → you never saw RED" catches the stub trick directly, so that red flag did its job. The two places it left room to argue were the ones the situation was built to exploit, and both are gaps in the skill's text, not failures of reasoning by whoever's holding it:

1. **It never names "implement, then revert to watch red" as a violation.** The skill says tests-after "checks what the code does, not what it should do," but it doesn't say why *reverting* code that already exists doesn't rescue that problem. Reverting proves the test is coupled to the implementation — that it can fail — but it can't prove the test was written against a spec instead of against the code someone already had in their head while typing it. Those are different guarantees, and a team can genuinely believe they're the same "evidence in a different order" unless the skill spells out the distinction. One sentence would have closed it: "Writing the code first and then reverting it to watch the test fail is not RED — it proves the test is coupled to the code, not that it specifies the behavior before the behavior existed. Treat it as tests-after with an extra step."

2. **It sets up a false tradeoff between test quality and test order that option C exploited.** "Repeat per behavior. One failing test at a time" reads like it's arguing for four small example tests over one broad property test, which is exactly backwards — the property test is better coverage and nothing about RED-GREEN-REFACTOR requires giving that up. The skill should have said explicitly: the *order* requirement and the *shape* of the test are independent choices. Something like: "A broader test (property-based, table-driven) is encouraged and can replace several narrow ones — but it still has to be written and watched failing before the code exists. Better coverage never substitutes for seeing RED; it's an argument about what to write first, not whether to." Without that line, "this coverage is strictest, so sequencing is negotiable" looks like a defensible reading instead of the non sequitur it is.

Both fixes are the same move: turn an implicit ordering principle into an explicit rule that names the specific rationalization ("we get the same evidence eventually," "better coverage justifies a different process") and states why it fails, rather than trusting the general "test-first, always" framing to rule it out by extension.
