# Spec: Skill Stickiness

drovr's skill docs read well and do not bind under context pressure: they describe correct
practice but nothing in them constrains an agent working inline or mid-drift. This spec decides
five fixes, one new meta-skill, and an empirical acceptance test that must pass before any fix's
armor ships.

---

## 1. Decision: build order

Section numbers below are not execution order. The actual order, and why:

1. **`drovr:writing-skills` + the scenario corpus** (§7) first — nothing else is testable until
   the harness exists.
2. **Capture arm A / RED per skill** (§8) at the pre-fix `HEAD`, before any skill file is
   touched — this is a hard gate; once fix 1 lands, arm A is unrecoverable without a checkout.
3. **Fixes 1 + 3** (§3, §5).
4. **Fix 4** (§6), using the RED wording from step 2 for the rationalization tables.
5. **Held-out arm B + the voice probe** (§8, §9).
6. **Fix 2's hook layer** (§4.2) — the only Rust work; independently orderable, no dependency on
   steps 1–5. Fix 2's doc layer (§4.1) belongs with step 4.

## 2. Decision: the four-tier authoring rule

Every design choice in this spec is labelled by which tier justified it. This labelling is
binding on later phases — new text added under this spec follows the same rule, and any
deviation from it needs the same kind of justification:

1. **Published evidence exists** → the evidence decides; keep the citation in the text.
2. **No published evidence, but the question is reachable by this run's probe loop** →
   **measure it** (§9). "Reachable" means expressible as a text variant of an existing probe
   skill, scorable by the existing rubric, within the §8 budget table's ceiling. Cost may
   discharge a tier-2 obligation only when measuring it would exceed that ceiling — never
   because it seems not worth it.
3. **Not reachable, or the measurement is inconclusive, and superpowers has a convention** →
   **follow superpowers**, stated plainly as a convention-follow, not evidence.
4. **No superpowers analogue at all** → **engineering judgement, marked `[tier 4]`.** Applies to:
   the gate's byte budget, skill body length caps, `per_turn`'s default, the reflex-marker
   boundary, the probe's model choice, the §2.1 caps. None of these may be defended as backed by
   a convention or a study.

Two standing exceptions, both procedural, both binding on every phase that writes skill text:

- **No fabricated measurements.** Never state a number, duration, frequency, or comparative as
  measured unless drovr measured it or a citation supports it. Rhetorical emphasis ("every
  time") is fine; a false measurement claim is not.
- **No copied text.** Both projects are MIT-licensed, so copying with attribution would be legal,
  but drovr writes its own sentences — mechanisms are ported, expression is drovr's. If a
  verbatim line is later found, add the MIT notice and credit.

### 2.1 What the tiering actually resolved

- **Authority vs. unity vs. moral framing** are all **tier 2**: none has a published isolation
  for procedural adherence (as opposed to persuading a chat model to violate its safety
  training), and all three are reachable by the §9 probe. Settled empirically in §9, not by this
  section.
- **Commitment devices** (announcement string, checklist→tracked-task binding) are **tier 1**:
  commitment ranks top-two in both cited Meincke studies. Promoted to primary; implemented as
  fixes 3 and 4.
- **Unity** ranks top-two in the 2026 replication, above authority — a deviation from
  superpowers, which withholds unity from discipline skills per the older ranking it cites.
  drovr applies unity to discipline skills on the strength of the newer data, using literal-truth
  phrasing (the next phase agent inheriting the work *is* the same agent, minus its context) —
  not superpowers' rhetorical "your human partner" framing. Unity gets no stronger standing than
  authority: the same paper that ranks it does not isolate either for procedural adherence, so
  both are still measured in §9, not assumed.
- **Position effects** (Lost in the Middle: retrieval accuracy is U-shaped, highest at start/end)
  are the basis for top-loading binding content (§6) — not proof mid-document rules are ignored;
  the finding is about document retrieval, not instruction obedience, and the models are three
  generations old. Applied only to §6's section ordering, not cited elsewhere.
- **Load-under-task-degradation figures** (−2–21%, secondary summaries not read in full) are
  consistent with the redundancy rule (§2.2) and the per-turn gate (§4.2) but do not establish
  either. Per exception 1, they are never quoted as measured drovr numbers in shipped skills.
- **Generic rule-wrapper ablation** (arXiv:2601.22025) is non-monotonic — degrades
  extraction/RAG, improves instruction-following +13% — read as "untested at drovr's scale," not
  as "generic rules hurt." Consequence: keep the per-turn card (§4.2) short and drovr-specific;
  do not claim to know its net effect.
- **Social proof** is adopted only in its true form (naming an observed failure mode from
  `docs/skill-evidence/`), never in invented-frequency form ("steps get skipped. Every time.") —
  forbidden by exception 1.
- **Persuasion effects shrink on newer/smaller models**, and none of the tested models (Haiku
  4.5, GPT-5 mini, Gemini 3 Flash) are the ones drovr runs (drovr's probes use Sonnet, §8;
  sessions run Opus-class). Extrapolating to Sonnet/Opus is a **stated assumption, `[tier 4]`**,
  not a finding. Register is treated as a real but secondary lever on that assumption.
- **Instruction phrasing**: every prohibition pairs with the required action in the same
  sentence, and every rule carries its reason, per Anthropic's current-model prompting guidance.
  The rationalization table's second column is written as an instruction ("Confidence is not
  evidence; run the command"), never as a bare rebuttal.
- **Transfer is not established** — the cited persuasion studies measure a chat model being
  argued into an unsafe response, not a coding agent adhering to a procedure it already agrees
  with over many turns under task load. This is exactly why §7–§9's own empirical loop exists;
  absolute compliance percentages from the cited studies (33%→72%, 35%→51%) are never quoted as
  drovr numbers.

### 2.2 Length and the byte budget

> **The byte budget applies to teaching content. Binding content is deliberately redundant.**

Teaching content stays terse, cross-referenced, never restated. Binding content — the
prohibition an agent will try to talk itself out of — is stated 3–4 times per skill (Iron Law,
red flag, rationalization row, checklist item); redundancy is the mechanism, not a defect.

**Decisions, binding on implementation:**

- `cli/tests/skills_valid.rs`'s `BODY_BUDGET` (currently 2200 bytes, over the four methodology
  skills only, `:17,20-25`) rises to **12000 bytes** `[tier 4 — no superpowers analogue, no
  evidence sets a correct length]`.
- **`using-drovr` gets its own cap, 9000 bytes**, and joins the checked list (previously exempt).
  It is injected in full on every `SessionStart`, making it the highest-cost document in the
  repo; leaving it uncapped while capping the rest is indefensible.
- Above cap, split into `references/`.
- `cli/tests/skills_valid.rs`'s byte check is **the single authoritative size check.** `wc -l` /
  `wc -w` are author guidance only, never asserted anywhere (including §11).

### 2.3 Skill docs are prompts, not replies

The user's global terseness preference governs assistant *replies*. It does not apply to
documents whose job is to survive a filling context window — this spec's skill-doc length
decisions are not in tension with that preference.

## 4. Decision: Fix 1 — un-scope the four methodology skills

**Problem this fixes:** all four discipline skills scope themselves to drovr phases in their
`description:` (e.g. "in a drovr phase"), while `using-drovr` makes inline work the default
mode — so the trigger text tells an agent working inline the skill does not apply to what it is
doing. Related: a `description:` that summarizes the workflow (as `using-drovr`'s currently does)
gives the agent a shortcut instead of a reason to read the skill; Anthropic's skill-authoring
guidance independently names the trigger description as a skill's highest-leverage line.

**New `description:` strings** (shipped defaults; RED, §7, may tighten wording per the four-part
closure's description clause, but these are the targets):

| File | New `description:` |
|---|---|
| `skills/tdd/SKILL.md:3` | `Use when implementing any feature or bugfix, before writing implementation code — requires a test you have watched fail before any implementation exists; no production code without a red test first` |
| `skills/systematic-debugging/SKILL.md:3` | `Use when encountering any bug, test failure, or unexpected behavior, before proposing or writing a fix — requires a reproduction and a mechanistic root cause before any code change` |
| `skills/verification-before-completion/SKILL.md:3` | `Use when about to claim any work is done, fixed, or passing, before reporting, committing, or handing off — requires running the verification command in this message and reading its output; evidence before assertion, always` |
| `skills/code-review/SKILL.md:3` | `Use when you have written any change, before calling it done or handing it forward — requires read-only reviewer subagents run in the foreground, with every Critical and Important finding resolved or explicitly recorded as deferred` |
| `skills/using-drovr/SKILL.md:3` | `Use at the start of every session and before every response, including before clarifying questions and before reading any file — routes to the right drovr skill and requires invoking it whenever there is even a 1% chance one applies` |

**Body demotions** — every drovr-phase reference in these bodies becomes a clearly-marked
*additional* consequence, never a precondition; the skill itself reads as unconditional
discipline:

| File | Change |
|---|---|
| `skills/tdd/SKILL.md:17-19` | Demotes to one subordinate line: *"Inside a drovr phase this also binds the next phase's contract."* |
| `skills/systematic-debugging/SKILL.md:14-17` | Same demotion. The read-only-explorer rule is unconditional and unchanged. |
| `skills/verification-before-completion/SKILL.md:15-17,40-42` | `drovr phase done` demotes to: *"If you are in a phase, this is also what gates `drovr phase done`."* |
| `skills/code-review/SKILL.md:13-14,41` | Same demotion for pipeline-review-phase and report-done references. |

**`docs/known-issues.md`:** one entry, in the file's existing convention (`## <symptom title> —
FIXED <date>`, `**Status:**`, `**Severity:** medium`, `**Found:**`, `### Symptom` / `### Root
cause` / `### Fix`), documenting that four descriptions scoped unconditional discipline to phases
while `using-drovr` makes inline the default. One entry only — the remaining fixes are design
work, not defect repairs.

## 5. Decision: Fix 2 — `using-drovr` becomes a per-turn gate

### 5.1 Doc layer (`skills/using-drovr/SKILL.md`)

New content, in this order (position-effects rule, §2.1):

1. `<SUBAGENT-STOP>` — keep as-is (`:8-11`).
2. **The 1% rule** `[tier 3]`, placed above the H1 inside the existing `<EXTREMELY_IMPORTANT>`
   framing: even a 1% chance a drovr skill applies means invoke it, paired with a cost-lowering
   clause (if it turns out not to fit, drop it — invoking costs almost nothing).
3. **The per-turn rule**: check before any response, including before a clarifying question and
   before read-only exploration.
4. **Instruction-priority ladder** `[tier 3]`: human's explicit instructions > drovr skills >
   default behaviour. This is the safety counterweight to the MUST language — not optional, not
   removable.
5. **Gate function**, as a fenced `dot` flowchart (branching, per §3's placement rule): message
   received → does any skill apply (≥1%) → invoke → announce → does it have a checklist → create
   one tracked item per step → follow it → only then respond.
6. **Red-flag table for the router's own failure mode** — invoking nothing at all (currently zero
   coverage). Candidate rows: "this is a one-line change", "I'll just look at the file first",
   "they asked a question, not for work", "I'm already mid-task, the router was for turn one",
   "escalating to a phase would be overkill so no skill applies." **Final wording is produced by
   RED (§7), not fixed here.**
7. Existing sections (single-writer, always-review, methodology, escalation) retained unchanged.

**Sectioning constraint:** items 2–5 sit outside every `<!-- reflex:section:NAME -->` marker
`[tier 4 — no sectioned-reflex analogue in superpowers]`. `[reflex.sections]` may subtract
advisory sections but must never be able to silently delete the routing core; only `[reflex]
enabled = false` removes it. Rationale in one line: a half-disabled router produces an agent that
believes it is running drovr and is not, whereas an explicit master-switch-off is an informed
choice.

### 5.2 Hook layer (new `UserPromptSubmit` hook)

Every decision below is `[tier 4]` — superpowers is `SessionStart`-only, so there is no
convention and no study covers per-turn re-injection. This is drovr's most novel mechanism and
ships as **an explicit, unmeasured bet**, recorded in `docs/skill-evidence/per-turn-gate.md`.

- `hooks/hooks.json` gains a `UserPromptSubmit` entry running a new, thin `hooks/user-prompt`
  script that `exec`s `drovr reflex --gate`. **`UserPromptSubmit` takes no `matcher`** — the
  existing `SessionStart` entry's `startup|clear|compact` matcher must not be copied across.
- **Cost is cumulative, not a rate**: `additionalContext` is appended every turn and stays in the
  window. Budget, stated both ways: **≤600 bytes per injection**, and a **cumulative ceiling of
  ~60 KB over a 100-turn session**.
- **Suppression rule** (bounds the cumulative cost): the card is emitted only when no `drovr:*`
  skill was invoked in the previous turn. A session already running the discipline is not
  re-told; a drifted session is. Bounds the common case to a handful of injections.
- **Assertion is byte budget, not tokens** — the CLI has no tokenizer and length ≠ tokens.
  Checked as rendered `additionalContext` ≤ 600 bytes in `cli/src/reflex.rs`'s test module.
- **Card content**: the 1% rule, the per-turn check, the announcement string, the
  checklist-binding line, a `<SUBAGENT-STOP>` line, and a pointer to `Skill drovr:using-drovr`.
- **Three API facts, verified against source, that implementation must handle**:
  1. `reflex.rs:143-152`'s `envelope()` hardcodes `"hookEventName": "SessionStart"` — must be
     parameterized to take the event name.
  2. `main.rs:114-118` declares `Reflex { skill: PathBuf }` required, and `main.rs:1276-1278`
     asserts bare `drovr reflex` errors. `--gate` forces `Option<PathBuf>`, a clap arg-group rule
     (`--gate` xor `--skill`), and an update to that test.
  3. **Card text source is a `const` in `reflex.rs`**, not extracted from `SKILL.md` — extraction
     would need markers inside the region §5.1 deliberately places outside all `reflex:section`
     markers. Accepted cost: drift between card and skill, mitigated by a test asserting the
     card's key phrases appear in `using-drovr/SKILL.md`.
- **Subagents**: `using-drovr:8-11` already carries `<SUBAGENT-STOP>` for this case, and this
  run's own foreground probe subagents (§8, §9) plus drovr's read-only reviewers all launch from
  a gate-on session. If `UserPromptSubmit` fires for Agent-tool subagents in this harness, the
  card would inject into every one and contaminate the probes. **Decision: the card carries its
  own subagent-stop line unconditionally**, and step 1 of §1's build order verifies empirically
  whether the hook fires for subagents, recording the answer in
  `docs/skill-evidence/per-turn-gate.md`.
- **Config**: new `[reflex] per_turn` bool in `ReflexConfig` (`cli/src/config.rs:39-64`),
  **default `true`** `[tier 4]`, suppressible per-user. Implemented with a **named default fn**,
  not bare `#[serde(default)]` — avoids the existing documented trap at `config.rs:108-110`.
- **Suppression is asymmetric, deliberately**: the full `SessionStart` reflex stays suppressed
  inside phases (`DROVR_PHASE` set), because a phase agent runs on its injected briefing. The
  per-turn gate does **not** suppress in phases — a phase is exactly where the discipline must
  hold.
- `README.md:70-94` updated with the new config key.

with no verification evidence) is enforcement rather than persuasion — a larger design with real
false-positive risk. Not built in this run.

## 6. Decision: Fix 3 — bind checklists to tracked task state

Stated harness-agnostically because harnesses differ (some expose `TaskCreate`/`TaskUpdate`/
`TaskList` and no `TodoWrite`; stable Claude Code exposes `TodoWrite`):

> When a skill or briefing gives you a numbered checklist, create **one tracked item per step**
> using whatever task tool this harness exposes — `TodoWrite`, or `TaskCreate`/`TaskUpdate` —
> before you start step 1. Mark each in-progress when you start it and complete when its evidence
> is in hand. If the harness exposes no task tool, write the checklist to
> `~/.local/share/drovr/runs/<run>/checklist.md` when inside a run, or `CHECKLIST.md` at the repo
> root otherwise, and tick items there. An untracked checklist decays with the context window;
> that decay is the exact failure drovr exists to fight.

**Applied at four sites** (no CLI change required):

1. `skills/using-drovr/SKILL.md` — the gate function's checklist branch (§5.1 item 5).
2. Each discipline skill's numbered procedure gets a one-line binding directive above it.
3. `skills/pipeline/phase-prompts/*.md` — the `## Do` lists (`implement-task.md:14-64`, 7 steps,
   and the equivalents in `brainstorm.md`, `plan.md`, `review.md`, `review-angle.md`) gain the
   directive as step 0. Pure text change (agent-assembled markdown, not compiled).
4. `skills/handoff/SKILL.md` and `skills/handoff/HANDOFF-template.md` — the 7-section handoff is
   a checklist and gets the same treatment.

## 7. Decision: Fix 4 — armor structure for the four discipline skills

`tdd`, `systematic-debugging`, `verification-before-completion`, `code-review` are restructured
to this fixed section order `[tier 3 — superpowers' convention, adopted wholesale]`:

```
   REQUIRED — all four skills
1. description:      trigger, not summary (fix 1)
2. Overview          core principle + spirit-vs-letter line + the WHY, ≤6 lines
3. Unity line        "the next phase agent is you, with your context gone"
4. The Iron Law      one fenced all-caps line + "No exceptions:" bullets closing named loopholes,
                     each bullet pairing the prohibition with the required action
5. Announce          the exact sentence to emit when invoking the skill (commitment device)
6. The procedure     numbered, preceded by the task-binding directive (fix 3)
8. Red flags — STOP  inner-monologue fragments, closed by a catch-all bullet
9. Rationalizations  thought → reality; the reality column is an INSTRUCTION, not a rebuttal
10. Worked example   one ✅/❌ pair of actual utterances. One good example, not five
11. Cross-refs       bare skill names with REQUIRED markers; never @-links (they force-load)

   CONDITIONAL — only where named below
7. Requirements      claim → required evidence → not sufficient
                     ONLY: verification-before-completion, code-review
6b. Cycle flowchart  a fenced dot graph of the loop
                     ONLY: tdd, systematic-debugging
```

**Placement rationale, stated for the reviewer:** sections 2–5 sit at the top per the
position-effects prior (§2.1). Sections 8–9 sit late for proximity to the point of temptation —
`[tier 4]`, not the U-shape finding. Section 6 (the procedure) sits mid-document deliberately: it
is the section the agent actively re-reads while executing, so it is least dependent on
single-pass recall. **The position finding must not be cited for sections 6–9.**

**Announcement sentences** — template `Using drovr:<skill> to <purpose>.`:

- `tdd` — *"Using drovr:tdd — writing the failing test before the implementation."*
- `systematic-debugging` — *"Using drovr:systematic-debugging — reproducing before fixing."*
- `verification-before-completion` — *"Using drovr:verification-before-completion — running the
  checks before claiming done."*
- `code-review` — *"Using drovr:code-review — dispatching read-only reviewers before calling this
  done."*

**Per-skill specifics:**

- **`tdd`** — Iron Law: no implementation code before a test you have watched fail. Loophole
  closures: "I'll keep the code as reference", "the test is obvious so I'll write it after",
  "it's a refactor so TDD doesn't apply", "the harness makes it hard to run one test".
- **`systematic-debugging`** — Iron Law: no fix before a reproduction and a mechanistic cause.
  Adds the numeric escalation trigger: after 3 failed fixes, stop and question the design before
  attempting fix #4.
- **`verification-before-completion`** — Iron Law: no completion claim without fresh evidence
  produced in this message. Requirements table covers tests / build / linter / bug-fixed /
  subagent-reported-success. Catch-all red flag for any wording implying success.
- **`code-review`** — Iron Law: no change is done until a read-only reviewer has looked at it and
  every Critical/Important finding is resolved or explicitly recorded as deferred. Loophole
  closures: "the change is too small", "I already reviewed it myself", "the pipeline's review
  phase will catch it". The existing FOREGROUND rule (`code-review/SKILL.md:19-23`) is promoted
  into the no-exceptions list — backgrounding a reviewer is the known silent-failure mode.

**Expected size**: 39–51 lines today → roughly 120–180 lines each; the binding constraint is the
12000-byte `BODY_BUDGET` (§2.2), not a line count.

## 8. Decision: Fix 5 — `drovr:writing-skills` meta-skill and evidence corpus

### 8.1 New skill: `skills/writing-skills/SKILL.md`

Pass criteria, the four-part closure, and scenario-construction rules are `[tier 3]`,
convention-follows ported from superpowers' `testing-skills-with-subagents.md:182-275` in
drovr's own wording. Convergent with Anthropic's own skill-authoring guidance (eval-first,
baseline-without-the-skill, minimal instructions, iterate), not merely borrowed.

- **The mapping**: pressure scenario ↔ test case; `SKILL.md` ↔ production code; RED ↔ the agent
  violates the rule without the skill; GREEN ↔ it complies with the skill; REFACTOR ↔ close each
  new loophole.
- **The loop** (fenced `dot` flowchart, a stop-too-early loop): build the scenario set → run the
  baseline → transcribe every excuse verbatim → write the minimal counter-text → re-run on
  held-out scenarios → apply the four-part closure to each new rationalization → repeat **until a
  run produces no new rationalization or the §9 REFACTOR ceiling is reached, whichever comes
  first.** The ceiling is not optional — an uncapped loop is the same unbounded-cost defect this
  spec exists to fix.
- **The four-part closure**, all four every time: explicit negation inside the rule; a row in the
  rationalization table; a bullet in red flags; a `description:` update adding the symptom of
  being about to violate.
- **Scenario construction rules**: real file paths, concrete numbers and deadlines, a forced
  A/B/C choice, "what do you do" not "what should you do", no escape hatch to "I'd ask the
  human", ≥3 combined pressure types (time, sunk cost, authority, economic, exhaustion, social,
  pragmatic).
- **Pass criteria**, all four required: correct option under maximum pressure; agent cites a
  specific section; names the temptation and complies anyway; meta-test ("how should this have
  been written?") returns "it was clear." Not-bulletproof signals: new rationalizations, arguing
  the skill is wrong, invented hybrid approaches, asking permission while still arguing for the
  violation.
- **drovr-specific constraints**: scenario subagents run in the FOREGROUND; the author is the
  single writer; the no-fabricated-measurements rule (§2) applies.
- Reference files: `references/pressure-scenarios.md` and `references/testing-with-subagents.md`,
  keeping `SKILL.md` under the §2.2 cap.

### 8.2 Evidence corpus (new files)

- `skills/writing-skills/scenarios/<skill>-<n>.md` — checked-in scenario prompts, each tagged
  `dev` or `holdout` (§9).
- `docs/skill-evidence/<skill>.md` — per skill: scenarios used, verbatim baseline
  rationalizations, the counter-text written for each, and re-test results with dates.
- `docs/skill-evidence/voice.md` — the §10 probe record.
- `docs/skill-evidence/per-turn-gate.md` — §5.2's unmeasured-bet record and the subagent-firing
  answer.
- `docs/skill-evidence/transcripts/` — raw transcripts; the corpus any numeric claim in shipped
  skill text must cite (§2 exception 1).

### 8.3 The acceptance test

Answers: *how do we know stickiness improved rather than that the docs got longer?*

**Held-out design.** Authoring arm B from the scenarios that grade it would fit the text to the
test. Per skill: **3 scenarios — 1 development, 2 held-out.** RED transcription and all
counter-text authoring use the development scenario only. The pass bar is pre-registered and
scored on the held-out pair, never read while writing arm B.

**Arms** (three, so fix 1 and fix 4 are separable):

| Arm | Text |
|---|---|
| **A** | Current `SKILL.md` at the pre-fix `HEAD` (captured per §1 step 2) |
| **A′** | Fix-1-only: descriptions un-scoped, no armor |
| **B** | Full rewrite (fixes 1 + 3 + 4) |

Arm A′ exists because arm A's phase-scoped descriptions are the defect §4 fixes — without A′, a
non-phase-framed scenario handicaps A for reasons unrelated to the armor, and B > A would prove
nothing about fix 4 specifically. A′ isolates the armor's own contribution.

**Budget table** — every stage has a hard ceiling; hitting one **halts the stage and records a
null** in `docs/skill-evidence/`, never a silent extension:

| Stage | Scope | Runs | Ceiling |
|---|---|---|---|
| RED / baseline on dev set | 5 skills × 1 dev scenario × 2 samples | 10 | 10 |
| Arm A on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| Arm A′ on held-out | 4 discipline skills × 2 × 2 | 16 | 16 |
| Arm B on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| REFACTOR re-tests | failing skills only, ≤2 iterations each | ≤20 | 20 |
| Voice probe (§10) | 4 variants × 2 scenarios × 3 samples | 24 | 24 |
| `using-drovr` no-skill-applies class | 2 scenarios × 3 arms × 2 samples | 12 | 12 |
| **Total** | | **≈122** | **122 hard ceiling** |

`using-drovr`'s extra scenario class checks the router's own failure mode (invoking nothing)
without inducing the opposite failure (invoking everything reflexively); it is budgeted, not
free.

**Decomposition.** 122 foreground subagent runs with verbatim transcription do not fit one
`implement-task` context — the exact failure this spec targets. Decision: **one dedicated phase
per skill**, `ab-<skill>` (5 phases), each running its own stages and writing
`docs/skill-evidence/<skill>.md` plus raw transcripts, then exiting; the voice probe is a sixth
phase, `ab-voice`. The driver aggregates results. No phase holds more than ~25 runs.

**Scoring, pre-registered, not run by arm B's author:**

- **Rubric**: binary compliant/non-compliant on the scenario's forced choice, plus the four §8.1
  pass criteria recorded separately as booleans.
- **Scorer**: a read-only reviewer subagent, given only the transcript and the rubric.
- **Blinding**: arm labels stripped and transcripts shuffled before scoring; the mapping is
  restored only after all scores are recorded.
- **Model**: `sonnet` for both probe subagents and the scorer.

**Pre-registered bars:**

- **Arm A bar**: a skill "already passes" if A is compliant on **≥3 of its 4 held-out runs.**
- **Arm B bar**: compliant on **≥3 of its 4 held-out runs**, AND strictly more compliant runs
  than both A and A′.
- **Consequence of failure.** A skill whose B fails after its REFACTOR ceiling **does not ship
  its armor**: it reverts to arm A′ (fix-1-only), and `docs/skill-evidence/<skill>.md` records
  the failure and the reverted state. Fix 1 ships regardless (it is a defect repair); fix 4 must
  earn its bytes.
- **Falsifiable**: if arm A already passes for a skill, that skill's rewrite is not justified and
  reverts to A′.
- If A′ ≈ B for a skill, the armor is not carrying weight there and that skill reverts to A′ even
  if B independently clears its own bar.

Null and negative results are recorded alongside positive ones — not omitted.

## 9. Decision: voice as a measured variable

Three register questions (authority, unity, moral framing) have no published procedural-adherence
study and are all reachable as text variants of one probe skill — `[tier 2]` per §2.

**Probe skill: `verification-before-completion`** — sharpest binary outcome (claimed done without
running the command), shortest scenarios. **Model: `sonnet`**, matching §8 — stated limitation:
this is not the Opus-class model drovr sessions actually run on, alongside the §2.1
Haiku/mini/Flash → Sonnet/Opus extrapolation.

**Four variants**, identical structure (same Iron Law, procedure, tables, placement), each adding
exactly one register device to the baseline so factors stay separable at this sample size:

| Variant | Register |
|---|---|
| **V0** | Baseline: plain imperative; no all-caps, no absolutist "no exceptions"; operational consequence only |
| **V1** | V0 + unity line |
| **V2** | V0 + full authority register (`MUST`/`NEVER`, all-caps Iron Law, no-exceptions bullets) |
| **V3** | V0 + moral framing, in superpowers' register |

4 variants × 2 scenarios × 3 samples = 24 runs, 6 per variant.

**Pre-registered decision rule** — each variant vs. V0 on 6 runs per side; separation margin
**≥3 of 6** (set to match the stated power; a 2-of-12 margin on binary outcomes is roughly one
standard deviation and would fire on noise):

1. Variant beats V0 by ≥3 → that device ships across all five documents.
2. V0 beats the variant by ≥3 → that device is **dropped**, baseline register ships. (Explicit
   branch: a plain-register win is a real, valid outcome.)
3. No separation ≥3 (the likeliest outcome) → **tier 3: follow superpowers.** Authority ships,
   moral framing ships, and unity ships anyway on the strength of the 2026 published ranking
   (tier 1 outranks tier 3) even though superpowers itself withholds unity from discipline
   skills. Each recorded in `docs/skill-evidence/voice.md` as convention-or-prior, with the null
   attached.
4. Whatever wins applies to the other four documents without re-testing each. Stated limitation:
   measured on one skill, one model, generalized to five documents.

**Unity's arm is reported, not decisive** — 6 runs cannot overturn the N=126,000 published
result; the arm can only show a large local effect if one exists. **No directional escape
hatch**: if V1 loses to V0 by ≥3, that is recorded as a genuine conflict between the published
prior and drovr's own data, and **escalates to the human** rather than auto-resolving.

**Power note**: n=6 per variant detects only large effects, and register effects are expected to
be small on frontier models, so outcome 3 is the single likeliest result — informative, not a
failure. Nothing stronger than "suggestive" is recorded from this probe.
