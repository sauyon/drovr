# Spec: TUI deploy-config picker — browse any config in the project

## Problem

The deployment browser's `V` key is labelled "switch deploy config" but can only switch
**versions of the config the deployment is already linked to**, because of two independent
gates: the fetch in `browse_deploy_config.go:76` is pinned to the linked config's name, and
`browse_model.go:1910` rejects opening the picker at all when `m.sel.DeployConfigID == nil`.
Every other config in the project — including shared configs, which are how fleet-wide config
is distributed — is unreachable from `V`.

No API or server change is required: `deployConfigService.List` with no name filter
(`api-server/services/deploy_config.go:194-201`) already returns the latest version of every
config in the project, including shared configs (ordinary rows materialised by
`reconcileShared`), and the typed client (`api.Client.ListDeployConfigs`) already exists.

## Decisions

### D1 — Picker shape: three-level tree, not sequential prompts

`V` opens a single browsable, collapsible tree — benchmark project → config → version — built
on the browser's existing `fieldTree` widget (`browse_fieldtree.go:151`), reusing its
`up`/`down`/`toggle`/`setCollapsed`/`reflatten`/`render`. This was decided in two passes: turn 1
fixed the three levels (Q1), turn 2 replaced the originally-assumed sequential `huh.Select`
steps with one navigable tree (Q5), because browsing sideways — comparing configs without
backing out — is the point of the feature, and a stepped picker makes that awkward. Cross-project
adoption falls out of the project level being a tree root.

Cost accepted: `fieldTree` has no type-to-filter (the `huh.Select` steps had
`.Filtering(true)`). Out of scope here; tracked as a follow-up on the widget itself.

### D2 — Lazy, cached, per-level loading

Expanding a branch triggers its fetch; a branch caches its children after first load, so
re-collapsing/re-expanding does not refetch.

| Level | Loaded when | Call |
|---|---|---|
| projects | picker opens | `ListBenchmarkProjects` |
| configs of a project | that project first expanded | `ListDeployConfigs(project)` + `latestPerConfig` |
| versions of a config | that config first expanded | `fetchDeployConfigVersions(project, name)` |

An unexpanded branch renders a placeholder child (`loading…`, replaced on arrival; `(none)` if
empty) so it shows as expandable before its contents are known.

### D3 — Auto-expand on open (Q2)

- Linked deployment: auto-expand its project and its config; cursor starts on the current
  version.
- Unlinked deployment: auto-expand the sole project when the org has exactly one; otherwise
  leave all projects collapsed, cursor on the first. This applies even to linked deployments —
  the project auto-expand is unconditional, only the *choice* of which project depends on the
  link.

The linked-deployment path issues the same three requests (projects, its project's configs, its
config's versions) that a stepped picker would have made, so the common case costs no more than
today.

### D4 — Selection carried on the node, not on a bare key

`fieldNode` (`browse_fieldtree.go:139-146`) gains one optional field: `pick any`, non-nil only
on version leaves, holding the `*schemasv1.DeployConfigSchema` for that version. `enter` reads
`pick` back off the cursor node. Branch nodes (project, config) leave `pick` nil — that nilness
*is* "a branch is never a selection"; no separate node-kind enum is added. This removes the
`Select[uint]` collision a version-number-keyed design would have, since nothing is keyed on a
bare version number.

A `current() *fieldNode` accessor is added to `fieldTree` so the picker doesn't reach into its
unexported `flat`/`cursor` fields.

### D5 — Entry gate removed

`browse_model.go:1910-1917` drops the `DeployConfigID == nil` rejection; `V` is valid on any
detail-screen selection. `helpAdapter.dcLinked` (`browse_model.go:2916`) loses its
`DeployConfigID != nil` condition so the key is advertised on unlinked deployments too.

### D6 — Unlinked deployment adopting a config: two-way deep merge, not verbatim (Q3)

Today, `switchDeployConfigAction` passes `m.deployCfg` as baseline into
`preserveDeploymentDivergences`; when unlinked that baseline is `nil` and the function returns
the target **verbatim**, silently discarding every field the deployment has (e.g. a pinned
`engine_spec.image`) — the exact incident class `preserveDeploymentDivergences` exists to
prevent (commit `e351fdd69`).

**Decision:** when the linked baseline is absent, `preserveDeploymentDivergences` must instead
perform a two-way deep merge — target config as base, deployment's current configuration as
overlay, overlay wins on conflicting leaves, target-only keys still land. This matches the
edit form's existing behavior (`completeConfigPick` falling back to
`overridesFromConfiguration(prior)`) and the documented semantics of `mergeJSONPtr` ("deep-merge
overlay onto base: new deploy-config fields are kept, deployment-specific overrides win on
conflict").

**Implementation constraint:** do not reuse `threeWayMerge` with an empty-map baseline — its
"value only current has" branch takes `curVal` wholesale for any key absent from the baseline,
so nested keys the target contributes would be dropped and top-level deployment keys would
replace the target's wholesale. Implement a distinct, recursing map-level helper (the map twin
of `mergeJSONPtr`).

This change to `preserveDeploymentDivergences` also fixes the same gap on the existing
`mcloud deployment deploy-config set` CLI path, which shares the function.

### D7 — Cross-config-name switch: keep the three-way merge (Q4)

When switching to a different config name (or a different project), the existing three-way
merge against the previously-linked baseline is kept as-is, even though that baseline has no
relationship to the target: a pinned image surviving the switch matters more in practice than
merge purity, and applying the target verbatim on a name change would reopen the same unpinning
hazard D6 closes. Confirm copy must state that overrides are carried across. This applies
identically to cross-project switches — the baseline is wherever the deployment was linked to.

### D8 — Confirm copy

`actionSwitchDeployConfig`'s confirm states, one line each: that switching redeploys the
deployment (unchanged); that overrides are carried across (D6/D7); and, when the chosen config
is `shared`, that the config's *latest* will move under future `mcloud deploy-config apply`
runs while this deployment stays pinned to the version selected here (versions are immutable
rows).

### D9 — Labelling

- Project node: `"<name>"`.
- Config node: `"<name>  (latest v<N>)"`, plus `"  (shared)"` when `Shared` is true, plus
  `"  (current)"` when it is the linked config.
- Version leaf: `"v<N>  <created>  <description>"` (reusing the label logic already in
  `newDeployConfigVersionPicker`, `browse_source_config.go:361-362`), plus `"  (latest)"` on the
  newest and `"  (current)"` on the deployment's current version.
- Panel label (`browse_panels.go:226-228`): `"V: switch version"` → `"V: switch deploy config"`.
- Key help (`browse_model.go:200`) already reads `"switch deploy config"`; no change needed
  there, it becomes accurate as a side effect.

`Shared` (`schemasv1.DeployConfigSchema:16`) is already returned by the list endpoint but
currently unused anywhere in the CLI/TUI; this is its first use.

## Interfaces / contracts

### New `appModel` state (`browse_model.go`, replacing the existing `dc*` block)

```go
dcTree    *fieldTree                     // the picker; non-nil exactly while it is open
dcLinked  *schemasv1.DeployConfigSchema  // linked config, if any: drives auto-expand,
                                         // cursor placement, and is the merge baseline
dcLoading map[string]bool                // in-flight branch loads, keyed "" (projects) /
                                         // "<project>" / "<project>\x00<config>"
```

`dcForm`, `dcVersions`, `dcCurrent`, `dcChoice` are removed (replaced by the tree).
`dcVersLoading` is removed (replaced by `len(dcLoading) > 0`).

### New messages

```go
type dcProjectsMsg struct { name string; items []*schemasv1.BenchmarkProjectSchema; err error }
type dcConfigsMsg  struct { name, project string; items []*schemasv1.DeployConfigSchema; err error }
type dcVersionsMsg struct { name, project, config string; items []*schemasv1.DeployConfigSchema; err error }
```

`name` is the deployment name on all three, preserving the existing stale-result drop
(`msg.name != m.sel.Name`). `project`/`config` identify which branch a result fills, so a result
arriving after the user collapsed that branch lands on the right node without moving the cursor.
`dcVersionsMsg` drops the `current uint` field from the old design — current version is read
from `dcLinked`.

### Overlay routing

`currentOverlay()` (`browse_model.go:880`) keeps a single arm: `case m.dcTree != nil:` returning
`overlayHandler{m.updateDCPicker, m.dcPickerView}`.

`autoRefreshPaused()`: the `m.dcVersLoading` arm is replaced by `m.dcTree != nil`, so auto-refresh
cannot swap `m.sel` while the picker is open — including while it's open and idle between branch
loads (a gap the old in-flight-only flag had).

### Transport — unchanged

`switchDeployConfigVersion` (`deploy_config.go:406`) already takes `(project, name, version)` via
`confirmState` (`dcProject`, `dcName`, `dcVersion`) and already sends `deploy_config_id` + full
`configuration`. `completeDCSelection` is changed to populate `dcProject`/`dcName` from the
chosen leaf's project/config rather than from the linked config — no transport or schema change.

## Scope boundaries

**In scope**
- `V` reaches every deploy config in the project, shared included, on both linked and unlinked
  deployments.
- Cross-project adoption via the tree's project level.
- `preserveDeploymentDivergences` nil-baseline fix (D6) — also fixes the same gap in
  `mcloud deployment deploy-config set`, which shares the function.
- `fieldNode.pick` + `fieldTree.current()`.
- `(shared)` / `(current)` / `(latest)` labelling; confirm copy per D8.
- Panel label fix.
- Tests: table-driven model tests in `browse_deploy_config_test.go` covering picker open/gate,
  branch fill, labelling, auto-expand, cross-project selection, branch-toggle-is-not-a-selection,
  fetch caching, esc-cancel, stale-result drop, overlay routing, and `pick` nilness on
  non-picker trees; table-driven pure-function tests in `deploy_config_test.go` covering the
  nil-baseline merge (recovers a pin, recurses into nested keys) and confirming non-nil-baseline
  (three-way) behavior is unchanged. Plus `mise run go:lint`.

**Out of scope**
- Any API-server or schema change — the existing unfiltered `List` and typed client already
  cover this.
- Type-to-filter in the picker. `fieldTree` has no equivalent to the old `huh.Select`
  `.Filtering(true)`; browsing is cursor-only. Follow-up: add filtering to `fieldTree` itself
  (shared widget, benefits other panels, own blast radius).
- Converting `browse_source_config.go`'s create/edit source picker, or `browse_form_sync.go`'s
  sync picker, to this tree. They keep their `huh.Select` steps; only `V` changes. Follow-up:
  revisit once `fieldTree` has filtering.
- A warning that editing a shared config gets reverted: moot, because the TUI/CLI have no
  deploy-config write path at all (reads only, via `internal/mcloudcli/api/deploy_config.go`;
  the only write is `mcloud deploy-config apply`, the shared-apply POST itself). The adjacent,
  in-scope concern — that linking to a shared config means its *latest* will move under you — is
  covered by the D8 confirm copy, not a separate warning.
- Refactoring `browse_source_config.go` and the new `V` flow into one generic picker: they differ
  in presentation, terminal action (reseed a form vs. arm a confirm + PATCH), and entry
  conditions. Shared data helpers (`latestPerConfig`, `findDeployConfigVersion`,
  `fetchDeployConfigVersions`) are reused as-is, not refactored.
