# Spec: skill stickiness

Make drovr's skill docs *bind* under context pressure instead of merely describing correct
practice. Five fixes, one new meta-skill, and an empirical acceptance test.

---

## 0. Order of work

Section numbers are not the build order. Fix 5 produces the wording fixes 2 and 4 depend on, and
arm A must be captured before fix 1 overwrites it.

1. **`drovr:writing-skills` + the scenario corpus** (§6.1, §6.2). Nothing else can be tested until
   the harness exists.
2. **Capture arm A / RED per skill** (§6.3) — at the pre-fix `HEAD`, before any skill file is
   touched. Hard gate: once fix 1 lands, arm A is unrecoverable without a checkout.
3. **Fixes 1 + 3** (§2, §4) — descriptions, phase-framing demotions, task-binding directives.
4. **Fix 4** (§5), using the RED wording from step 2 for the rationalization tables.
5. **Held-out arm B + the voice probe** (§6.3, §6.4).
6. **Fix 2's hook layer** (§3.2) — the only Rust work; independently orderable, no dependency on
   steps 1–5. Fix 2's doc layer (§3.1) belongs with step 4.

---

## 1. Scope of the problem this spec fixes

drovr's four discipline skills (`tdd`, `systematic-debugging`, `verification-before-completion`,
`code-review`) scope themselves to drovr phases in their `description:` and body text, while
`using-drovr` makes inline work the default mode — so the trigger text tells an agent working
inline that the skill does not apply to what it's doing. The compliance devices that make
superpowers' equivalent skills bind (Iron Laws, rationalization tables, loophole closures,
announcement strings, checklist→task binding) are absent from drovr's. Checklists bind to nothing
durable (no `TodoWrite`/`TaskCreate` usage in any skill). drovr's enforcement language skews
toward mechanics over discipline, and the discipline skills run 39–51 lines against superpowers'
139–371. The reflex hook (`SessionStart`) fires once per session and no-ops inside phases; nothing
re-asserts discipline after turn one.

**Root cause**: superpowers has `writing-skills`, a meta-skill that applies TDD to skill authoring
itself — RED (run a pressure scenario against a subagent without the skill, transcribe its
rationalizations verbatim), GREEN (write the minimal counter-text), REFACTOR (close each new
loophole, re-run). drovr has no such loop; its skills were written by describing correct practice
rather than by testing what an agent rationalizes past. Fixes 1–4 without fix 5 are assertions;
fix 5 makes them evidence.

## 2. Decision: authoring precedence and honesty rules

**Four-tier precedence governs every stylistic/design choice in this spec**, applied in order:

1. Published evidence exists → the evidence decides, citation kept in the text.
2. No published evidence, but the question is reachable by this run's probe loop (expressible as a
   text variant of an existing probe skill, scorable by the existing rubric, within the §6.3
   budget) → measure it (§6.4). Cost may discharge a tier-2 obligation only when measurement would
   exceed the ceiling — never because it seems not worth it.
3. Not reachable, or measurement inconclusive, and superpowers has a convention → follow
   superpowers, marked explicitly as a convention-follow, not evidence-backed.
4. No superpowers analogue at all → engineering judgement, marked **[tier 4]**. Applies to: the
   gate's byte budget, the card length, the `per_turn` default, the reflex-marker boundary, the
   probe's model choice, the §2.4-equivalent length caps below. None of these may be defended as
   though a convention or study backed them.

**Two standing rules, non-negotiable regardless of tier:**

1. **No fabricated measurements.** drovr states a number, duration, frequency, or comparative only
   if drovr measured it or a citation supports it. Rhetorical emphasis is fine; a false measurement
   claim is not.
2. **No copied text.** Both projects are MIT; drovr still writes its own sentences — mechanisms are
   ported, expression is drovr's. Any verbatim line found in review gets the MIT notice and credit
   added.

### 2.1 Voice decisions (bound by measurement, §6.4)

- **Authority register** (`MUST`/`NEVER`/imperative second person) and **moral framing**: both
  **tier 2**, decided empirically in §6.4, with superpowers' full register as tier-3 fallback if
  the measurement is inconclusive.
- **Unity** (*"the next phase agent is you, with your context gone"*) is adopted on the 2026
  replication's published ranking (unity top-two, above authority) and is also measured in §6.4 as
  a reported-not-decisive arm — 6 runs cannot overturn an N=126,000 result, so a loss in the local
  arm is escalated to the human, not auto-resolved.
- **Commitment devices** (announcement string, checklist→tracked-task binding) are adopted
  unconditionally as primary, without a local measurement arm: commitment ranks top-two in both
  published studies, and these are the cheapest, best-evidenced devices available.
- **Social proof** is adopted only in its true form (naming a failure mode actually observed in
  `docs/skill-evidence/`), never as an invented frequency claim.
- **Flowcharts** (fenced `dot` blocks): adopted **[tier 3]**, not measured — the variant changes
  document structure rather than a text register, so it can't share the probe's rubric. Used only
  for genuine branching or stop-too-early loops, never linear instructions: the `using-drovr`
  router (§3.1), the RED/GREEN/REFACTOR loop (§6.1), `drovr:tdd`'s red-green-refactor cycle, and
  `systematic-debugging`'s loop. All other discipline procedures stay numbered lists.
- **Review-UI rendering of `dot` blocks, and pairing a graph with the plan as a progress display**,
  is a product judgement **[tier 4]** for a human audience, not a measured decision — and it is
  **out of scope** for this run (§7). Recorded as a follow-up in `docs/known-issues.md` under a
  `## Resolved`-adjacent entry: *render fenced `dot` blocks in the review UI and show the
  phase/gate graph alongside the plan.*

### 2.2 Length decisions

> **The byte budget applies to teaching content. Binding content is deliberately redundant** —
> stated 3–4 times per skill (Iron Law, red flag, rationalization row, checklist item).

- **`cli/tests/skills_valid.rs`'s `BODY_BUDGET` is the single authoritative size check** for the
  four methodology skills. `wc -l`/`wc -w` are author guidance only, never asserted as a
  verification criterion.
- **`BODY_BUDGET` rises 2200 → 12000 bytes** for the four methodology skills **[tier 4 — no
  superpowers analogue, no evidence sets a correct length]**.
- **`using-drovr` gets its own cap: 9000 bytes**, and joins the checked list (currently exempt by
  accident of history; it is the most expensive document in the repo, injected in full on every
  `SessionStart`).
- Content above cap moves to `references/`.
- Expected discipline-skill size after fix 4: 39–51 lines → roughly 120–180 lines each; the binding
  constraint is the 12000-byte budget, not a line count.
- The user's global reply-terseness preference does not apply to skill docs — a skill doc's job is
  to survive a filling context window, not to read like a terse reply.

## 4. Fix 2 — make `using-drovr` a per-turn gate

### 4.1 Doc layer (`skills/using-drovr/SKILL.md`)

New content, in this order (position-effects rationale: start/end of a document retrieve best, so
binding content top-loads). Items 2 and 4 are **[tier 3]** convention-follows, ported from
`using-superpowers/SKILL.md:11-29` in drovr's own wording:

1. `<SUBAGENT-STOP>` — keep, `:8-11`.
2. **The 1% rule** — above the H1, inside the existing `<EXTREMELY_IMPORTANT>` framing: even a 1%
   chance a drovr skill applies means invoke it, paired with a cost-lowering clause (if it turns
   out not to fit, drop it — invoking costs almost nothing).
3. **The per-turn rule** — check before any response, including before a clarifying question and
   before read-only exploration.
4. **Instruction-priority ladder** — human's explicit instructions > drovr skills > default
   behaviour. Safety counterweight to the MUST language; not optional.
5. **Gate function** — fenced `dot` flowchart: message received → does any skill apply (≥1%) →
   invoke → announce → does it have a checklist → create one tracked item per step → follow it →
   only then respond.
6. **Red-flag table for the router's own failure mode** (invoking nothing at all — currently zero
   coverage). Candidate rows: *"this is a one-line change"*, *"I'll just look at the file first"*,
   *"they asked a question, not for work"*, *"I'm already mid-task, the router was for turn one"*,
   *"escalating to a phase would be overkill so no skill applies"*. Final wording comes from RED
   (§6), not this list.
7. Existing sections (single-writer, always-review, methodology, escalation) retained.

**Items 2–5 sit outside every `<!-- reflex:section:NAME -->` marker** **[tier 4 — no sectioned-
reflex analogue in superpowers]**. `[reflex.sections]` can subtract advisory sections but cannot
silently delete the routing core; only `[reflex] enabled = false` removes it — a half-disabled
router must not produce an agent that believes it's running drovr and isn't.

### 4.2 Hook layer (new `UserPromptSubmit` hook)

Every decision here is **[tier 4]** — superpowers is `SessionStart`-only, so there's no convention,
and no study covers per-turn re-injection. It ships as an explicit unmeasured bet, recorded in
`docs/skill-evidence/per-turn-gate.md`.

- `hooks/hooks.json` gains a `UserPromptSubmit` entry running a thin `hooks/user-prompt` script
  that `exec`s `drovr reflex --gate`. **`UserPromptSubmit` takes no `matcher`** — the existing
  `SessionStart` entry's `startup|clear|compact` matcher must not be copied across.
- **Budget: ≤600 bytes per injection, cumulative ceiling ~60 KB over a 100-turn session.**
  `additionalContext` is appended every turn and stays in the window, so cost is cumulative, not a
  rate.
- **Suppression rule** (bounds the cumulative cost): the card is emitted only when no `drovr:*`
  skill was invoked in the previous turn.
- **Byte budget, not tokens** — the CLI has no tokenizer. Assertion: rendered `additionalContext` ≤
  600 bytes, checked in `cli/src/reflex.rs`'s test module.
- **Card content**: the 1% rule, the per-turn check, the announcement string, the
  checklist-binding line, a `<SUBAGENT-STOP>` line, and a pointer to `Skill drovr:using-drovr`.
- **Card text source: a `const` in `reflex.rs`, not extraction from `SKILL.md`** — extraction would
  need markers inside the region §4.1 places outside all `reflex:section` markers. Drift risk is
  mitigated by a test asserting the card's key phrases appear in `using-drovr/SKILL.md`.
- **Three required API changes** (verified against source):
  1. `reflex.rs:143-152`'s `envelope()` hardcodes `"hookEventName": "SessionStart"` — parameterize
     to take the event name.
  2. `main.rs:114-118` declares `Reflex { skill: PathBuf }` as required, and `main.rs:1276-1278`
     asserts bare `drovr reflex` errors. `--gate` forces `Option<PathBuf>`, a clap arg-group rule
     (`--gate` xor `--skill`), and an update to that test.
  3. Card text ships as the `reflex.rs` `const` described above.
- **Subagents**: the card carries its own unconditional subagent-stop line, because §6.3/§6.4's
  foreground probe subagents and drovr's own read-only reviewers all launch from a gate-on session
  and must not have the card injected. Step 1 of §0 verifies empirically whether the hook fires for
  Agent-tool subagents in this harness, and the answer is recorded in
  `docs/skill-evidence/per-turn-gate.md`.
- **Config**: new `[reflex] per_turn` bool in `ReflexConfig` (`cli/src/config.rs:39-64`), **default
  true** **[tier 4]**, suppressible per-user. Uses a named default fn, not bare
  `#[serde(default)]` (the trap documented at `config.rs:108-110`).
- **Asymmetric suppression, deliberate**: the full `SessionStart` reflex stays suppressed inside
  phases (`DROVR_PHASE` set) — a phase agent runs on its injected briefing. The per-turn gate does
  **not** suppress in phases — a phase is exactly where the discipline must hold.
- `README.md:70-94` updated with the new key.

### 4.3 Out of scope

`PreToolUse` hard-denial of an `Edit` that skipped `drovr:tdd`, or a `git commit` with no
verification evidence — enforcement rather than persuasion, a larger design with real
false-positive risk. Not this run.

## 5. Fix 3 — bind checklists to tracked task state

Stated harness-agnostically (some sessions expose `TaskCreate`/`TaskUpdate`/`TaskList` and no
`TodoWrite`; stable Claude Code exposes `TodoWrite`):

> When a skill or briefing gives you a numbered checklist, create **one tracked item per step**
> using whatever task tool this harness exposes — `TodoWrite`, or `TaskCreate`/`TaskUpdate` —
> before you start step 1. Mark each in-progress when you start it and complete when its evidence
> is in hand. If the harness exposes no task tool, write the checklist to
> `~/.local/share/drovr/runs/<run>/checklist.md` when inside a run, or `CHECKLIST.md` at the repo

Applied at four sites, no CLI change required:

2. Each discipline skill's numbered procedure — a one-line binding directive above it.
3. `skills/pipeline/phase-prompts/*.md` — the `## Do` lists (`implement-task.md:14-64`, 7 steps;
   and the equivalents in `brainstorm.md`, `plan.md`, `review.md`, `review-angle.md`) gain the

   the binary.
4. `skills/handoff/SKILL.md` and `skills/handoff/HANDOFF-template.md` — the 7-section handoff gets
   the same treatment.

## 6. Fix 4 — move the armor onto the discipline skills

`tdd`, `systematic-debugging`, `verification-before-completion` and `code-review` restructure to a
fixed section order **[tier 3 — superpowers' convention, adopted wholesale]**:

```
   REQUIRED — all four skills
1. description:      trigger, not summary (fix 1)
2. Overview          core principle + spirit-vs-letter line + the WHY, ≤6 lines
3. Unity line        "the next phase agent is you, with your context gone"
4. The Iron Law      one fenced all-caps line + "No exceptions:" bullets closing named loopholes,
                     each bullet pairing the prohibition with the required action
5. Announce          the exact sentence to emit when invoking the skill (commitment device)
6. The procedure     numbered, preceded by the task-binding directive (fix 3)
8. Red flags — STOP  inner-monologue fragments, closed by a catch-all bullet
9. Rationalizations  thought → reality; the reality column is an INSTRUCTION, not a rebuttal
10. Worked example   one ✅/❌ pair of actual utterances. One good example, not five
11. Cross-refs       bare skill names with REQUIRED markers; never @-links (they force-load)

   CONDITIONAL — only where named below
7. Requirements      claim → required evidence → not sufficient
                     ONLY: verification-before-completion, code-review
6b. Cycle flowchart  a fenced dot graph of the loop
                     ONLY: tdd, systematic-debugging
```

**Announcement sentences** — template `Using drovr:<skill> to <purpose>.`:

- `tdd` — *"Using drovr:tdd — writing the failing test before the implementation."*
- `systematic-debugging` — *"Using drovr:systematic-debugging — reproducing before fixing."*
- `verification-before-completion` — *"Using drovr:verification-before-completion — running the
  checks before claiming done."*
- `code-review` — *"Using drovr:code-review — dispatching read-only reviewers before calling this
  done."*

**Placement**: sections 2–5 sit at the top (position-effects rationale, §2). Sections 8–9 sit late
for a different reason — proximity to the point of temptation, a **[tier 4]** judgement, not the
position finding. The procedure (6) sits mid-document deliberately: it's the section the agent
actively re-reads while working, so it's least dependent on single-pass recall.

**Per-skill specifics:**

- **`tdd`** — Iron Law: no implementation code before a test you have watched fail. Loophole
  closures: "I'll keep the code as reference", "the test is obvious so I'll write it after", "it's
  a refactor so TDD doesn't apply", "the harness makes it hard to run one test".
- **`systematic-debugging`** — Iron Law: no fix before a reproduction and a mechanistic cause.
  Adds a numeric escalation trigger: after 3 failed fixes, stop and question the design — no
  fix #4 without that conversation.
- **`verification-before-completion`** — Iron Law: no completion claim without fresh evidence
  produced in this message. Requirements table covers tests / build / linter / bug-fixed /
  subagent-reported-success. Catch-all red flag for any wording implying success.
- **`code-review`** — Iron Law: no change is done until a read-only reviewer has looked at it and
  every Critical/Important finding is resolved or explicitly recorded as deferred. Loophole
  closures: "the change is too small", "I already reviewed it myself", "the pipeline's review phase
  will catch it". The existing FOREGROUND rule (`code-review/SKILL.md:19-23`) is promoted into the
  no-exceptions list.

Expected size: 39–51 lines → roughly 120–180 lines each; binding constraint is the 12000-byte
`BODY_BUDGET` (§2.2), not line count.

## 7. Fix 5 — the meta-skill and the empirical loop

### 7.1 New skill: `drovr:writing-skills`

`skills/writing-skills/SKILL.md`, in drovr's own voice. Pass criteria, four-part closure, and
scenario-construction rules below are **[tier 3]** convention-follows ported from
`testing-skills-with-subagents.md:182-275`.

- **Mapping**: pressure scenario ↔ test case; `SKILL.md` ↔ production code; RED ↔ agent violates
  the rule without the skill; GREEN ↔ complies with the skill; REFACTOR ↔ close each new loophole.
- **Loop** (fenced `dot` flowchart): build the scenario set → run the baseline → transcribe every
  excuse verbatim → write the minimal counter-text → re-run on held-out scenarios → apply the
  four-part closure to each new rationalization → repeat until a run produces no new
  rationalization **or the §7.3 REFACTOR ceiling is reached, whichever comes first.**
- **Four-part closure** (all four every time): explicit negation inside the rule; a row in the
  rationalization table; a bullet in red flags; a `description:` update adding the symptom of being
  about to violate.
- **Scenario construction rules**: real file paths, concrete numbers and deadlines, a forced
  A/B/C choice, "what do you do" not "what should you do", no escape hatch to "I'd ask the human",
  and ≥3 combined pressure types (time, sunk cost, authority, economic, exhaustion, social,
  pragmatic).
- **Pass criteria** (all four): correct option under maximum pressure; agent cites a specific
  section; names the temptation and complies anyway; meta-test ("how should this have been
  written?") returns "it was clear". Not-bulletproof signals: new rationalizations, arguing the
  skill is wrong, invented hybrid approaches, asking permission while arguing for the violation.
- **drovr-specific constraints**: scenario subagents run in the FOREGROUND; the author is the
  single writer; §2's no-fabricated-measurements rule applies.
- Reference files: `references/pressure-scenarios.md`, `references/testing-with-subagents.md`,
  keeping `SKILL.md` under the §2.2 cap.

### 7.2 Evidence corpus

- `skills/writing-skills/scenarios/<skill>-<n>.md` — checked-in scenario prompts, tagged `dev` or
  `holdout` (§7.3).
- `docs/skill-evidence/<skill>.md` — per skill: scenarios used, verbatim baseline rationalizations,
  the counter-text, re-test results with dates.
- `docs/skill-evidence/voice.md` — the §7.4 probe record.
- `docs/skill-evidence/per-turn-gate.md` — §4.2's unmeasured-bet record and the subagent-firing
  answer.
- Raw transcripts under `docs/skill-evidence/transcripts/` — the corpus any numeric claim in
  shipped skill text must cite (§2 exception 1).

### 7.3 The acceptance test — runs in this run

**Held-out design**: per skill, 3 scenarios — 1 development, 2 held-out. RED transcription and
counter-text authoring use the development scenario only. The pass bar is scored on the held-out
pair, never read while writing arm B (authoring arm B from the grading scenarios would fit the text
to the test).

**Arms** (three, so fix 1 and fix 4 are separable):

| Arm | Text |
|---|---|
| **A** | Current `SKILL.md` at the pre-fix `HEAD` (captured in §0 step 2) |
| **A′** | Fix-1-only: descriptions un-scoped, no armor |
| **B** | Full rewrite (fixes 1 + 3 + 4) |

A′ isolates the armor's contribution — without it, a non-phase-framed scenario would handicap A for
reasons unrelated to the armor, and B > A would prove nothing about fix 4.

**Budget table** — every line has a hard ceiling; hitting one halts and records a null in
`docs/skill-evidence/`, never a silent extension:

| Stage | Scope | Runs | Ceiling |
|---|---|---|---|
| RED / baseline on dev set | 5 skills × 1 dev scenario × 2 samples | 10 | 10 |
| Arm A on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| Arm A′ on held-out | 4 discipline skills × 2 × 2 | 16 | 16 |
| Arm B on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| REFACTOR re-tests | failing skills only, ≤2 iterations each | ≤20 | 20 |
| Voice probe (§7.4) | 4 variants × 2 scenarios × 3 samples | 24 | 24 |
| `using-drovr` no-skill-applies class | 2 scenarios × 3 arms × 2 samples | 12 | 12 |
| **Total** | | **≈122** | **122 hard ceiling** |

`using-drovr`'s extra scenario class checks the router's own failure mode (invoking nothing) without
inducing the opposite failure (invoking everything reflexively); it is budgeted, not free.

**Execution decomposition**: 122 foreground subagent runs with verbatim transcription do not fit
one implement-task context. One dedicated phase per skill, `ab-<skill>` (5 phases), each running
its own stages and writing `docs/skill-evidence/<skill>.md` plus raw transcripts; a sixth phase,
`ab-voice`, runs the voice probe. The driver aggregates. No phase holds more than ~25 runs.

**Scoring** (pre-registered, not by arm B's author):

- **Rubric**: binary compliant/non-compliant on the scenario's forced choice, plus the four §7.1
  pass criteria recorded separately as booleans.
- **Scorer**: a read-only reviewer subagent, given the transcript and rubric only.
- **Blinding**: arm labels stripped, transcripts shuffled before scoring; mapping restored only
  after all scores are recorded.
- **Model**: `sonnet` for probe subagents and the scorer.

**Pre-registered bars:**

- **Arm A bar**: a skill "already passes" if A is compliant on ≥3 of its 4 held-out runs (2
  held-out scenarios × 2 samples).
- **Arm B bar**: compliant on ≥3 of its 4 held-out runs, AND strictly more compliant runs than both
  A and A′.
- **Consequence of B failing after its REFACTOR ceiling**: the skill does not ship its armor —
  reverts to arm A′ (fix-1-only), and `docs/skill-evidence/<skill>.md` records the failure and the
  reverted state. Fix 1 ships regardless (it's a defect repair); fix 4 must earn its bytes.
- **If arm A already passes**, that skill's rewrite is not justified and reverts to A′.
- **If A′ ≈ B for a skill**, the armor isn't carrying its weight there and that skill reverts to A′
  even if B independently clears its own bar.

Null and negative results are recorded alongside positive ones.

### 7.4 Voice as a measured variable

**Probe skill: `verification-before-completion`** — sharpest binary outcome (claimed done without
running the command), shortest scenarios. **Model: `sonnet`**, matching §7.3; this is a stated
limitation (drovr sessions run Opus-class).

Four variants, identical in structure (same Iron Law, procedure, tables, placement), each adding
exactly one register device to the baseline:

| Variant | Register |
|---|---|
| **V0** | Baseline: plain imperative; no all-caps, no absolutist "no exceptions"; operational consequence only |
| **V1** | V0 + unity line |
| **V2** | V0 + full authority register (`MUST`/`NEVER`, all-caps Iron Law, no-exceptions bullets) |
| **V3** | V0 + moral framing, in superpowers' register |

4 variants × 2 scenarios × 3 samples = 24 runs, 6 per variant.

**Pre-registered decision rule** — each variant vs. V0, 6 runs per side, separation margin ≥3 of 6:

1. Variant beats V0 by ≥3 → that device ships across all five documents.
2. V0 beats the variant by ≥3 → that device is dropped; baseline register ships.
3. No separation ≥3 (likeliest outcome) → tier 3, follow superpowers: authority ships, moral
   framing ships, and unity ships anyway on the strength of the 2026 published ranking (tier 1
   outranks tier 3). Each recorded in `docs/skill-evidence/voice.md` as convention-or-prior, with
   the null attached.
4. Whatever wins applies to the other four documents without re-testing each. Stated limitation:
   measured on one skill, one model, generalized to five documents.

**Unity's arm is reported, not decisive** — 6 runs cannot overturn the N=126,000 published result.
If V1 loses to V0 by ≥3, that is recorded as a genuine conflict between the prior and drovr's own
data and **escalates to the human** rather than auto-resolving in either direction.
