# Spec: TUI deploy-config picker — browse any config in the project

## Problem

The deployment browser's `V` key is labelled "switch deploy config" but can only switch
**versions of the config the deployment is already linked to**. Two gates cause it:

1. **Name-pinned fetch.** `browse_deploy_config.go:76` calls
   `fetchDeployConfigVersions(ctx, c, cfg.BenchmarkProjectName, cfg.Name)` against the
   deployment's *currently linked* config, scoping the listing to one config name.
2. **Link-required entry point.** `browse_model.go:1910` rejects with `"not based on a
   deploy config"` when `m.sel.DeployConfigID == nil`, so an unlinked deployment cannot
   open the picker.

Net effect: every shared config, and every other config in the project, is unreachable
from `V`. Shared configs are the acute case — a deployment never linked to one can't
adopt it from the browser.

No API or server change is needed: `deployConfigService.List` with no name filter
already returns the latest version of every config in the project (including shared
configs, which are ordinary rows), and `api.Client.ListDeployConfigs` already exists and
is already used elsewhere.

## Decisions

### D1. Picker shape: three-level tree — project → config → version

Cross-project adoption follows directly: every project in the org is a root, so a
deployment can switch to a config in any project, not just its current one.

### D2. Presentation: one browsable collapsible tree, not sequential prompts

Built on the browser's existing `fieldTree` widget (`browse_fieldtree.go:151`), which
already backs the config/revision/diff panels and supplies cursor motion,
expand/collapse, and rendering. Rejected: three sequential `huh.Select` steps (as used by
`browse_source_config.go`) — a stepped picker can't compare two configs without backing
out and restarting, and browsing sideways is the point of this feature. `fieldTree` has
**no type-to-filter** (the `huh.Select` steps had `.Filtering(true)`); this is an accepted
cost, not silently dropped — see *Out of scope*.

Reused as-is from `browse_source_config.go`: `loadSrcConfigsCmd`/`latestPerConfig`
(listing configs), `fetchDeployConfigVersions` (listing versions),
`ListBenchmarkProjects` (listing projects), the async in-flight/stale-result guard
pattern, and the count-parameter pitfall (an omitted `count` means `LIMIT 0`, not
unlimited). Not reused: `newDeployConfigVersionPicker` and the `huh.Select` wiring — they
stay in place, still serving the create/edit form and `browse_form_sync.go`.

### D3. Lazy loading, one level at a time, with per-branch caching

Expanding a branch triggers its fetch; a branch that has never been expanded shows a
placeholder child (`loading…`, or `(none)` if empty) so it renders as expandable before
its children are known. Each branch caches its children after first load — collapse then
re-expand does not refetch. This is what makes the tree strictly cheaper than loading
every version of every config up front.

| Level | Loaded when | Call |
|---|---|---|
| projects | picker opens | `ListBenchmarkProjects` |
| configs of a project | that project first expanded | `ListDeployConfigs(project)` + `latestPerConfig` |
| versions of a config | that config first expanded | `fetchDeployConfigVersions(project, name)` |

### D4. Auto-expand on open

- **Linked deployment:** auto-expand its project and config, cursor on the current
  version — `V`, `↓`, `enter` covers the common case.
- **Unlinked deployment:** auto-expand the sole project when the org has exactly one,
  otherwise all projects stay collapsed, cursor on the first.

The linked case's auto-expand issues the same three requests a stepped picker would have
made on open, so the common path costs no more than today.

### D5. Selection payload lives on the tree node, not on a bare key

`fieldNode` gains one optional field: `pick any`, non-nil only on picker version leaves.
This removes the `Select[uint]` collision a flat-list design would have (version numbers
are not globally unique; the row id is, but a flat list keyed on it would force dropping
version selection or loading every version up front). `enter` on a branch (project or
config) just toggles it and arms no selection; `enter` on a version leaf arms the confirm.
`esc` cancels with `statusDCCanceled`.

### D6. Unlinked deployment adopting a config: preserve its configuration as overrides

`switchDeployConfigAction` passes `m.deployCfg` as the merge baseline into
`preserveDeploymentDivergences`. When unlinked, that baseline is currently `nil`, and the
function returns the target **verbatim** — resetting every field the deployment has,
including e.g. a pinned `engine_spec.image`. This is the same class of incident the
divergence-preservation work (`e351fdd69`) was written to prevent, and the edit form
already avoids it via `overridesFromConfiguration(prior)` fallback; `V` must match.

**Rule:** when the linked baseline is absent, `preserveDeploymentDivergences` performs a
**two-way deep merge** instead of returning the target verbatim: target is base,
deployment's current configuration is overlay, overlay wins on conflicting leaves, and
keys only the target carries still land. Implement as a distinct map-level helper (the
map twin of `mergeJSONPtr`) — reusing `threeWayMerge` with an empty-map baseline is
wrong, because its "value only current has" branch takes `curVal` wholesale for any key
absent from the baseline, dropping nested keys the target contributes.

### D7. Switching across config names: keep the three-way merge

The existing three-way merge (divergences from the previously-linked config) is kept even
when crossing to a different config name, because a pinned image surviving the switch
matters more in practice than semantic precision, and applying verbatim on a name change
would reintroduce the unpinning hazard D6 closes. Applies identically to cross-project
switches. Confirm copy states that overrides are carried across.

### D8. Confirm copy

`actionSwitchDeployConfig` confirm states, one line each: (a) switching redeploys
(already true today); (b) overrides are carried across (D6/D7); (c) when the chosen
config is shared, that its content is owned by the shared spec — the next `mcloud
deploy-config apply` creates a new version and moves the config's *latest*, but the
deployment stays pinned to the version selected here (versions are immutable rows).

### D9. Entry-point gate removed

`browse_model.go:1910-1917` drops the `DeployConfigID == nil` rejection — `V` becomes
valid on any detail-screen selection. `helpAdapter.dcLinked` (`browse_model.go:2916`)
loses its `DeployConfigID != nil` condition so the key is advertised on unlinked
deployments too.

### D10. Labelling

- Project node: `"<name>"`.
- Config node: `"<name>  (latest v<N>)"`, plus `"  (shared)"` when `Shared`, plus
  `"  (current)"` when it is the linked config.
- Version leaf: `"v<N>  <created>  <description>"` (reusing the label
  `newDeployConfigVersionPicker` already builds), plus `"  (latest)"` on the newest and
  `"  (current)"` on the deployment's current version.
- Panel label (`browse_panels.go:226-228`): `"V: switch version"` → `"V: switch deploy config"`.

`Shared` (`schemasv1.DeployConfigSchema:16`) is already returned by the list endpoint but
currently surfaced nowhere in the CLI/TUI; this is its first use.

## Interfaces / contracts

### New state on `appModel` (`browse_model.go`, alongside the existing `dc*` block)

```go
dcTree    *fieldTree                     // the picker; non-nil exactly while it is open
dcLinked  *schemasv1.DeployConfigSchema  // the linked config, when any: drives auto-expand,
                                         // cursor placement, and merge baseline for confirm
dcLoading map[string]bool                // in-flight branch loads, keyed "" (projects) /
                                         // "<project>" / "<project>\x00<config>"
// dcForm, dcVersions, dcCurrent, dcChoice are REPLACED by the tree.
// dcVersLoading is replaced by len(dcLoading) > 0.
```

### `fieldNode` (`browse_fieldtree.go:139-146`)

Adds one optional field: `pick any` — non-nil only on picker version leaves, nil on
every node existing (config/revision/diff) trees build. Mirrors how `diff` was added:
zero value is `nil`, so other trees are unaffected.

Adds `current() *fieldNode` accessor on `fieldTree`, returning the node under the
cursor, so the picker doesn't reach into unexported `flat`/`cursor` internals.

### New messages

```go
type dcProjectsMsg struct { name string; items []*schemasv1.BenchmarkProjectSchema; err error }
type dcConfigsMsg  struct { name, project string; items []*schemasv1.DeployConfigSchema; err error }
type dcVersionsMsg struct { name, project, config string; items []*schemasv1.DeployConfigSchema; err error }
```

`name` is the **deployment** name on all three, preserving the existing stale-result drop
(`msg.name != m.sel.Name`). `project`/`config` identify which branch the result fills, so
a result arriving after the user collapsed that branch lands on the right node rather
than the cursor's. `dcVersionsMsg` drops the `current uint` field the old design carried
— the current version is now known from `dcLinked`.

### Overlay routing

`currentOverlay()` (`browse_model.go:880`) keeps a single arm, now `case m.dcTree != nil:`
returning `overlayHandler{m.updateDCPicker, m.dcPickerView}`.

`autoRefreshPaused()`: the `m.dcVersLoading` arm is replaced with `m.dcTree != nil`, so
auto-refresh cannot swap `m.sel` out while the picker is open, including while it is idle
between branch loads (which the old in-flight flag did not cover).

### Transport — unchanged

`switchDeployConfigVersion` (`deploy_config.go:406`) already takes `(project, name,
version)` via confirm state (`dcProject`, `dcName`, `dcVersion` on `confirmState`) and
already sends `deploy_config_id` + full `configuration`. `completeDCSelection` populates
`dcProject`/`dcName` from the chosen leaf's config rather than the linked config's — no
transport change required.

## Scope boundaries

**In scope**
- `V` reaches every deploy config in the project, shared included.
- `V` works on unlinked deployments.
- Cross-project adoption via the tree's project level.
- Preserving the deployment's configuration when an unlinked deployment adopts a config
  (D6) — a change to `preserveDeploymentDivergences`, which also fixes the same gap for
  the existing `mcloud deployment deploy-config set` path that shares it.
- `pick` payload on `fieldNode` + `current()` accessor on `fieldTree`.
- `(shared)` / `(current)` / `(latest)` markers; confirm copy per D8.
- Panel/help label accuracy.
- Tests (below).

**Out of scope**
- Any API-server or schema change — not needed (see *Problem*).
- Type-to-filter in the picker — `fieldTree` has no equivalent to `huh.Select`'s
  `.Filtering(true)`; deferred as a shared-widget change with its own blast radius, not
  bundled here.
- Converting the create/edit form's source picker (`browse_source_config.go`) or the sync
  picker (`browse_form_sync.go`) to the tree — they differ in presentation, terminal
  action, and entry conditions; only `V` changes.
- Warning that editing a shared config gets reverted — moot: the TUI/CLI has no
  deploy-config write path at all (reads only via
  `internal/mcloudcli/api/deploy_config.go`; the sole write is `mcloud deploy-config
  apply`). The relevant consequence — linking to a shared config means the next
  `deploy-config apply` moves that config's *latest* out from under the deployment
  (which stays pinned to the version it selected) — is covered by the confirm copy in D8.
- Refactoring `browse_source_config.go` and the new `V` flow into one generic picker —
  they differ in presentation, terminal action, and entry conditions. Shared *data*
  helpers (`latestPerConfig`, `findDeployConfigVersion`, `fetchDeployConfigVersions`) are
  reused as-is.

## Follow-ups (not this change)

- Filtering in `fieldTree` — worth adding to the widget itself (config/revision panels
  would benefit too), but out of scope here.
- Converting the create/edit source picker to the same tree, once the tree has filtering.

## Testing

Table-driven model tests (`browse_deploy_config_test.go`, driving `appModel.Update` with
synthetic messages and a nil client):

1. `V` on an unlinked deployment opens the picker instead of `"not based on a deploy
   config"`.
2. `dcConfigsMsg` fills the right project branch with one node per config name; two
   configs' version leaves coexist in one tree with distinct `pick` payloads (regression
   guard for the `Select[uint]` collision the old design had).
3. A shared config's node label carries `(shared)`; the linked one carries `(current)`;
   the newest version leaf carries `(latest)`.
4. Auto-expand on open: linked deployment expands its project + config with cursor on
   the current version; unlinked with exactly one project expands that project; unlinked
   with two or more leaves everything collapsed.
5. `enter` on a version leaf arms `confirmState` with that leaf's project and config name
   (not the linked config's) — covers the cross-project case.
6. `enter` on a project or config branch toggles it and arms no confirm (`pick == nil`).
7. Expanding a branch twice issues one fetch; children are cached across collapse/expand.
8. Esc clears `dcTree` and sets `statusDCCanceled`.
9. Stale-result drop: a `dcConfigsMsg` for a deployment that is no longer `m.sel` is
   discarded; one for a branch the user has since collapsed fills that branch without
   moving the cursor.
10. `currentOverlay()` routes input to `updateDCPicker` exactly when `dcPickerView`
    renders.
11. `fieldNode.pick` is nil on every node the existing config/revision/diff tree builders
    produce (guards against the shared-widget change leaking into other panels).

Merge-semantics tests on `preserveDeploymentDivergences` (pure functions, table-driven,
no model):

12. Nil baseline preserves (D6): target config + a deployment carrying a pinned
    `engine_spec.image` and no link ⇒ the pin survives, and a key only the target carries
    still lands.
13. Nil baseline recurses: a nested key present in the target but absent from the
    deployment's config is not dropped (guards against the wholesale-replace trap noted
    in D6's implementation note).
14. Non-nil baseline unchanged: existing three-way behaviour is untouched, so the
    cross-config-name case (D7) keeps carrying divergences.

Plus `mise run go:lint`.
