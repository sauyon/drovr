# Spec: skill stickiness

drovr's skill docs read well but do not bind an agent under context pressure. This spec makes
them bind: five fixes, one new meta-skill, and an empirical acceptance test that gates whether the
armor ships.

## Order of work

Section numbers below are not build order. Actual order:

1. `drovr:writing-skills` + the scenario corpus (§6) — nothing else is testable without it.
2. Capture arm A / RED per skill (§6.3) at the pre-fix `HEAD`, before any skill file is touched —
   a hard gate; unrecoverable after fix 1 without a checkout.
3. Fixes 1 + 3 (descriptions, phase-framing demotions, task-binding directives).
4. Fix 4 (armor rewrite), using RED wording from step 2 for the rationalization tables.
5. Held-out arm B + the voice probe (§6.3, §6.4).
6. Fix 2's hook layer (Rust) — independently orderable, no dependency on 1–5. Fix 2's doc layer
   belongs with step 4.

## Decisions

### Authoring precedence (governs every claim in this spec and in the shipped skill text)

Four tiers, in order: (1) published evidence, cited in place; (2) no published evidence but the
question is measurable by this run's probe within the §6.3 budget — measure it; (3) not
measurable, or measurement inconclusive, and superpowers has a convention — follow it, and say so
is a convention-follow, not evidence; (4) no superpowers analogue — engineering judgement, marked
`[tier 4]`. Reason: superpowers' corpus is the output of an adversarial testing loop drovr has not
yet run, so it is a prior and tie-break, never a substitute for a reachable measurement.

Two standing rules regardless of tier:
- No fabricated measurements — a number, duration, or comparative is stated only if drovr measured
  it or a citation supports it.
- No copied text from superpowers — mechanisms are ported, wording is drovr's own (both MIT, so
  this is a project-identity choice, not a legal requirement).

### Voice / register

Three register questions (authority, unity, moral framing) are tier-2: measured in §6.4 rather
than settled here. Adopted by convention regardless of that outcome:

- Iron Law (one fenced all-caps line), spirit-vs-letter line before the rules, announcement string,
  checklist→task binding, rationalization table, red-flags list, "no exceptions" bullets pairing
  prohibition with required action, claim→evidence→not-sufficient table, numeric escalation
  trigger, ✅/❌ paired examples, top-loading binding content — all adopted from superpowers
  (tier 3 unless individually marked otherwise below).
- Commitment devices (announcement string, checklist→task binding) are evidence-backed as the
  strongest lever measured in the cited literature — promoted to primary, not contingent on §6.4.
- Unity ("the next phase agent is you, with your context gone") is applied to discipline skills —
  a deviation from superpowers, which withholds it there — on the strength of a newer replication
  ranking it top-two. Reported, not decisive: 6 probe runs cannot overturn that published result,
  but a loss by the pre-registered margin (§6.4) is recorded as a genuine conflict and escalated to
  a human rather than auto-resolved.
- Social proof is adopted only in true form (naming an observed failure mode from
  `docs/skill-evidence/`), never invented-frequency form.
- Flowcharts (fenced `dot` blocks): tier 3, used only for genuine branching or stop-too-early
  loops — the router's decision flow, the RED/GREEN/REFACTOR loop, and `tdd`'s and
  `systematic-debugging`'s red-green-refactor / reproduce-fix cycles. Everything else stays a
  numbered list. Rendering `dot` blocks in the review UI is out of scope (recorded as a follow-up
  in `docs/known-issues.md`).

### Length budget

- `cli/tests/skills_valid.rs`'s `BODY_BUDGET` is the single authoritative size check. `wc -l`/`wc
  -w` are author guidance only, never asserted.
- `BODY_BUDGET` for the four methodology skills (tdd, systematic-debugging,
  verification-before-completion, code-review): **2200 → 12000 bytes** `[tier 4]`.
- `using-drovr` gets its own budget and joins the checked list at **9000 bytes** `[tier 4]` —
  reason: it is injected in full on every `SessionStart`, making it the most expensive document in
  the repo, and is currently uncapped only by accident.
- Above cap, split into `references/`.
- Byte budget applies to teaching content only. Binding content (the prohibition an agent will try
  to talk itself out of) is deliberately restated 3–4 times per skill (Iron Law, red flag,
  rationalization row, checklist item) — redundancy is the mechanism, not a defect to trim.

## Fix 1 — un-scope the four methodology skills

Problem: all four discipline skills' `description:` scopes them to "a drovr phase," while
`using-drovr` makes inline work the default mode — so an agent working inline correctly concludes
the skill doesn't apply. Fix: descriptions become unconditional triggers; every drovr-phase
reference in the body demotes to a clearly-marked *additional* consequence, never a precondition.

New `description:` strings (final wording may tighten per fix 5's RED loop, but these are the
shipped defaults):

| File | New `description:` |
|---|---|
| `skills/tdd/SKILL.md:3` | Use when implementing any feature or bugfix, before writing implementation code — requires a test you have watched fail before any implementation exists; no production code without a red test first |
| `skills/systematic-debugging/SKILL.md:3` | Use when encountering any bug, test failure, or unexpected behavior, before proposing or writing a fix — requires a reproduction and a mechanistic root cause before any code change |
| `skills/verification-before-completion/SKILL.md:3` | Use when about to claim any work is done, fixed, or passing, before reporting, committing, or handing off — requires running the verification command in this message and reading its output; evidence before assertion, always |
| `skills/code-review/SKILL.md:3` | Use when you have written any change, before calling it done or handing it forward — requires read-only reviewer subagents run in the foreground, with every Critical and Important finding resolved or explicitly recorded as deferred |
| `skills/using-drovr/SKILL.md:3` | Use at the start of every session and before every response, including before clarifying questions and before reading any file — routes to the right drovr skill and requires invoking it whenever there is even a 1% chance one applies |

Body demotions: `tdd:17-19`, `systematic-debugging:14-17` (read-only-explorer rule stays
unconditional), `verification-before-completion:15-17,40-42`, `code-review:13-14,41` each collapse
their phase-framing to one subordinate sentence.

`docs/known-issues.md` gets one entry (file's standard convention) recording the scoping defect.
Only one entry — the rest of this spec is design work, not a defect report.

## Fix 2 — make `using-drovr` a per-turn gate

### Doc layer (`skills/using-drovr/SKILL.md`)

New content, in this order (position matters — earlier content gets read-position priority):

1. `<SUBAGENT-STOP>` — unchanged.
2. The 1% rule `[tier 3]`, above the H1: even a 1% chance a drovr skill applies means invoke it,
   paired with a cost-lowering clause (if it doesn't fit, drop it — invoking costs almost nothing).
3. Per-turn rule: check before any response, including clarifying questions and read-only
   exploration.
4. Instruction-priority ladder `[tier 3]`: human's explicit instructions > drovr skills > default
   behavior — the safety counterweight to the MUST language, not optional.
5. Gate function as a fenced `dot` flowchart: message received → does any skill apply (≥1%) →
   invoke → announce → has a checklist → create one tracked item per step → follow it → only then
   respond.
6. Red-flag table for the router's own failure mode (invoking nothing). Final row wording comes
   from the RED loop (fix 5), not fixed here.
7. Existing sections (single-writer, always-review, methodology, escalation) retained as-is.

Items 2–5 sit outside every `<!-- reflex:section:NAME -->` marker `[tier 4]` — `[reflex.sections]`
can subtract advisory sections but must not be able to silently delete the routing core; only
`[reflex] enabled = false` removes it.

### Hook layer (new `UserPromptSubmit` hook)

Everything in this subsection is `[tier 4]` — no superpowers analogue, no study on per-turn
re-injection. Ships as an explicit unmeasured bet, recorded in
`docs/skill-evidence/per-turn-gate.md`.

**Interface/contract:**

- `hooks/hooks.json` gains a `UserPromptSubmit` entry (no `matcher` — unlike `SessionStart`'s
  `startup|clear|compact`, which must not be copied across) running `hooks/user-prompt`, which
  `exec`s `drovr reflex --gate`.
- Byte budget: rendered `additionalContext` ≤ **600 bytes per injection**; cumulative ceiling
  **~60 KB over a 100-turn session**. Bytes, not tokens — the CLI has no tokenizer.
- Suppression rule: the card is emitted only when no `drovr:*` skill was invoked in the previous
  turn — bounds the cumulative cost; a session already running the discipline isn't re-told.
- Card content: the 1% rule, the per-turn check, the announcement string, the checklist-binding
  line, a `<SUBAGENT-STOP>` line, and a pointer to `Skill drovr:using-drovr`.
- Card text lives in a `const` in `reflex.rs`, not extracted from `SKILL.md` — extraction would
  need markers inside the region the doc layer deliberately places outside all `reflex:section`
  markers. Drift risk is mitigated by a test asserting the card's key phrases appear in
  `using-drovr/SKILL.md`.
- Config: new `[reflex] per_turn` bool in `ReflexConfig` (`cli/src/config.rs:39-64`), default
  **true** `[tier 4]`, suppressible per-user. Must use a named default fn, not bare
  `#[serde(default)]` (existing documented trap at `config.rs:108-110`).
- Suppression asymmetry, deliberate: the full `SessionStart` reflex stays suppressed inside phases
  (`DROVR_PHASE` set); the per-turn gate does **not** suppress in phases — a phase is exactly where
  the discipline must hold.
- Subagent handling: the card carries its own subagent-stop line unconditionally, because if
  `UserPromptSubmit` fires for Agent-tool subagents in this harness it would inject into every
  probe subagent and contaminate the evidence corpus. Step 1 of the build order empirically
  verifies whether the hook fires for subagents and records the answer in
  `docs/skill-evidence/per-turn-gate.md`.
- `README.md:70-94` updated with the new config key.

**Required API changes (verified against source, all in scope):**

1. `reflex.rs:143-152`'s `envelope()` hardcodes `"hookEventName": "SessionStart"` — parameterize to
   take the event name.
2. `main.rs:114-118` declares `Reflex { skill: PathBuf }` as required, and `main.rs:1276-1278`
   asserts bare `drovr reflex` errors. Adding `--gate` makes the field `Option<PathBuf>`, needs a
   clap arg-group rule (`--gate` xor `--skill`), and an update to that assertion's test.

**Out of scope for fix 2:** `PreToolUse` hard-denial of an `Edit` that skipped `drovr:tdd`, or of a
`git commit` with no verification evidence. That is enforcement, not persuasion — a larger design
with real false-positive risk, not this run.

## Fix 3 — bind checklists to tracked task state

Stated harness-agnostically because harnesses differ (some expose `TaskCreate`/`TaskUpdate`, stable
Claude Code exposes `TodoWrite`). Directive text to insert:

> When a skill or briefing gives you a numbered checklist, create one tracked item per step using
> whatever task tool this harness exposes before you start step 1. Mark each in-progress when
> started, complete when its evidence is in hand. If the harness exposes no task tool, write the
> checklist to `~/.local/share/drovr/runs/<run>/checklist.md` when inside a run, or `CHECKLIST.md`
> at the repo root otherwise, and tick items there.

Applied at four sites: `using-drovr`'s gate-function checklist branch; each discipline skill's
numbered procedure (one-line directive above it); `skills/pipeline/phase-prompts/*.md`'s `## Do`
lists (as step 0 — these are agent-assembled markdown, not compiled, so pure text change);
`skills/handoff/SKILL.md` and `HANDOFF-template.md`'s 7-section handoff. No CLI change required.

## Fix 4 — move the armor onto the discipline skills

`tdd`, `systematic-debugging`, `verification-before-completion`, `code-review` are restructured to
a fixed section order `[tier 3 — superpowers' convention, adopted wholesale]`:

```
   REQUIRED — all four skills
1. description:      trigger, not summary (fix 1)
2. Overview          core principle + spirit-vs-letter line + the WHY, ≤6 lines
3. Unity line        "the next phase agent is you, with your context gone"
4. The Iron Law      one fenced all-caps line + "No exceptions:" bullets closing named loopholes,
                     each bullet pairing the prohibition with the required action
5. Announce          the exact sentence to emit when invoking the skill (commitment device)
6. The procedure     numbered, preceded by the task-binding directive (fix 3)
8. Red flags — STOP  inner-monologue fragments, closed by a catch-all bullet
9. Rationalizations  thought → reality; the reality column is an INSTRUCTION, not a rebuttal
10. Worked example   one good ✅/❌ pair of actual utterances, not five
11. Cross-refs       bare skill names with REQUIRED markers; never @-links (they force-load)

   CONDITIONAL — only where named below
7. Requirements      claim → required evidence → not sufficient
                     ONLY: verification-before-completion, code-review
6b. Cycle flowchart  a fenced dot graph of the loop
                     ONLY: tdd, systematic-debugging
```

Announcement strings (template `Using drovr:<skill> to <purpose>.`):

- `tdd` — "Using drovr:tdd — writing the failing test before the implementation."
- `systematic-debugging` — "Using drovr:systematic-debugging — reproducing before fixing."
- `verification-before-completion` — "Using drovr:verification-before-completion — running the
  checks before claiming done."
- `code-review` — "Using drovr:code-review — dispatching read-only reviewers before calling this
  done."

Per-skill Iron Law and loophole closures:

- **tdd** — no implementation code before a test you have watched fail. Closes: "I'll keep the
  code as reference," "the test is obvious so I'll write it after," "it's a refactor so TDD
  doesn't apply," "the harness makes it hard to run one test."
- **systematic-debugging** — no fix before a reproduction and a mechanistic cause. Adds a numeric
  escalation trigger: after 3 failed fixes, stop and question the design before attempting fix #4.
- **verification-before-completion** — no completion claim without fresh evidence produced in this
  message. Requirements table covers tests / build / linter / bug-fixed / subagent-reported-success,
  plus a catch-all red flag for any wording implying success.
- **code-review** — no change is done until a read-only reviewer has looked at it and every
  Critical/Important finding is resolved or explicitly recorded as deferred. Closes: "the change is
  too small," "I already reviewed it myself," "the pipeline's review phase will catch it." The
  existing FOREGROUND rule is promoted into the no-exceptions list.

Placement reasons, stated so a reviewer doesn't over-read them: sections 2–5 sit early because
earlier position aids recall; sections 8–9 sit late for proximity to the point of temptation
(a judgement call, not the same finding); the procedure sits mid-document deliberately, since it's
what the agent actively re-reads while working and is least dependent on single-pass recall.

Expected size: roughly 120–180 lines each; the binding constraint is the 12000-byte budget, not
line count.

## Fix 5 — the meta-skill and the empirical loop

### New skill: `drovr:writing-skills`

`skills/writing-skills/SKILL.md`, in drovr's own voice; the pass criteria, four-part closure, and
scenario-construction rules are `[tier 3]` convention-follows ported from superpowers.

- Mapping: pressure scenario ↔ test case; `SKILL.md` ↔ production code; RED ↔ agent violates the
  rule without the skill; GREEN ↔ complies with the skill; REFACTOR ↔ close each new loophole.
- Loop (fenced `dot` flowchart): build scenario set → run baseline → transcribe every excuse
  verbatim → write minimal counter-text → re-run on held-out scenarios → apply the four-part
  closure to each new rationalization → repeat until a run produces no new rationalization **or**
  the §6.3 REFACTOR ceiling is reached, whichever first. The ceiling is not optional.
- Four-part closure, all four every time: explicit negation inside the rule; a rationalization-table
  row; a red-flags bullet; a `description:` update naming the symptom of being about to violate.
- Scenario construction: real file paths, concrete numbers/deadlines, a forced A/B/C choice, "what
  do you do" not "what should you do," no "I'd ask the human" escape hatch, ≥3 combined pressure
  types (agents resist single pressures, break under combined ones).
- Pass criteria, all four required: correct option under maximum pressure; agent cites a specific
  section; names the temptation and complies anyway; meta-test ("how should this have been
  written?") returns "it was clear."
- Scenario subagents run in the FOREGROUND; the author remains the single writer.
- Reference files: `references/pressure-scenarios.md`, `references/testing-with-subagents.md`,
  keeping `SKILL.md` itself under budget.

### Evidence corpus (interface: what gets written where)

- `skills/writing-skills/scenarios/<skill>-<n>.md` — checked-in scenario prompts, tagged `dev` or
  `holdout`.
- `docs/skill-evidence/<skill>.md` — per skill: scenarios used, verbatim baseline
  rationalizations, counter-text, re-test results with dates.
- `docs/skill-evidence/voice.md` — the voice-probe record.
- `docs/skill-evidence/per-turn-gate.md` — fix 2's unmeasured-bet record and the subagent-firing
  answer.
- `docs/skill-evidence/transcripts/` — raw transcripts; the corpus any numeric claim in shipped
  skill text must cite.

### The acceptance test (runs in this run)

Answers: did stickiness improve, or did the docs just get longer?

**Held-out design.** Per skill: 3 scenarios, 1 development + 2 held-out. RED transcription and
counter-text authoring use only the development scenario. The pass bar is scored on the held-out
pair, never read while writing arm B — authoring against the grading scenarios would fit the text
to the test.

**Arms** (three, so fix 1 and fix 4 are separable):

| Arm | Text |
|---|---|
| A | Current `SKILL.md` at pre-fix `HEAD` |
| A′ | Fix-1-only: descriptions un-scoped, no armor |
| B | Full rewrite (fixes 1 + 3 + 4) |

A′ exists because arm A's phase-scoped descriptions are themselves the defect fix 1 repairs;
without A′, B beating A would conflate fix 1's contribution with fix 4's.

**Budget** (hard ceiling; a ceiling hit halts and records a null, never silently extends):

| Stage | Runs | Ceiling |
|---|---|---|
| RED/baseline on dev set | 10 | 10 |
| Arm A on held-out | 20 | 20 |
| Arm A′ on held-out | 16 | 16 |
| Arm B on held-out | 20 | 20 |
| REFACTOR re-tests (failing skills only, ≤2 iterations each) | ≤20 | 20 |
| Voice probe | 24 | 24 |
| `using-drovr` no-skill-applies class | 12 | 12 |
| **Total** | **≈122** | **122** |

Decomposition: one dedicated phase per skill (`ab-<skill>`, 5 phases) plus a sixth (`ab-voice`),
each writing its own evidence file and transcripts and exiting; a driver aggregates. No phase holds
more than ~25 runs — reason: 122 foreground runs with verbatim transcription do not fit one
implement-task context.

**Scoring, pre-registered:**

- Rubric: binary compliant/non-compliant on the forced choice, plus the four pass criteria as
  separate booleans.
- Scorer: a read-only reviewer subagent given only the transcript and rubric.
- Blinding: arm labels stripped, transcripts shuffled before scoring; mapping restored only after
  all scores are recorded — arm B's author does not self-score.
- Model: `sonnet` for probe subagents and the scorer.

**Pre-registered bars:**

- Arm A "already passes": compliant on ≥3 of its 4 held-out runs.
- Arm B bar: compliant on ≥3 of its 4 held-out runs, AND strictly more compliant runs than both A
  and A′.
- Consequence of failure: a skill whose B fails after its REFACTOR ceiling does not ship its
  armor — it reverts to arm A′, and the evidence file records the failure and reverted state. Fix 1
  ships regardless (it's a defect repair); fix 4 must earn its bytes.
- If arm A already passes, that skill's rewrite is not justified and reverts to A′.
- If A′ ≈ B for a skill, the armor isn't carrying weight there and that skill reverts to A′ even if
  B passes its own bar.

Null and negative results are committed alongside positive ones.

### Voice probe

Probe skill: `verification-before-completion` (sharpest binary outcome, shortest scenarios). Model:
`sonnet`, matching the acceptance test — explicitly not the Opus-class model drovr sessions run on
(a stated limitation).

| Variant | Register |
|---|---|
| V0 | Baseline: plain imperative, no all-caps, no absolutist "no exceptions," operational consequence only |
| V1 | V0 + unity line |
| V2 | V0 + full authority register (MUST/NEVER, all-caps Iron Law, no-exceptions bullets) |
| V3 | V0 + moral framing, superpowers' register |

4 variants × 2 scenarios × 3 samples = 24 runs, 6 per variant, each compared against V0.

**Decision rule**, separation margin ≥3 of 6 each side:

1. Variant beats V0 by ≥3 → that device ships across all five documents.
2. V0 beats the variant by ≥3 → that device is dropped; baseline register ships.
3. No separation (likeliest outcome given n=6) → tier-3 fallback: authority ships, moral framing
   ships (superpowers uses both), unity ships anyway on the strength of the published ranking
   (tier 1 outranks tier 3). Each recorded in `docs/skill-evidence/voice.md` as
   convention-or-prior, with the null attached.
4. Whichever wins applies to the other four documents without re-testing each — stated limitation:
   measured on one skill, one model, generalized to five documents.

Exception: if V1 (unity) loses to V0 by ≥3, that is a genuine conflict between the published prior
and drovr's own data and escalates to a human rather than auto-resolving.

## Scope

**In scope:**

- All 8 `skills/*/SKILL.md`. Five get `description:` changes (fix 1); the four discipline skills
  get the fix-4 rewrite; `handoff`, `pipeline`, `worktrees` get only the fix-3 task-binding
  directive.
- `skills/handoff/HANDOFF-template.md`; the 5 files under `skills/pipeline/phase-prompts/`.
- New: `skills/writing-skills/` tree (`SKILL.md`, `references/`, `scenarios/`);
  `docs/skill-evidence/`.
- One `docs/known-issues.md` entry, plus a review-UI flowchart-rendering follow-up note.
- `hooks/hooks.json`, new `hooks/user-prompt`.
- `cli/src/reflex.rs` (`--gate`, `envelope()` parameterization), `cli/src/config.rs` (`per_turn`),
  `cli/src/main.rs` (arg-group wiring).
- `cli/tests/skills_valid.rs` (`BODY_BUDGET` 2200 → 12000; add `using-drovr` at 9000),
  `cli/tests/reflex_hook.rs` (per-turn hook cases), `main.rs:1276-1278`'s bare-`drovr reflex`
  assertion.
- `README.md:70-94`.

**Out of scope:**

- Rewriting `handoff` / `pipeline` / `worktrees` as full documents (task-binding directive only).
- `PreToolUse` enforcement of any kind.
- Any change to the phase state machine, the review gate, or `drovr code-review` itself.
- Rendering `dot` blocks in the review UI, or pairing a graph with the plan as a progress display —
  recorded as a `docs/known-issues.md` follow-up instead of built here.

**Deployment note:** these skills ship via the nix flake; nothing here takes effect in a running
session until the flake pin is bumped. The probe harness therefore feeds skill text to subagents
explicitly rather than relying on ambient injection.
