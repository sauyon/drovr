# Spec: TUI deploy-config picker — browse any config in the project

## Problem

The deployment browser's `V` key claims to "switch deploy config" but only switches
**versions of the config the deployment is already linked to**. Two gates cause it:

1. The fetch is name-pinned: `browse_deploy_config.go:76` calls
   `fetchDeployConfigVersions(ctx, c, cfg.BenchmarkProjectName, cfg.Name)` using the
   deployment's *currently linked* config, so the listing is scoped to one config name.
2. The entry point requires a link: `browse_model.go:1910` rejects with
   `"not based on a deploy config"` when `m.sel.DeployConfigID == nil`.

Net effect: every shared config, and every other config in the project, is unreachable
from `V`. Shared configs are the acute case — a deployment never linked to one can never
adopt it from the browser.

No API or server change is needed: `deployConfigService.List`
(`api-server/services/deploy_config.go:194-201`) with no name filter already returns the
latest version of every config in the project, including shared configs (ordinary rows
materialised by `reconcileShared`, `deploy_config.go:484-490`), and
`api.Client.ListDeployConfigs` (`internal/mcloudcli/api/deploy_config.go:26`) already
exposes it.

The TUI can already reach shared configs indirectly, via `e` (edit) → source = Deploy
config → 3-step picker (`browse_source_config.go`). The gap this spec closes is the
**direct, browsable path from the detail screen** — what `V` already claims to be.

## Decision: `V` opens a browsable collapsible tree

`V` opens a single tree — benchmark project → config → version — built on the browser's
existing `fieldTree` widget (`browse_fieldtree.go:151`), replacing the current
single-level version list. Rejected alternative: a chain of `huh.Select` steps (what
`browse_source_config.go` uses) — it forces committing to one level before seeing the
next, which defeats browsing ("what else is in this project?") and was reversed by the
reviewer on turn 2 in favor of one navigable tree.

`fieldTree` already supplies cursor motion (`up`/`down`), expand/collapse
(`setCollapsed`, `toggle`), visible-node recomputation (`reflatten`), and tree rendering
with `├──`/`└──` connectors — reused as-is. `browse_source_config.go`'s data plumbing
(`loadSrcConfigsCmd`/`latestPerConfig`, `fetchDeployConfigVersions`,
`ListBenchmarkProjects`, per-step stale-result guards, the `count`-omitted-means-`LIMIT 0`
pitfall) is reused wholesale; only its `huh.Select` presentation is dropped.

Not reused: `newDeployConfigVersionPicker` and its `huh.Select` wiring — they keep serving
the create/edit form and `browse_form_sync.go` unchanged.

### View and interaction

```
▾ project-a
  ├─ ▸ config-x   (latest v7)  (shared)
  ├─ ▾ config-y   (latest v2)  (current)
  │    ├─ v2  2026-07-01 09:14  bump engine image   (latest) (current)
  │    └─ v1  2026-06-20 11:02  initial
  └─ ▸ config-z   (latest v1)
▸ project-b
```

- `↑`/`↓` move the cursor over visible nodes.
- `→`/`l` expands, `←`/`h` collapses; `space` toggles.
- `enter` on a **version leaf** chooses it and arms the confirm. `enter` on a project or
  config branch only toggles it — a branch is never a selection.
- `esc` cancels the picker with `statusDCCanceled`.

### Lazy loading, per level, cached per branch

| Level | Loaded when | Call |
|---|---|---|
| projects | picker opens | `ListBenchmarkProjects` (1 request) |
| configs of a project | that project is first expanded | `ListDeployConfigs(project)` + `latestPerConfig` |
| versions of a config | that config is first expanded | `fetchDeployConfigVersions(project, name)` |

A never-expanded branch holds one placeholder child (`loading…`, replaced on arrival;
`(none)` when empty) so it renders as expandable before its children are known. Children
are cached after first load; re-collapsing/re-expanding does not refetch. This makes the
tree strictly cheaper than a flat list of every version of every config, which would need
all version listings up front. Rejected alternative — flat list keyed on config row id:
correctly fixes the `Select[uint]` collision the task named, but forces a choice between
dropping version selection (a regression) or loading everything eagerly; the tree gets
both without that trade-off, because selection is carried on the node (`pick`, below)
rather than keyed on a bare version number.

### On open

- **Linked deployment:** auto-expand its project and its config; cursor starts on the
  current version, so the common case is `V`, `↓`, `enter`.
- **Unlinked deployment:** auto-expand the sole project when the org has exactly one,
  otherwise leave all projects collapsed with the cursor on the first.

Auto-expand on open issues the same three requests (projects → linked project's configs →
linked config's versions) a stepped picker would have made, so the common path costs no
more than today.

### Cross-project adoption

Every project in the org is a tree root, so a deployment can switch to a config in any
project, not just its own — visible directly in the tree rather than requiring a
restart-from-scratch step change. No transport change: `switchDeployConfigVersion`
(`deploy_config.go:406`) already takes `project` as a parameter, and `confirmState`
already carries `dcProject`; `completeDCSelection` populates it from the chosen leaf's
project instead of the linked config's.

### Cost accepted: no type-to-filter

`huh.Select` had `.Filtering(true)`; `fieldTree` has no type-to-filter, so browsing a
large org is cursor-only. Adding filtering to `fieldTree` is out of scope (Follow-ups).

## Interfaces / contracts

### New state on `appModel` (`browse_model.go`, replacing the existing `dc*` block)

```go
dcTree    *fieldTree                     // the picker; non-nil exactly while it is open
dcLinked  *schemasv1.DeployConfigSchema  // linked config, if any: drives auto-expand,
                                         // cursor placement, and is the merge baseline
dcLoading map[string]bool                // in-flight branch loads, keyed "" (projects) /
                                         // "<project>" / "<project>\x00<config>"
```

`dcForm`, `dcVersions`, `dcCurrent`, `dcChoice` are removed (replaced by the tree).
`dcVersLoading` is removed (replaced by `len(dcLoading) > 0`).

### `fieldNode` gains a selection payload

`fieldNode` (`browse_fieldtree.go:139-146`) gains one optional field, zero value `nil` so
the config/revision/diff trees are unaffected (mirrors how `diff` was added):

```go
pick any // non-nil only on picker version leaves
```

The picker sets `pick` to the `*schemasv1.DeployConfigSchema` on each version leaf; `enter`
reads it back. Branch nodes leave it `nil` — that nil-ness *is* the "a branch is never a
selection" rule; no separate node-kind enum is added.

`fieldTree` gains a `current() *fieldNode` accessor returning the node under the cursor,
so the picker does not reach into the unexported `flat`/`cursor` internals.

### New messages

```go
type dcProjectsMsg struct { name string; items []*schemasv1.BenchmarkProjectSchema; err error }
type dcConfigsMsg  struct { name, project string; items []*schemasv1.DeployConfigSchema; err error }
type dcVersionsMsg struct { name, project, config string; items []*schemasv1.DeployConfigSchema; err error }
```

`name` is the deployment name on all three, preserving the existing stale-result drop
(`msg.name != m.sel.Name`). `project`/`config` identify which branch the result fills, so a
result for a branch the user has since collapsed lands on that branch, not the cursor.
`dcVersionsMsg` drops the `current uint` field — current version now comes from `dcLinked`.

### Overlay routing

`currentOverlay()` (`browse_model.go:880`) keeps a single arm, `case m.dcTree != nil:`,
returning `overlayHandler{m.updateDCPicker, m.dcPickerView}` — one form-like object, no
precedence ordering needed (a three-form `dcPickerActive()` would have needed one).

`autoRefreshPaused()`: the `m.dcVersLoading` arm becomes `m.dcTree != nil`, so an
auto-refresh cannot swap `m.sel` while the picker sits open and idle between branch loads
(a case the old in-flight-only flag did not cover).

### Entry-point gate

`browse_model.go:1910-1917`: drop the `DeployConfigID == nil` rejection — `V` becomes
valid on any detail-screen selection. `helpAdapter.dcLinked` (`browse_model.go:2916`) drops
its `DeployConfigID != nil` condition so the key is advertised on unlinked deployments too.

### Labelling

- Project node: `"<name>"`.
- Config node: `"<name>  (latest v<N>)"`, plus `"  (shared)"` when `Shared` is true, plus
  `"  (current)"` when it is the linked config. (`Shared`, `schemasv1.DeployConfigSchema:16`,
  is already returned by the list endpoint but currently surfaced nowhere in CLI or TUI —
  this is its first use.)
- Version leaf: `"v<N>  <created>  <description>"` (label logic reused from
  `newDeployConfigVersionPicker`, `browse_source_config.go:361-362`, via `trunc`/
  `sanitizeCell`), plus `"  (latest)"` on the newest and `"  (current)"` on the current
  version.
- Panel label (`browse_panels.go:226-228`): `"V: switch version"` → `"V: switch deploy
  config"`.
- Key help (`browse_model.go:200`) already reads `"switch deploy config"` — unchanged, now
  accurate.

### Transport — unchanged

`switchDeployConfigVersion` (`deploy_config.go:406`) already takes `(project, name,
version)` via `confirmState` (`dcProject`, `dcName`, `dcVersion`) and already sends
`deploy_config_id` + full `configuration`. `completeDCSelection` populates
`dcProject`/`dcName` from the chosen config rather than the linked one; no transport
change.

## Decision A: unlinked deployment adopting a config — preserve overrides

`switchDeployConfigAction` passes `m.deployCfg` as the merge baseline into
`preserveDeploymentDivergences` (`deploy_config.go:448`). For an unlinked deployment that
baseline is `nil` today, and the function returns the target **verbatim** — adopting a
config would reset every field the deployment has, including a pinned
`engine_spec.image`. This is the incident class `preserveDeploymentDivergences` exists to
prevent (commit `e351fdd69`; its doc comment cites 62 engine replicas rolled onto a
floating tag). The edit form already avoids this via
`completeConfigPick`→`overridesFromConfiguration(prior)` (`browse_source_config.go:445`);
`V` must match it.

**Rule.** When the linked baseline is absent, `preserveDeploymentDivergences` performs a
**two-way deep merge** instead of returning the target verbatim: target config is base,
deployment's current configuration is overlay, overlay wins on conflicting leaves, and
keys only the target carries still land. This is `mergeJSONPtr`'s existing semantics
("deep-merge overlay onto base: new deploy-config fields are kept, deployment-specific
overrides win on conflict", `browse_form_state.go:730-732`).

**Implementation constraint.** Do not reuse `threeWayMerge` with an empty-map baseline —
its "value only current has" branch takes `curVal` wholesale for any key absent from the
baseline (`deploy_config.go:479-481`), which would replace the target's top-level keys
wholesale and drop nested keys the config contributes. Implement the two-way merge as a
distinct, recursing map-level helper (the map twin of `mergeJSONPtr`), not a variant call
into `threeWayMerge`.

This also fixes the same gap in `mcloud deployment deploy-config set`, which shares
`preserveDeploymentDivergences`.

## Decision B: switching across config names — keep the three-way merge

Crossing to a different config name, the three-way merge's divergence baseline (the
previously-linked config) has no relationship to the target — but it is kept anyway: a
pinned image surviving the switch is the behavior that matters most in practice, and
applying verbatim on a name change would reopen the unpinning hazard Decision A closes.
The confirm copy states that overrides are carried across. Applies identically to a
cross-**project** switch — the baseline is the previously-linked config regardless of
which project it lived in.

## Decision: confirm copy

`actionSwitchDeployConfig`'s confirm states, one line each:

- switching redeploys the deployment (already true today);
- the deployment's overrides are carried across (Decision A/B);
- when the chosen config is shared: its content is owned by the shared spec, so the next
  `mcloud deploy-config apply` creates a new version and the config's *latest* moves — the
  deployment stays pinned to the version selected here, because versions are immutable
  rows.

## Resolved decisions

| # | Question | Decision |
|---|---|---|
| Q1 | Picker shape | Three-level: project → config → version. Cross-project adoption follows from this. |
| Q5 | Presentation | One browsable collapsible tree (turn-2 revision), not three sequential `huh.Select` prompts; built on `fieldTree`. Trade-off: no type-to-filter (Follow-ups). |
| Q2 | Project-level default when it can't be inferred | Auto-expand the sole project when the org has exactly one; otherwise leave projects collapsed — including for linked deployments, whose own project is auto-expanded regardless of org size. |
| Q3 | Unlinked deployment adopting a config | Preserve the deployment's current configuration as overrides (Decision A), via a recursing two-way deep merge. |
| Q4 | Switching across config names | Keep the three-way divergence merge against the previously-linked baseline (Decision B); confirm copy discloses it. |

Context: `schemasv1.DeploymentSchema` carries no benchmark-project field (only
`DeployConfigID`/`DeployConfigVersion`, `deployment.go:52`) — the project must come from
the picker or the linked config, never from the deployment itself.

## Scope boundaries

**In scope**
- `V` reaches every deploy config in the project, shared included, on unlinked
  deployments too.
- Cross-project adoption via the tree's project level.
- `preserveDeploymentDivergences` nil-baseline fix (Decision A) — also fixes `mcloud
  deployment deploy-config set`, which shares it.
- `fieldNode.pick` + `fieldTree.current()`.
- `(shared)`/`(current)`/`(latest)` markers; confirm copy per above.
- Panel/help label accuracy.
- Tests (below).

**Out of scope**
- Any API-server or schema change — none is needed.
- Type-to-filter in `fieldTree` (Follow-ups).
- Converting `browse_source_config.go`'s picker or `browse_form_sync.go`'s sync picker to
  the tree — they keep their `huh.Select` steps; only `V` changes.
- Warning that editing a shared config gets reverted — moot: the TUI/CLI have no
  deploy-config write path at all (`internal/mcloudcli/api/deploy_config.go` is read-only;
  the sole write is `mcloud deploy-config apply`,
  `internal/mcloudcli/cli/deploy_config_cmd.go:86`, the shared-apply POST itself). What
  *is* disclosed is the consequence of linking to a shared config (latest moves out from
  under a pinned deployment) — covered by the confirm-copy decision above.
- Refactoring `browse_source_config.go` and the new `V` flow into one generic picker: they
  differ in presentation, terminal action (reseed a form vs. arm a confirm + PATCH), and
  entry conditions. Shared data helpers (`latestPerConfig`, `findDeployConfigVersion`,
  `fetchDeployConfigVersions`) are reused as-is without this refactor.

## Follow-ups (not this change)

- Filtering in `fieldTree` — belongs on the shared widget (config/revision panels would
  benefit too), separate blast radius from this change.
- Converting the create/edit source picker to the same tree, once filtering exists, so the
  two paths look alike again.

## Testing

Table-driven model tests, existing style (`browse_deploy_config_test.go`, driving
`appModel.Update` with synthetic messages and a nil client):

1. `V` on an unlinked deployment opens the picker instead of `"not based on a deploy
   config"`.
2. `dcConfigsMsg` fills the right project branch with one node per config name; two
   configs' version leaves coexist in one tree with distinct `pick` payloads (regression
   guard for the `Select[uint]` collision the old design had).
3. A shared config's node carries `(shared)`; the linked one carries `(current)`; the
   newest version leaf carries `(latest)`.
4. Auto-expand on open: linked deployment expands its project + config with cursor on the
   current version; unlinked with exactly one project expands that project; unlinked with
   two-or-more leaves everything collapsed.
5. `enter` on a version leaf arms `confirmState` with that leaf's project and config name,
   not the linked config's (covers the cross-project case).
6. `enter` on a project or config branch toggles it and arms no confirm (`pick == nil`).
7. Expanding a branch twice issues one fetch; children are cached across collapse/expand.
8. Esc clears `dcTree` and sets `statusDCCanceled`.
9. Stale-result drop: a `dcConfigsMsg` for a deployment no longer `m.sel` is discarded; one
   for a branch the user has since collapsed fills that branch without moving the cursor.
10. `currentOverlay()` routes input to `updateDCPicker` exactly when `dcPickerView`
    renders.
11. `fieldNode.pick` is nil on every node the existing config/revision/diff tree builders
    produce (guards against the shared-widget change leaking into other panels).

Merge-semantics tests on `preserveDeploymentDivergences` (pure, table-driven, no model):

12. Nil baseline preserves (Q3): target config + a deployment carrying a pinned
    `engine_spec.image` and no link ⇒ the pin survives, and a key only the target carries
    still lands.
13. Nil baseline recurses: a nested key present in the target but absent from the
    deployment's config is not dropped (guards the wholesale-replace trap noted in
    Decision A's implementation constraint).
14. Non-nil baseline unchanged: existing three-way behavior is untouched, so the
    cross-config-name case (Q4) keeps carrying divergences.

Plus `mise run go:lint`.
