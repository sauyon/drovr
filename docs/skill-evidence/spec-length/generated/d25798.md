# Spec: skill stickiness

Drovr's skill docs read well and do not bind: they describe correct practice but nothing in
them forces compliance from an agent under context pressure. This spec makes five fixes, adds
one new meta-skill, and runs an empirical acceptance test to prove the fixes actually change
agent behavior rather than just lengthening the docs.

## Build order (not the section order)

1. `drovr:writing-skills` + the scenario corpus (§6) — nothing else is testable until this
   exists.
2. Capture arm A / RED per skill (§6.3), at pre-fix `HEAD`, before any skill file is touched.
   Hard gate: once fix 1 lands, arm A is unrecoverable without a checkout.
3. Fixes 1 + 3 (descriptions, task-binding directives).
4. Fix 4, using the RED wording captured in step 2 for its rationalization tables.
5. Held-out arm B + the voice probe (§6.3, §6.4).
6. Fix 2's hook layer (Rust) — independently orderable, no dependency on steps 1–5. Fix 2's doc
   layer belongs with step 4.

## Decision: evidentiary precedence for every authoring choice in this spec

Four tiers, checked in order, and every non-obvious choice below is tagged with the tier that
justifies it:

1. **Tier 1 — published evidence exists:** the evidence decides; citation kept in the text.
2. **Tier 2 — no evidence, but the question is answerable by this run's own probe within the §6.3
   budget:** measure it. Cost may excuse a tier-2 obligation only when measuring would exceed the
   stated ceiling, never because it seems not worth it.
3. **Tier 3 — not measurable, or measurement is inconclusive, and superpowers has a convention:**
   follow superpowers, and label it a convention-follow, not evidence.
4. **Tier 4 — no superpowers analogue at all:** engineering judgement, labelled `[tier 4]`.
   Applies to: the gate's byte budget, the card length, `per_turn`'s default, the reflex-marker
   boundary, the probe's model choice, the §7's length caps.

Two absolute rules regardless of tier:

- **No fabricated measurements.** No number, duration, frequency, or comparative is stated as
  measured unless drovr measured it or a citation supports it. (Superpowers states unverified
  figures like "15–30 minutes vs 2–3 hours"; drovr does not.)
- **No copied text.** Both projects are MIT, so copying-with-attribution would be legal, but
  drovr writes its own sentences — mechanisms are ported, expression is not. Any verbatim line
  found in review gets the MIT notice and credit added.

## Decision: what the evidence supports, and what it doesn't

- **Commitment devices are the best-evidenced lever** (top-two in both cited Meincke studies).
  The announcement string and checklist→tracked-task binding are commitment devices — promoted
  to primary (fixes 3, 4).
- **Unity ranks top-two in the 2026 replication**, above authority. Superpowers withholds unity
  from discipline skills, following the older ranking. Drovr applies unity to discipline skills
  anyway — a deviation backed by the newer data, framed literally rather than rhetorically: *the
  agent that inherits this work is the same agent, minus its context.*
- **Authority register** (`MUST`/`NEVER`/imperative) has no isolating study for procedural
  adherence → tier 2, measured in §6.4, with superpowers' full register as tier-3 fallback if
  inconclusive.
- **Moral framing** has no settling evidence either (the EmotionPrompt result is about benchmark
  accuracy from emotional stimuli, not procedural adherence, and its own headline number is a
  cherry-picked BIG-Bench selection; the corrected effect is +2.58% across benchmarks with the
  replication's own test finding no significant effect) → tier 2, measured in §6.4 on the same
  footing as authority.
- **Social proof** is adopted only in true form (naming an observed failure mode, e.g. from
  `docs/skill-evidence/`), never in superpowers' invented-frequency form ("every time"), per the
  no-fabrication rule above.
- **Position effects** (*Lost in the Middle*: retrieval is U-shaped, highest at start/end) are the
  basis for top-loading binding content (§4.1, §7) — measured on document retrieval, not
  mid-document instruction obedience, and on three-generations-old models, so treated as a prior
  for placement, not proof mid-document rules are ignored.
- **Load-degradation figures** (−2–21% formatting compliance under concurrent load) come from
  unread secondary summaries of 2026 preprints. They motivate but do not establish the redundancy
  rule (§7) or the per-turn gate (§3.2); never quoted as a measured drovr number.
- **Generic rule wrappers are non-monotonic** (one cited ablation: hurts extraction and RAG
  compliance, helps instruction-following +13%) → argues for keeping the per-turn card short and
  drovr-specific, not for any stronger claim.
- **Flowcharts are adopted `[tier 3]`** — no study compares flowcharts to numbered lists for
  agent compliance and the variant isn't probe-measurable (it's a structural change, not a text
  register). Placement follows superpowers' rule: flowcharts only for genuine branching or
  stop-too-early loops, never for linear instructions. Concretely: the `using-drovr` gate
  function, the RED/GREEN/REFACTOR loop, and `tdd`/`systematic-debugging`'s cycles get fenced
  `dot` blocks (superpowers already does this for TDD's cycle, so withholding it here would be an
  unmarked deviation); everything else linear stays a numbered list.
  - Rendering those `dot` blocks in the review UI, and pairing a graph with the plan as a
    progress display, is **out of scope** — it's review-UI work, not skill-doc work. Recorded as
    a follow-up in `docs/known-issues.md`.
- **Persuasion effects shrink on newer/smaller models** (40-point lift on GPT-4o-mini vs. a
  16-point lift on the 2026 Haiku/GPT-5-mini/Gemini-Flash replication), and none of the tested
  models are Sonnet or Opus, which is what drovr actually runs. Extrapolating to Sonnet/Opus is a
  stated assumption `[tier 4]`, not a finding.
- **Every prohibition pairs with the required action, and every rule carries its why** — per
  Anthropic's own prompting guidance (tell Claude what *to* do; give context/motivation).

## Fix 1 — un-scope the four methodology skills

**Problem this fixes:** all four discipline skills' `description:` fields say "in a drovr
phase" / "a drovr task" / "a drovr phase has produced," while `using-drovr` makes inline work
the default mode — so an agent working inline correctly concludes the skill doesn't apply to it.
Separately, a `description:` that summarizes the workflow (as `using-drovr`'s currently does)
lets the agent skip reading the skill body; Anthropic's own guidance calls the trigger
description the highest-leverage line in a skill.

**Decision — literal new `description:` strings, binding text (RED may tighten wording per the
fix-5 closure process, but these are the shipped defaults):**

| File | New `description:` |
|---|---|
| `skills/tdd/SKILL.md:3` | `Use when implementing any feature or bugfix, before writing implementation code — requires a test you have watched fail before any implementation exists; no production code without a red test first` |
| `skills/systematic-debugging/SKILL.md:3` | `Use when encountering any bug, test failure, or unexpected behavior, before proposing or writing a fix — requires a reproduction and a mechanistic root cause before any code change` |
| `skills/verification-before-completion/SKILL.md:3` | `Use when about to claim any work is done, fixed, or passing, before reporting, committing, or handing off — requires running the verification command in this message and reading its output; evidence before assertion, always` |
| `skills/code-review/SKILL.md:3` | `Use when you have written any change, before calling it done or handing it forward — requires read-only reviewer subagents run in the foreground, with every Critical and Important finding resolved or explicitly recorded as deferred` |
| `skills/using-drovr/SKILL.md:3` | `Use at the start of every session and before every response, including before clarifying questions and before reading any file — routes to the right drovr skill and requires invoking it whenever there is even a 1% chance one applies` |

**Decision — body demotions:** every drovr-phase reference in the four discipline skills'
bodies (`tdd:17-19`, `systematic-debugging:14-17`, `verification-before-completion:15-17,40-42`,
`code-review:13-14,41`) demotes to one subordinate, clearly-marked line stating it as an
*additional* consequence when in a phase, never a precondition for applying at all. Example:
*"Inside a drovr phase this also binds the next phase's contract."* The read-only-explorer rule
in `systematic-debugging` is unconditional already and is unchanged.

**Decision — known-issues entry:** one entry in `docs/known-issues.md`, in the file's existing
convention, documenting that four descriptions scoped unconditional discipline to phases while
`using-drovr` makes inline the default. One entry only — the other fixes are design work, not
defect writeups.

## Fix 2 — make `using-drovr` a per-turn gate

### Doc layer (`skills/using-drovr/SKILL.md`)

**Decision — new content, in this order** (top-loaded per the position-effects prior above):

1. `<SUBAGENT-STOP>` — unchanged, kept at `:8-11`.
2. **The 1% rule** `[tier 3]`, placed above the H1 inside the existing `<EXTREMELY_IMPORTANT>`
   block: even a 1% chance a drovr skill applies means invoke it, paired with a cost-lowering
   clause (if it doesn't fit, drop it — invoking costs almost nothing).
3. **The per-turn rule**: check before any response, including before a clarifying question or
   any read-only exploration.
4. **Instruction-priority ladder** `[tier 3]`: human's explicit instructions > drovr skills >
   default behavior. This is the safety counterweight to the MUST language, not optional.
5. **Gate function**, a fenced `dot` flowchart: message received → does any skill apply (≥1%)? →
   invoke → announce → has a checklist? → create one tracked item per step → follow it → only
   then respond.
6. **Red-flag table for the router's own failure mode** (invoking nothing) — drovr currently has
   zero coverage of this. Final row wording comes from fix 5's RED transcription, not authored in
   advance.
7. Existing sections (single-writer, always-review, methodology, escalation) retained unchanged.

**Decision:** items 2–5 sit outside every `<!-- reflex:section:NAME -->` marker `[tier 4]`.
`[reflex.sections]` config can subtract advisory sections but must never be able to silently
delete the routing core; only `[reflex] enabled = false` removes it, so a router can't end up
half-disabled without the operator making an explicit choice.

### Hook layer (new `UserPromptSubmit` hook) — all decisions here are `[tier 4]`, an explicit
unmeasured bet, recorded as such in `docs/skill-evidence/per-turn-gate.md`

**Interface/contract decisions:**

- `hooks/hooks.json` gains a `UserPromptSubmit` entry running a new thin script,
  `hooks/user-prompt`, which `exec`s `drovr reflex --gate`. This entry takes **no `matcher`**
  (unlike the existing `SessionStart` entry's `startup|clear|compact` matcher — that pattern must
  not be copied across).
- **Byte budget, not tokens** (the CLI has no tokenizer): rendered `additionalContext` ≤ **600
  bytes per injection**, plus a cumulative ceiling of **~60 KB over a 100-turn session**, since
  `additionalContext` is appended every turn and stays in the window. Asserted in
  `cli/src/reflex.rs`'s test module.
- **Suppression rule:** the card is emitted only when no `drovr:*` skill was invoked on the
  previous turn — bounds the cumulative cost so a session already running the discipline isn't
  re-told every turn.
- **Card content:** the 1% rule, the per-turn check, the announcement string, the
  checklist-binding line, an unconditional `<SUBAGENT-STOP>` line, and a pointer to
  `Skill drovr:using-drovr`.
- **Card text source:** a Rust `const` in `reflex.rs`, not extraction from `SKILL.md` (extraction
  would need markers inside the region the doc layer deliberately keeps outside all
  `reflex:section` markers). Accepted cost: drift between card and skill, mitigated by a test
  asserting the card's key phrases appear in `using-drovr/SKILL.md`.
- **Subagent contamination guard:** the card carries its own unconditional subagent-stop line
  regardless of whether `UserPromptSubmit` actually fires for Agent-tool subagents in this
  harness — build-order step 1 verifies that empirically and records the answer in
  `docs/skill-evidence/per-turn-gate.md`.
- **Config:** new `[reflex] per_turn` bool in `ReflexConfig` (`cli/src/config.rs:39-64`),
  **default true**, suppressible per-user, implemented with a **named default fn** (not bare
  `#[serde(default)]` — the trap already documented at `config.rs:108-110`).
- **Asymmetric suppression, deliberate:** the full `SessionStart` reflex stays suppressed inside
  phases (`DROVR_PHASE` set), because a phase agent runs on its injected briefing. The per-turn
  gate does **not** suppress in phases — a phase is exactly where the discipline must hold.
- `README.md:70-94` updated with the new config key.

**Three API facts that constrain the implementation (verified against source):**

1. `reflex.rs:143-152`'s `envelope()` hardcodes `"hookEventName": "SessionStart"` — must be
   parameterized to take the event name.
2. `main.rs:114-118` declares `Reflex { skill: PathBuf }` as required, and `main.rs:1276-1278`
   asserts bare `drovr reflex` errors. Adding `--gate` requires making the field
   `Option<PathBuf>`, adding a clap arg-group rule (`--gate` xor `--skill`), and updating that
   test.

### Out of scope for fix 2

`PreToolUse` hard-denying an `Edit` that skipped `drovr:tdd`, or a `git commit` with no
verification evidence — that's enforcement, not persuasion, a larger design with real
false-positive risk. Not this run.

## Fix 3 — bind checklists to tracked task state

**Decision — directive text, harness-agnostic** (some harnesses expose `TaskCreate`/
`TaskUpdate`/`TaskList`, stable Claude Code exposes `TodoWrite`):

> When a skill or briefing gives you a numbered checklist, create one tracked item per step using
> whatever task tool this harness exposes — `TodoWrite`, or `TaskCreate`/`TaskUpdate` — before you
> start step 1. Mark each in-progress when you start it and complete when its evidence is in
> hand. If the harness exposes no task tool, write the checklist to
> `~/.local/share/drovr/runs/<run>/checklist.md` when inside a run, or `CHECKLIST.md` at the repo
> root otherwise, and tick items there. An untracked checklist decays with the context window;
> that decay is the exact failure drovr exists to fight.

**Decision — applied at exactly four sites, no CLI change required:**

1. `skills/using-drovr/SKILL.md` — the gate function's checklist branch.
2. Each of the four discipline skills' numbered procedure gets a one-line binding directive
   immediately above it.
3. `skills/pipeline/phase-prompts/*.md` — the `## Do` lists (`implement-task.md:14-64` and the
   equivalents in `brainstorm.md`, `plan.md`, `review.md`, `review-angle.md`) gain the directive
   as step 0. These files are agent-assembled markdown, not compiled into the binary — pure text
   change.
4. `skills/handoff/SKILL.md` and `skills/handoff/HANDOFF-template.md` — the 7-section handoff is
   a checklist and gets the same treatment.

## Fix 4 — move the armor onto the discipline skills

**Decision — fixed section order for `tdd`, `systematic-debugging`,
`verification-before-completion`, `code-review`** `[tier 3 — superpowers' convention, adopted
wholesale]`:

```
   REQUIRED — all four skills
1. description:      trigger, not summary (fix 1)
2. Overview          core principle + spirit-vs-letter line + the WHY, ≤6 lines
3. Unity line        "the next phase agent is you, with your context gone"
4. The Iron Law      one fenced all-caps line + "No exceptions:" bullets closing named loopholes,
                     each bullet pairing the prohibition with the required action
5. Announce          the exact sentence to emit when invoking the skill (commitment device)
6. The procedure     numbered, preceded by the task-binding directive (fix 3)
8. Red flags — STOP  inner-monologue fragments, closed by a catch-all bullet
9. Rationalizations  thought → reality; the reality column is an INSTRUCTION, not a rebuttal
10. Worked example   one ✅/❌ pair of actual utterances. One good example, not five
11. Cross-refs       bare skill names with REQUIRED markers; never @-links (they force-load)

   CONDITIONAL — only where named below
7. Requirements      claim → required evidence → not sufficient
                     ONLY: verification-before-completion, code-review
6b. Cycle flowchart  a fenced dot graph of the loop
                     ONLY: tdd, systematic-debugging
```

Placement reasoning, stated so it isn't over-cited: sections 2–5 sit at the top because of the
position-effects prior. Sections 8–9 sit late for proximity to the point of temptation
(`[tier 4]` judgement, not the position finding). The procedure (6) sits mid-document
deliberately — it's the section the agent actively re-reads while working, so it's least
dependent on single-pass recall. The position finding is not cited for sections 6–9.

**Decision — announcement strings**, template `Using drovr:<skill> to <purpose>.`:

- `tdd` — *"Using drovr:tdd — writing the failing test before the implementation."*
- `systematic-debugging` — *"Using drovr:systematic-debugging — reproducing before fixing."*
- `verification-before-completion` — *"Using drovr:verification-before-completion — running the
  checks before claiming done."*
- `code-review` — *"Using drovr:code-review — dispatching read-only reviewers before calling this
  done."*

**Decision — per-skill Iron Laws and loophole closures:**

- **`tdd`** — Iron Law: no implementation code before a test you have watched fail. Closes: "I'll
  keep the code as reference", "the test is obvious so I'll write it after", "it's a refactor so
  TDD doesn't apply", "the harness makes it hard to run one test".
- **`systematic-debugging`** — Iron Law: no fix before a reproduction and a mechanistic cause.
  Adds a numeric escalation trigger: after 3 failed fixes, stop and question the design before
  attempting fix #4.
- **`verification-before-completion`** — Iron Law: no completion claim without fresh evidence
  produced in this message. Requirements table covers tests / build / linter / bug-fixed /
  subagent-reported-success. Catch-all red flag for any wording implying success.
- **`code-review`** — Iron Law: no change is done until a read-only reviewer has looked at it and
  every Critical/Important finding is resolved or explicitly deferred. Closes: "the change is too
  small", "I already reviewed it myself", "the pipeline's review phase will catch it". The
  existing FOREGROUND rule (`code-review/SKILL.md:19-23`) is promoted into the no-exceptions list
  — backgrounding a reviewer is the known way this skill silently fails.

**Decision — length budget** (binding constraint, not the line count): expected growth from
39–51 lines to roughly 120–180 lines each; see the byte-budget decision below for the actual
gate.

**Decision — byte budget test.** `cli/tests/skills_valid.rs:17` currently sets
`const BODY_BUDGET: usize = 2200` bytes over the four methodology skills only
(`using-drovr`/`handoff`/`pipeline` are unchecked). This spec's fix-4 rewrite breaks that budget
3–4×, so:

- `BODY_BUDGET` for the four methodology skills rises **2200 → 12000 bytes** `[tier 4 — no
  superpowers analogue, no evidence sets a "correct" length]`.
- `using-drovr` gets its own cap and joins the checked list at **9000 bytes** — it's the most
  expensive document in the repo (injected in full on every `SessionStart`, currently
  5087 B / 775 words / 93 lines and about to gain six blocks) and was previously exempt only by
  accident of history.
- Above cap, split into `references/`.
- `cli/tests/skills_valid.rs`'s byte check is the single authoritative size check. `wc -l`/`wc -w`
  are author guidance only, never asserted as a verification criterion.

## Fix 5 — the meta-skill and the empirical loop

### New skill: `drovr:writing-skills`

**Decision:** new file `skills/writing-skills/SKILL.md`, in drovr's voice, porting (not copying)
superpowers' `testing-skills-with-subagents.md:182-275` loop `[tier 3 convention-follow]`.
Also convergent with Anthropic's own skill-authoring guidance (build evals first, baseline
without the skill, write minimal instructions, iterate).

- **Mapping:** pressure scenario ↔ test case; `SKILL.md` ↔ production code; RED ↔ agent violates
  the rule without the skill; GREEN ↔ complies with the skill; REFACTOR ↔ close each new
  loophole.
- **Loop** (fenced `dot` flowchart, stop-too-early loop): build scenario set → run baseline →
  transcribe every excuse verbatim → write minimal counter-text → re-run on held-out scenarios →
  apply the four-part closure to each new rationalization → repeat **until a run produces no new
  rationalization or the §6.3 REFACTOR ceiling is reached, whichever comes first.** The ceiling is
  not optional — an uncapped loop is the exact unbounded-cost defect this spec exists to fix.
- **Four-part closure**, all four every time: explicit negation inside the rule; a row in the
  rationalization table; a bullet in red flags; a `description:` update adding the symptom of
  being about to violate.
- **Scenario construction rules:** real file paths, concrete numbers/deadlines, a forced A/B/C
  choice, "what do you do" not "what should you do", no escape hatch to "I'd ask the human", and
  ≥3 combined pressure types (time, sunk cost, authority, economic, exhaustion, social,
  pragmatic) — agents resist single pressures and break under combined ones.
- **Pass criteria (all four):** correct option under maximum pressure; the agent cites a specific
  section; it names the temptation and complies anyway; the meta-test ("how should this have been
  written?") returns "it was clear." Not-bulletproof signals: new rationalizations, arguing the
  skill is wrong, invented hybrid approaches, asking permission while still arguing for the
  violation.
- **drovr-specific constraints:** scenario subagents run in the FOREGROUND; the author is the
  single writer; the no-fabricated-measurements rule applies.
- Reference files `references/pressure-scenarios.md` and `references/testing-with-subagents.md`
  keep `SKILL.md` itself under the fix-4 byte cap.

### Evidence corpus (new paths, all in scope)

- `skills/writing-skills/scenarios/<skill>-<n>.md` — checked-in scenario prompts, each tagged
  `dev` or `holdout`.
- `docs/skill-evidence/<skill>.md` — per skill: scenarios used, verbatim baseline
  rationalizations, the counter-text written, re-test results with dates.
- `docs/skill-evidence/voice.md` — the voice-probe record.
- `docs/skill-evidence/per-turn-gate.md` — the fix-2 unmeasured-bet record and the
  subagent-firing answer.
- `docs/skill-evidence/transcripts/` — raw transcripts; the corpus any numeric claim in shipped
  skill text must cite.

### The acceptance test (runs inside this run)

**Purpose:** answers "did stickiness improve, or did the docs just get longer?"

**Decision — held-out design.** Per skill: 3 scenarios, 1 development + 2 held-out. RED
transcription and counter-text authoring use only the development scenario. The pass bar is
pre-registered and scored on the held-out pair, never read while writing arm B. (Grading arm B
against the scenarios that trained it would make the pass bar unfailable.)

**Decision — three arms**, so fix 1 and fix 4 are separable:

| Arm | Text |
|---|---|
| **A** | Current `SKILL.md` at pre-fix `HEAD` |
| **A′** | Fix-1-only: descriptions un-scoped, no armor |
| **B** | Full rewrite (fixes 1 + 3 + 4) |

A′ exists because A's descriptions are phase-scoped (the fix-1 defect) — without A′, a
non-phase-framed scenario would handicap A for reasons unrelated to the fix-4 armor, and any B>A
result would prove nothing about the armor specifically.

**Decision — budget table.** Every stage has a hard ceiling; hitting one halts that stage and
records a null in `docs/skill-evidence/` rather than silently extending:

| Stage | Scope | Runs | Ceiling |
|---|---|---|---|
| RED / baseline on dev set | 5 skills × 1 dev scenario × 2 samples | 10 | 10 |
| Arm A on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| Arm A′ on held-out | 4 discipline skills × 2 × 2 | 16 | 16 |
| Arm B on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| REFACTOR re-tests | failing skills only, ≤2 iterations each | ≤20 | 20 |
| Voice probe | 4 variants × 2 scenarios × 3 samples | 24 | 24 |
| `using-drovr` no-skill-applies class | 2 scenarios × 3 arms × 2 samples | 12 | 12 |
| **Total** | | **≈122** | **122 hard ceiling** |

The `using-drovr` extra class checks the router's own failure mode (invoking nothing) without
inducing the opposite failure (invoking everything reflexively).

**Decision — execution structure.** 122 foreground runs with verbatim transcription won't fit in
one implement-task context. Decomposition: one dedicated phase per skill, `ab-<skill>` (5
phases), each running its own stages and writing its own `docs/skill-evidence/<skill>.md` plus
raw transcripts, then exiting; the voice probe is a sixth phase, `ab-voice`. The driver
aggregates. No phase holds more than ~25 runs.

**Decision — scoring, pre-registered, not by arm B's author:**

- Rubric: binary compliant/non-compliant on the scenario's forced choice, plus the four
  `writing-skills` pass criteria recorded separately as booleans.
- Scorer: a read-only reviewer subagent given only the transcript and the rubric.
- Blinding: arm labels stripped and transcripts shuffled before scoring; mapping restored only
  after all scores are recorded.
- Model: `sonnet` for probe subagents and the scorer.

**Decision — pre-registered bars:**

- **Arm A bar:** a skill "already passes" if A is compliant on ≥3 of its 4 held-out runs.
- **Arm B bar:** compliant on ≥3 of its 4 held-out runs AND strictly more compliant runs than
  both A and A′.
- **Consequence of failure:** a skill whose B fails after its REFACTOR ceiling does not ship its
  armor — it reverts to A′ (fix-1-only), and `docs/skill-evidence/<skill>.md` records the failure
  and the reverted state. Fix 1 ships regardless (it's a defect repair); fix 4 must earn its
  bytes per skill.
- **Falsifiable:** if arm A already passes for a skill, that skill's rewrite isn't justified and
  reverts to A′ — the guard against length-for-its-own-sake.
- If A′ ≈ B for a skill, the armor isn't carrying its weight there and that skill reverts to A′
  even if B independently clears its own bar.
- Null and negative results are recorded alongside positive ones, not discarded.

### Voice as a measured variable

**Decision — probe design.** Three register questions (authority, unity, moral framing) have no
isolating published study and are all reachable as text variants of one probe skill:
`verification-before-completion` (sharpest binary outcome, shortest scenarios). Model: `sonnet`
— a stated limitation, since drovr sessions themselves run Opus-class.

| Variant | Register |
|---|---|
| **V0** | Baseline: plain imperative; no all-caps, no absolutist "no exceptions"; operational consequence only |
| **V1** | V0 + unity line |
| **V2** | V0 + full authority register (`MUST`/`NEVER`, all-caps Iron Law, no-exceptions bullets) |
| **V3** | V0 + moral framing, in superpowers' register |

4 variants × 2 scenarios × 3 samples = 24 runs, 6 per variant, each variant compared against V0.

**Decision — pre-registered rule, separation margin ≥3 of 6** (set to match stated power, not
below it):

1. Variant beats V0 by ≥3 → that device ships across all five documents.
2. V0 beats the variant by ≥3 → that device is dropped; plain register ships. This is an
   explicit, real outcome, not undefined behavior.
3. No separation ≥3 (likeliest outcome given n=6 and expected small register effects on frontier
   models) → tier 3: follow superpowers. Authority ships, moral framing ships, and unity ships
   anyway on the strength of the published 2026 ranking (tier 1 outranks tier 3). Each choice is
   recorded in `docs/skill-evidence/voice.md` as convention-or-prior, with the null attached.
4. Whichever result wins applies to the other four documents without separately re-testing each
   — stated limitation: measured on one skill, one model, generalized to five documents.

**Decision — unity's arm is reported, not decisive.** 6 runs cannot overturn the N=126,000
published result; the arm can only surface a large local effect if one exists. If V1 loses to V0
by ≥3, that's recorded as a genuine prior-vs-data conflict and escalated to the human rather than
auto-resolved either direction.

## Scope boundaries

**In scope:**
