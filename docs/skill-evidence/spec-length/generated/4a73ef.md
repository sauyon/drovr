# Spec: skill stickiness

drovr's skills read well and do not bind under context pressure: they describe correct practice
but contain none of the compliance devices (Iron Laws, rationalization tables, loophole closures,
checklist→task binding) that make an instruction survive a filling context window. This spec
makes them bind. Five fixes, one new meta-skill, and an empirical acceptance test that gates
whether each fix ships.

Root cause: superpowers' compliance devices are the recorded output of `writing-skills`, a
meta-skill that runs RED (transcribe a pressure-tested subagent's rationalizations verbatim)
/ GREEN (write the minimal counter-text) / REFACTOR (close each loophole, re-run) against the
skill text itself. drovr has never run this loop. Fix 5 introduces it; fixes 1–4 are the
candidate rewrites it tests. **Fixes 1–4 without fix 5 are assertions about what an agent
rationalizes; fix 5 makes them evidence**, and §7.3's pass/fail bars are binding — a fix that
fails its bar reverts.

## 0. Build order

Section numbers are not build order.

1. `drovr:writing-skills` + the scenario corpus (§6.1–6.2). Nothing else is testable first.
2. Capture arm A / RED per skill (§6.3) at the pre-fix `HEAD`, before any skill file is touched.
   Hard gate: once fix 1 lands, arm A is unrecoverable without a checkout.
3. Fixes 1 + 3 (§2, §4): descriptions, phase-framing demotions, task-binding directives.
4. Fix 4 (§5), using the RED wording captured in step 2 for the rationalization tables.
5. Held-out arm B + the voice probe (§6.3–6.4).
6. Fix 2's hook layer (§3.2) — the only Rust work, independently orderable, no dependency on
   steps 1–5. Fix 2's doc layer (§3.1) belongs with step 4.

## 1. Authoring precedence (governs every decision below)

Every wording, ordering, or register choice in this spec was made by this rule, in order:

1. **Published evidence exists** → the evidence decides; the citation stays in the shipped text.
2. **No evidence, but reachable by this run's loop** → **measure it** (§6.4). "Reachable" means
   expressible as a text variant of an existing probe skill, scorable by the existing rubric,
   within §6.3's ceiling. Cost discharges this tier only when measurement would exceed the
   ceiling — never because it seems not worth it.
3. **Not reachable, or measurement inconclusive, and superpowers has a convention** → **follow
   superpowers**, and label it a convention-follow, not evidence-backed.
4. **No superpowers analogue** → **engineering judgement, marked `[tier 4]`.** Applies to: the
   hook's byte budget, the card length, `per_turn`'s default, the reflex-marker boundary, the
   probe's model choice, §1's length caps. None of these may be defended as evidence-backed.

Two standing exceptions, both non-negotiable regardless of tier:

- **No fabricated measurements.** No number, duration, frequency, or comparative is stated as
  measured unless drovr measured it or a citation supports it (`docs/skill-evidence/` is the only
  source of drovr-measured numbers). Rhetorical emphasis ("every time") is fine; a false
  measurement claim is not.
- **No copied text.** Both projects are MIT; mechanisms are ported, sentences are drovr's own.
  Any verbatim ≥8-word shingle found in review (§8's check) gets reworded or the MIT notice and
  credit added.

**Decisions closed by this rule, with citation kept for reviewer judgment:**

- **Commitment devices (announcement string, checklist→task binding) are primary** — tier 1,
  ranks top-two in both the 2025 and 2026 Meincke studies. Fixes 3 and 4.
- **Unity is adopted for the four discipline skills**, deviating from superpowers (which
  withholds it there) — tier 1, the 2026 replication ranks unity top-two, above authority, on a
  paper that gives authority no procedural-adherence isolation either. Phrasing: literally true
  for drovr ("the next phase agent is you, with your context gone"), not rhetorical.
- **Authority register and moral framing are tier 2** — no published isolation for procedural
  adherence, both reachable by the probe → measured in §6.4 (voice probe variants V2, V3).
- **Position effects** (Liu et al., *Lost in the Middle*: retrieval accuracy is U-shaped) are the
  basis for top-loading binding content (§5). Caveat carried into the design: it measures document
  retrieval, not mid-document instruction obedience, on three-generations-old models — used as a
  placement heuristic, not proof mid-document rules are ignored.
- **Load-under-task-degradation figures** (−2–21%, recovered 90–100%) come from unread secondary
  summaries and are directional only. They inform the redundancy rule (§1 length policy) and the
  per-turn gate (§3.2) but are never quoted as measured numbers in shipped skill text.
- **Social proof** is adopted only in its true form — naming a failure mode actually observed in
  `docs/skill-evidence/` — never superpowers' invented-frequency form ("every time"), which the
  no-fabrication exception forbids.
- **Generic rule-wrapper ablation** (arXiv:2601.22025) is non-monotonic (hurts extraction/RAG,
  helps instruction-following +13%) and untested at drovr's scale. It argues for keeping §3.2's
  card short and drovr-specific; it is not cited as proof of the card's net effect.
- **Extrapolation limit, stated once, binding throughout:** the 2026 replication's models (Haiku
  4.5, GPT-5 mini, Gemini 3 Flash) are not the models drovr runs (probes: Sonnet; sessions:
  Opus-class). Applying its findings to Sonnet/Opus is `[tier 4]`, a stated assumption. Register
  is a real but secondary lever on that assumption.
- **Flowcharts are `[tier 3]`** — no study compares them to numbered lists and the variant isn't
  probe-reachable (it changes structure, not register). superpowers' rule is adopted as-is:
  fenced `dot` blocks **only** for genuine branching or a stop-too-early loop, never for linear
  procedure or reference material. Applies to: `using-drovr`'s gate function (§3.1), the
  RED/GREEN/REFACTOR loop (§6.1), and `tdd`/`systematic-debugging`'s cycle (§5) — superpowers
  puts a `dot` block on exactly the TDD cycle, so omitting one here would be an unmarked
  deviation. Other discipline procedures stay numbered lists (linear).
- **Rendering `dot` blocks in the review UI, and pairing a phase/gate graph with the plan display,
  is `[tier 4]` product judgement for a different audience (a human orienting mid-run) — out of
  scope for this run** (§7). Filed as a `docs/known-issues.md` follow-up note, not built here.

## 3. Fix 2 — `using-drovr` becomes a per-turn gate

### 3.1 Doc layer (`skills/using-drovr/SKILL.md`)

New content, in this order (position per §1's position-effects heuristic — earliest content gets
retrieval priority). Items 2 and 4 are `[tier 3]` convention-follows structurally close to
`using-superpowers/SKILL.md:11-29`; wording is drovr's own, the devices are ported wholesale.

1. `<SUBAGENT-STOP>` — unchanged, keep at `:8-11`.
2. **The 1% rule** `[tier 3]`, placed above the H1 inside the existing `<EXTREMELY_IMPORTANT>`
   framing: even a 1% chance a drovr skill applies means invoke it. Paired with a cost-lowering
   clause — if it turns out not to fit, drop it; invoking costs almost nothing.
3. **The per-turn rule**: check before any response, including before a clarifying question and
   before any read-only exploration.
4. **Instruction-priority ladder** `[tier 3]`: the human's explicit instructions > drovr skills >
   default behaviour. This is the safety counterweight to the MUST language, not optional.
5. **Gate function**, a fenced `dot` flowchart (branching, per §1's flowchart rule): message
   received → does any skill apply (≥1%) → invoke → announce → does it have a checklist → create
   one tracked item per step → follow it → only then respond.
6. **Red-flag table for the router's own failure mode** (invoking nothing at all — currently zero
   coverage). Candidate rows: *"this is a one-line change"*, *"I'll just look at the file first"*,
   *"they asked a question, not for work"*, *"I'm already mid-task, the router was for turn
   one"*, *"escalating to a phase would be overkill so no skill applies"*. Final wording comes
   from RED (§6), not from this list.
7. Existing sections (single-writer, always-review, methodology, escalation) retained unchanged.

**Placement contract:** items 2–5 sit outside every `<!-- reflex:section:NAME -->` marker
(`[tier 4]` — superpowers has no sectioned-reflex analogue). `[reflex.sections]` may subtract
advisory sections but must never be able to silently delete the routing core; only
`[reflex] enabled = false` removes it. Rationale: a half-disabled router produces an agent that
believes it is running drovr and is not, whereas an explicit master-switch-off is an informed
choice.

### 3.2 Hook layer (new `UserPromptSubmit` hook)

Every decision in this subsection is `[tier 4]`: superpowers is `SessionStart`-only, so there is
no convention and no study covers per-turn re-injection. It ships as an explicit unmeasured bet,
recorded in `docs/skill-evidence/per-turn-gate.md`.

- `hooks/hooks.json` gains a `UserPromptSubmit` entry running a new thin `hooks/user-prompt`
  script that `exec`s `drovr reflex --gate`. `UserPromptSubmit` takes **no** `matcher` — the
  existing `SessionStart` entry's `startup|clear|compact` matcher must not be copied across.
- **Byte budget**: rendered `additionalContext` ≤ 600 bytes per injection, and a cumulative
  ceiling of ~60 KB over a 100-turn session (`additionalContext` is appended every turn and stays
  in the window — cost is cumulative, not a rate). Length is bytes, not tokens (the CLI has no
  tokenizer); asserted in `cli/src/reflex.rs`'s test module.
- **Suppression rule** (bounds the cumulative cost): the card is emitted only when no `drovr:*`
  skill was invoked in the previous turn. A session already running the discipline is not
  re-told; a drifted session is.
- **Card content**: the 1% rule, the per-turn check, the announcement string, the
  checklist-binding line, a `<SUBAGENT-STOP>` line, and a pointer to `Skill drovr:using-drovr`.
- **Card text source**: a `const` in `reflex.rs`, not extraction from `SKILL.md` (extraction
  would need markers inside the region §3.1 deliberately places outside all `reflex:section`
  markers). Drift risk is mitigated by a test asserting the card's key phrases appear in
  `using-drovr/SKILL.md`.
- **Three required API changes, verified against source:**
  1. `reflex.rs:143-152`'s `envelope()` hardcodes `"hookEventName": "SessionStart"` — must be
     parameterized to take the event name.
  2. `main.rs:114-118` declares `Reflex { skill: PathBuf }` as required, and `main.rs:1276-1278`
     asserts bare `drovr reflex` errors. Adding `--gate` requires `Option<PathBuf>`, a clap
     arg-group rule (`--gate` xor `--skill`), and an update to that test.
  3. (Card text source — see above.)
- **Subagent contamination guard.** `using-drovr:8-11` already carries `<SUBAGENT-STOP>` for this
  case, and §6.3/§6.4's foreground probe subagents plus drovr's own read-only reviewers all
  launch from a gate-on session. The card therefore carries its own subagent-stop line
  unconditionally, and §0 step 1 verifies empirically whether the hook fires for Agent-tool
  subagents in this harness, recording the answer in `docs/skill-evidence/per-turn-gate.md`.
- **Config**: new `[reflex] per_turn` bool in `ReflexConfig` (`cli/src/config.rs:39-64`), default
  `true` `[tier 4]`, suppressible per-user, via a named default fn (not bare
  `#[serde(default)]` — the trap documented at `config.rs:108-110`).
- **Asymmetric suppression, deliberate.** The full `SessionStart` reflex stays suppressed inside
  phases (`DROVR_PHASE` set) because a phase agent runs on its injected briefing. The per-turn
  gate does **not** suppress in phases — a phase is exactly where the discipline must hold.
- `README.md:70-94` updated with the new key.

## 4. Fix 3 — bind checklists to tracked task state

Directive text, stated harness-agnostically (some sessions expose `TaskCreate`/`TaskUpdate`/
`TaskList` and no `TodoWrite`; stable Claude Code exposes `TodoWrite`):

> When a skill or briefing gives you a numbered checklist, create **one tracked item per step**
> using whatever task tool this harness exposes — `TodoWrite`, or `TaskCreate`/`TaskUpdate` —
> before you start step 1. Mark each in-progress when you start it and complete when its evidence
> is in hand. If the harness exposes no task tool, write the checklist to
> `~/.local/share/drovr/runs/<run>/checklist.md` when inside a run, or `CHECKLIST.md` at the repo
> root otherwise, and tick items there. An untracked checklist decays with the context window;
> that decay is the exact failure drovr exists to fight.

**Applied at four sites:**

1. `skills/using-drovr/SKILL.md` — the gate function's checklist branch (§3.1 item 5).
2. Each discipline skill's numbered procedure gets a one-line binding directive above it (part of

3. `skills/pipeline/phase-prompts/*.md` — the `## Do` lists (`implement-task.md:14-64`, 7 steps,
   and the equivalents in `brainstorm.md`, `plan.md`, `review.md`, `review-angle.md`) gain the
   directive as step 0. Pure text change — these files are agent-assembled markdown, not
   compiled into the binary.
4. `skills/handoff/SKILL.md` and `skills/handoff/HANDOFF-template.md` — the 7-section handoff is
   a checklist and gets the same treatment.

## 5. Fix 4 — move the armor onto the four discipline skills

`tdd`, `systematic-debugging`, `verification-before-completion`, `code-review` are restructured
to a fixed section order `[tier 3` — order is superpowers' convention, adopted wholesale`]`:

```
   REQUIRED — all four skills
1. description:      trigger, not summary (fix 1)
2. Overview          core principle + spirit-vs-letter line + the WHY, ≤6 lines
3. Unity line        "the next phase agent is you, with your context gone"
4. The Iron Law      one fenced all-caps line + "No exceptions:" bullets closing named loopholes,
                     each bullet pairing the prohibition with the required action
5. Announce          the exact sentence to emit when invoking the skill (commitment device)
6. The procedure     numbered, preceded by the task-binding directive (fix 3)
8. Red flags — STOP  inner-monologue fragments, closed by a catch-all bullet
9. Rationalizations  thought → reality; the reality column is an INSTRUCTION, not a rebuttal
10. Worked example   one ✅/❌ pair of actual utterances. One good example, not five
11. Cross-refs       bare skill names with REQUIRED markers; never @-links (they force-load)

   CONDITIONAL — only where named below
7. Requirements      claim → required evidence → not sufficient
                     ONLY: verification-before-completion, code-review
6b. Cycle flowchart  a fenced dot graph of the loop
                     ONLY: tdd, systematic-debugging   (§1 flowchart rule)
```

Sections 2–5 sit early (position-effects heuristic, §1). Sections 8–9 sit late for proximity to
the point of temptation — a `[tier 4]` judgement, not the position-effects finding; do not cite
that finding for sections 6–9. Section 6 (the procedure) sits mid-document deliberately: it is
what the agent re-reads while actively executing, so it is least dependent on single-pass recall.

**Announcement sentences** — template `Using drovr:<skill> to <purpose>.`:

- `tdd` — *"Using drovr:tdd — writing the failing test before the implementation."*
- `systematic-debugging` — *"Using drovr:systematic-debugging — reproducing before fixing."*
- `verification-before-completion` — *"Using drovr:verification-before-completion — running the
  checks before claiming done."*
- `code-review` — *"Using drovr:code-review — dispatching read-only reviewers before calling this
  done."*

**Per-skill specifics:**

- **`tdd`** — Iron Law: no implementation code before a test you have watched fail. Loophole
  closures: "I'll keep the code as reference", "the test is obvious so I'll write it after",
  "it's a refactor so TDD doesn't apply", "the harness makes it hard to run one test".
- **`systematic-debugging`** — Iron Law: no fix before a reproduction and a mechanistic cause.
  Adds a numeric escalation trigger: after 3 failed fixes, stop and question the design; no
  attempt at fix #4 without that conversation.
- **`verification-before-completion`** — Iron Law: no completion claim without fresh evidence
  produced in this message. Requirements table covers tests / build / linter / bug-fixed /
  subagent-reported-success. Catch-all red flag for any wording implying success.
- **`code-review`** — Iron Law: no change is done until a read-only reviewer has looked at it and
  every Critical/Important finding is resolved or explicitly recorded as deferred. Loophole
  closures: "the change is too small", "I already reviewed it myself", "the pipeline's review
  phase will catch it". The existing FOREGROUND rule (`code-review/SKILL.md:19-23`) is promoted
  into the no-exceptions list — backgrounding a reviewer is the known way this skill silently
  fails.

Expected size: 39–51 lines today → roughly 120–180 lines each. The binding constraint is §1's new
12000-byte `BODY_BUDGET` (below), not a line count.

**Length budget, all four skills:** teaching content stays terse and is cross-referenced, never
restated; binding content (the Iron Law, the matching red flag, the matching rationalization row,
the matching checklist item) is deliberately redundant, stated 3–4 times per skill, because
redundancy is the compliance mechanism. `cli/tests/skills_valid.rs:17`'s `const BODY_BUDGET`
(currently `2200` bytes, checked over exactly these four skills at `:20-25`; `using-drovr`,
`handoff`, `pipeline` are deliberately unchecked) rises to **12000 bytes**. `using-drovr` gets its
own new cap and joins the checked list at **9000 bytes** — it is the most expensive document in
the repo (injected in full on every `SessionStart`, currently 5087 B / 775 words / 93 lines, and
§3.1 adds six blocks) and leaving the highest-cost file uncapped while capping the others is
indefensible. Above cap, split into `references/`. `cli/tests/skills_valid.rs`'s byte check is the
**single authoritative size check**; `wc -l`/`wc -w` are author guidance only, never asserted.
Both cap values are `[tier 4]` — no superpowers analogue, no evidence sets a correct length; they
deviate from superpowers' own numbers in both directions (its TDD skill is 371 lines / 1496
words; its own guidance recommends <200 words for frequently-loaded skills).

This length policy governs skill-doc content only, per §1's general precedence — it does not
apply to the user's separate terseness preference for assistant replies, which is a different
document class (a reply is read once; a skill doc must survive a filling context window).

## 6. Fix 5 — the meta-skill and the empirical loop

### 6.1 New skill: `skills/writing-skills/SKILL.md`, in drovr's voice

Pass criteria, the four-part closure, and the scenario-construction rules below are `[tier 3]`
convention-follows, ported in drovr's own wording from
`testing-skills-with-subagents.md:182-275`, and independently convergent with Anthropic's
skill-authoring guidance (build evaluations first, baseline without the skill, minimal
instructions, iterate).

- **Mapping**: pressure scenario ↔ test case; `SKILL.md` ↔ production code; RED ↔ agent violates
  the rule without the skill; GREEN ↔ complies with the skill; REFACTOR ↔ close each new
  loophole.
- **Loop** (fenced `dot` flowchart — a stop-too-early loop, per §1): build the scenario set → run
  the baseline → transcribe every excuse verbatim → write the minimal counter-text → re-run on
  held-out scenarios → apply the four-part closure to each new rationalization → repeat until a
  run produces no new rationalization **or** the §6.3 REFACTOR ceiling is reached, whichever
  comes first. The ceiling is not optional — an uncapped loop is the unbounded-cost defect this
  spec exists to fix elsewhere.
- **Four-part closure** (all four, every time): explicit negation inside the rule; a row in the
  rationalization table; a bullet in red flags; a `description:` update adding the symptom of
  being about to violate.
- **Scenario construction rules**: real file paths, concrete numbers and deadlines, a forced
  A/B/C choice, "what do you do" not "what should you do", no escape hatch to "I'd ask the
  human", and ≥3 combined pressure types (time, sunk cost, authority, economic, exhaustion,
  social, pragmatic).
- **Pass criteria** (all four): correct option under maximum pressure; agent cites a specific
  section; names the temptation and complies anyway; meta-test ("how should this have been
  written?") returns "it was clear". Not-bulletproof signals: new rationalizations, the agent
  arguing the skill is wrong, invented hybrid approaches, asking permission while arguing hard for
  the violation.
- **drovr-specific constraints**: scenario subagents run in the FOREGROUND; the author is the
  single writer; §1's no-fabricated-measurements rule applies to every claim written into
  `docs/skill-evidence/`.
- Reference files: `references/pressure-scenarios.md`, `references/testing-with-subagents.md`,
  keeping `SKILL.md` under the §5 cap.

### 6.2 Evidence corpus (new tree)

- `skills/writing-skills/scenarios/<skill>-<n>.md` — checked-in scenario prompts, each tagged
  `dev` or `holdout` (§6.3).
- `docs/skill-evidence/<skill>.md` — per skill: scenarios used, verbatim baseline
  rationalizations, the counter-text, re-test results with dates.
- `docs/skill-evidence/voice.md` — the §6.4 probe record.
- `docs/skill-evidence/per-turn-gate.md` — §3.2's unmeasured-bet record and the subagent-firing
  answer.
- `docs/skill-evidence/transcripts/` — raw transcripts; this is the corpus any numeric claim in
  shipped skill text must cite (§1 exception).

### 6.3 Acceptance test — runs in this run

Answers: did stickiness improve, or did the docs just get longer?

**Held-out design.** Authoring arm B from the scenarios that grade it would fit the text to the
test. Per skill: 3 scenarios, 1 development + 2 held-out. RED transcription and counter-text
authoring use only the development scenario. The pass bar is pre-registered and scored on the
held-out pair, never read while writing arm B.

**Arms** (three, so fix 1 and fix 4 are separable):

| Arm | Text |
|---|---|
| **A** | Current `SKILL.md` at the pre-fix `HEAD` (captured in §0 step 2) |
| **A′** | Fix-1-only: descriptions un-scoped, no armor |
| **B** | Full rewrite (fixes 1 + 3 + 4) |

Arm A′ isolates fix 4's contribution: arm A's descriptions are phase-scoped (the defect §2
fixes), so without A′ a non-phase-framed scenario would handicap A for reasons unrelated to the
armor, and B > A would prove nothing about fix 4.

**Budget table.** Every stage has a hard ceiling. Hitting a ceiling halts that stage and records a
null in `docs/skill-evidence/` — it does not silently extend.

| Stage | Scope | Runs | Ceiling |
|---|---|---|---|
| RED / baseline on dev set | 5 skills × 1 dev scenario × 2 samples | 10 | 10 |
| Arm A on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| Arm A′ on held-out | 4 discipline skills × 2 × 2 | 16 | 16 |
| Arm B on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| REFACTOR re-tests | failing skills only, ≤2 iterations each | ≤20 | 20 |
| Voice probe (§6.4) | 4 variants × 2 scenarios × 3 samples | 24 | 24 |
| `using-drovr` no-skill-applies class | 2 scenarios × 3 arms × 2 samples | 12 | 12 |
| **Total** | | **≈122** | **122 hard ceiling** |

`using-drovr`'s extra scenario class checks the router's own failure mode (invoking nothing)
without inducing the opposite failure (invoking everything reflexively); it is budgeted, not
free.

**Execution shape.** 122 foreground subagent runs with verbatim transcription do not fit one
`implement-task` context. Decomposition: one dedicated phase per skill, `ab-<skill>` (5 phases),
each running its own stages, writing `docs/skill-evidence/<skill>.md` plus raw transcripts, then
exiting. The voice probe is a sixth phase, `ab-voice`. The driver aggregates results. No phase
holds more than ~25 runs.

**Scoring**, pre-registered and not done by arm B's author:

- **Rubric**: binary compliant/non-compliant on the scenario's forced choice, plus §6.1's four
  pass criteria recorded separately as booleans.
- **Scorer**: a read-only reviewer subagent, given only the transcript and the rubric.
- **Blinding**: arm labels stripped and transcripts shuffled before scoring; the mapping is
  restored only after all scores are recorded.
- **Model**: `sonnet` for both probe subagents and the scorer.

**Pre-registered bars:**

- **Arm A "already passes" bar**: compliant on ≥3 of its 4 held-out runs (2 held-out scenarios ×
  2 samples).
- **Arm B bar**: compliant on ≥3 of its 4 held-out runs for that skill, **and** strictly more
  compliant runs than both A and A′.
- **Consequence of failure**: a skill whose B fails after its REFACTOR ceiling does not ship its
  armor — it reverts to arm A′ (fix-1-only), and `docs/skill-evidence/<skill>.md` records the
  failure and the reverted state. Fix 1 ships regardless (it is defect repair); fix 4 must earn
  its bytes.
- **Falsifiability**: if arm A already passes for a skill, that skill's rewrite is not justified
  and reverts to A′.
- **A′ ≈ B**: if A′ performs comparably to B for a skill, the armor isn't carrying weight there
  and that skill reverts to A′ even if B independently clears its own bar.

Null and negative results are committed to `docs/skill-evidence/` alongside positive ones — a
result is not omitted for being negative.

### 6.4 Voice probe

Three register questions (authority, unity, moral framing — §1) are `[tier 2]`: no published
isolation for procedural adherence, all three reachable as text variants of one probe skill.

**Probe skill**: `verification-before-completion` (sharpest binary outcome — claimed done without
running the command — shortest scenarios). **Model: `sonnet`**, matching §6.3; not the
Opus-class model drovr sessions run on — a stated limitation alongside the extrapolation caveat
in §1.

**Variants**, identical in structure (same Iron Law, procedure, tables, placement), each adding
exactly one register device to the baseline so factors stay separable at this sample size:

| Variant | Register |
|---|---|
| **V0** | Baseline: plain imperative; no all-caps, no absolutist "no exceptions"; operational consequence only |
| **V1** | V0 + unity line |
| **V2** | V0 + full authority register (`MUST`/`NEVER`, all-caps Iron Law, no-exceptions bullets) |
| **V3** | V0 + moral framing, in superpowers' register |

4 variants × 2 scenarios × 3 samples = 24 runs, 6 per variant, each compared against V0.

**Pre-registered decision rule** (separation margin ≥3 of 6, chosen to match stated power — a
2-of-12 margin on binary outcomes is roughly one standard deviation and would fire on noise):

1. Variant beats V0 by ≥3 → that device ships across all five skill documents.
2. V0 beats the variant by ≥3 → that device is dropped; baseline register ships for that
   dimension. (Explicit branch: a plain-register win is a real, expected outcome.)
3. No separation ≥3 (the likeliest outcome, given §1's expectation of small register effects on
   frontier models) → tier 3, follow superpowers: authority ships (superpowers uses it), moral
   framing ships (superpowers uses it throughout), unity ships anyway on the strength of the 2026
   published ranking (tier 1 outranks tier 3). Each such outcome is recorded in
   `docs/skill-evidence/voice.md` as convention-or-prior, with the null attached.
4. Whichever register wins applies to the other four documents without separately re-testing
   each. Stated limitation: measured on one skill and one model, generalised to five documents.

**Unity's arm is reported, not decisive** — 6 runs cannot overturn an N=126,000 published result,
and this run does not claim otherwise; it can only reveal a large local effect if one exists.
**No directional escape hatch**: if V1 loses to V0 by ≥3, that is recorded as a genuine conflict
between the published prior and drovr's own data, and escalates to the human rather than being
auto-resolved by this spec.
