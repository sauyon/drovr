# Spec: skill stickiness

drovr's skill docs describe correct practice but bind nothing under context pressure. Five fixes,
one new meta-skill, one empirical acceptance test, run in this order (not section order):

1. `drovr:writing-skills` + scenario corpus (§7) — nothing else is testable without it.
2. Capture arm A / RED at pre-fix `HEAD` (§7.3) — hard gate, unrecoverable once fix 1 lands.
3. Fixes 1 + 3 (§3, §5).
4. Fix 4 (§6), using RED's wording for the rationalization tables.
5. Arm B + voice probe (§7.3, §7.4).
6. Fix 2's hook layer (§4.2) — independently orderable, no dependency on 1–5. Fix 2's doc layer
   (§4.1) belongs with step 4.

---

## 1. Decisions binding the whole run

**Authoring precedence, in order — deviation requires a citation, a measurement, or an explicit
tier-4 marking:**

1. Published evidence exists → evidence decides, citation kept in text.
2. No evidence but the question is reachable by this run's probe (§4 below) → measure it. Cost
   discharges this obligation only when measurement would exceed the §7.3 budget ceiling, never
   because it "doesn't seem worth it."
3. Not reachable, or measurement inconclusive, and superpowers has a convention → follow
   superpowers, labelled as a convention-follow, not evidence.
4. No superpowers analogue → engineering judgement, marked **[tier 4]**.

Two standing rules regardless of tier:

- **No fabricated measurements.** No number, duration, frequency, or comparative is stated as
  measured unless drovr measured it or a citation supports it.
- **No copied text.** Both projects MIT-licensed; drovr still writes its own sentences (mechanisms
  are ported, expression is not). Any verbatim survivor found in review gets MIT attribution added.

**What was measured vs. adopted as convention:**

| Device | Status |
|---|---|
| Commitment (announcement string, checklist→task binding) | evidence-backed (top-two in both Meincke studies) — primary in fixes 3–4 |
| Unity line | tier-1 prior (2026 replication ranks it above authority) + **measured** in §7.4 |
| Authority register (`MUST`/`NEVER`/all-caps) | **tier 2 — measured** in §7.4, superpowers register as tier-3 fallback |
| Moral/emotional framing | **tier 2 — measured** in §7.4 (EmotionPrompt null does not settle this; it measured benchmark accuracy from stimuli, not rule-violation framing) |
| Social proof | adopted only in true form (a failure mode actually observed in `docs/skill-evidence/`); never invented-frequency form |
| Flowcharts (fenced `dot`) inside skill docs | **[tier 3]** convention-follow; no study compares flowchart vs. list and the variant isn't probe-reachable |
| Flowcharts rendered in review UI | **[tier 4]**, and **out of scope** — recorded as a follow-up, not built |
| Position: top-load binding content | based on Liu et al. *Lost in the Middle* (retrieval accuracy, not instruction obedience; 2023-vintage models — a stated transfer caveat) |
| Load-degradation figures (−2–21%) | **not load-bearing for any decision** — secondary summaries, not read in full; never quoted as a measured number |

None of the persuasion/position literature is claimed to transfer to "coding agent adheres to an
already-agreed procedure over many turns under task load" — that transfer gap is exactly why §7
(the empirical loop) exists and is what actually settles fixes 1–4.

## 2. Fix 1 — un-scope the four methodology skills, contract change

**Problem statement:** each discipline skill's `description:` scopes it to "a drovr phase," while
`using-drovr` makes inline work the default mode — so the trigger text tells an inline agent the
skill doesn't apply to what it's doing. A `description:` must be a trigger, not a summary (a
summary lets the agent skip reading the skill).

**Binding: exact new `description:` strings (shipped defaults; RED transcription in §7 may tighten
wording per the four-part closure, but these are the baseline):**

| File | New `description:` |
|---|---|
| `skills/tdd/SKILL.md:3` | `Use when implementing any feature or bugfix, before writing implementation code — requires a test you have watched fail before any implementation exists; no production code without a red test first` |
| `skills/systematic-debugging/SKILL.md:3` | `Use when encountering any bug, test failure, or unexpected behavior, before proposing or writing a fix — requires a reproduction and a mechanistic root cause before any code change` |
| `skills/verification-before-completion/SKILL.md:3` | `Use when about to claim any work is done, fixed, or passing, before reporting, committing, or handing off — requires running the verification command in this message and reading its output; evidence before assertion, always` |
| `skills/code-review/SKILL.md:3` | `Use when you have written any change, before calling it done or handing it forward — requires read-only reviewer subagents run in the foreground, with every Critical and Important finding resolved or explicitly recorded as deferred` |
| `skills/using-drovr/SKILL.md:3` | `Use at the start of every session and before every response, including before clarifying questions and before reading any file — routes to the right drovr skill and requires invoking it whenever there is even a 1% chance one applies` |

**Body demotions (phase-framing becomes an additional consequence, never a precondition):**

| File | Change |
|---|---|
| `skills/tdd/SKILL.md:17-19` | One subordinate line: *"Inside a drovr phase this also binds the next phase's contract."* |
| `skills/systematic-debugging/SKILL.md:14-17` | Same demotion. Read-only-explorer rule stays unconditional. |
| `skills/verification-before-completion/SKILL.md:15-17,40-42` | *"If you are in a phase, this is also what gates `drovr phase done`."* |
| `skills/code-review/SKILL.md:13-14,41` | Same demotion for pipeline-review-phase and report-done references. |

**Rule for all five files:** unconditional discipline is the reading; drovr-phase references are
clearly marked additional consequences only.

**`docs/known-issues.md`:** one entry, in-convention (`## <symptom> — FIXED <date>`, `**Status:**`,
`**Severity:** medium`, `**Found:**`, `### Symptom`/`### Root cause`/`### Fix`), documenting that
four descriptions scoped unconditional discipline to phases while `using-drovr` defaults to
inline. One entry only — the other fixes are design work, not defect repair.

## 3. Fix 2 — `using-drovr` becomes a per-turn gate

### 3.1 Doc layer (`skills/using-drovr/SKILL.md`)

New content, in this order (top-loaded per position-effects prior):

1. `<SUBAGENT-STOP>` — unchanged (`:8-11`).
2. **1% rule** [tier 3]: even a 1% chance a drovr skill applies means invoke it; paired with the
   cost-lowering clause (if it doesn't fit, drop it — invoking is nearly free).
3. **Per-turn rule**: check before any response, including clarifying questions and read-only
   exploration.
4. **Instruction-priority ladder** [tier 3]: human's explicit instructions > drovr skills >
   default behaviour. Safety counterweight to the MUST language, not optional.
5. **Gate function**, fenced `dot` flowchart (branches, so it gets the flowchart treatment): message
   received → does any skill apply (≥1%) → invoke → announce → has a checklist → create one
   tracked item per step → follow it → only then respond.
6. **Red-flag table** for the router's own failure mode (invoking nothing) — candidate rows:
   *"this is a one-line change,"* *"I'll just look at the file first,"* *"they asked a question,
   not for work,"* *"I'm already mid-task, the router was for turn one,"* *"escalating to a phase
   would be overkill so no skill applies."* Final wording comes from RED (§7), not this list.
7. Existing sections (single-writer, always-review, methodology, escalation) retained.

**Placement constraint:** items 2–5 sit outside every `<!-- reflex:section:NAME -->` marker
[tier 4]. `[reflex.sections]` may subtract advisory sections but cannot delete the routing core;
only `[reflex] enabled = false` removes it.

### 3.2 Hook layer (new `UserPromptSubmit` hook) — every decision here is [tier 4], an explicit
unmeasured bet recorded in `docs/skill-evidence/per-turn-gate.md`

- `hooks/hooks.json` gains a `UserPromptSubmit` entry running `hooks/user-prompt`, which `exec`s
  `drovr reflex --gate`. **No `matcher`** on this entry (unlike `SessionStart`'s
  `startup|clear|compact`, which must not be copied across).
- **Byte budget: ≤600 bytes per `additionalContext` injection; cumulative ceiling ~60 KB over a
  100-turn session** (cost is cumulative — context stays in the window, not a rate).
- **Suppression rule**: card emitted only when no `drovr:*` skill was invoked in the previous turn
  — bounds the common case to a handful of injections.
- **Assertion location**: rendered `additionalContext` ≤ 600 bytes, checked in `cli/src/reflex.rs`
  test module. Byte budget, not tokens — the CLI has no tokenizer.
- **Card content**: 1% rule, per-turn check, announcement string, checklist-binding line, a
  `<SUBAGENT-STOP>` line, pointer to `Skill drovr:using-drovr`.
- **Card text source**: a `const` in `reflex.rs`, not extracted from `SKILL.md` (the doc content
  lives outside `reflex:section` markers on purpose). Drift mitigated by a test asserting the
  card's key phrases appear in `using-drovr/SKILL.md`.
- **Three required API changes, verified against source:**
  1. `reflex.rs:143-152`'s `envelope()` hardcodes `"hookEventName": "SessionStart"` — must be
     parameterized to take the event name.
  2. `main.rs:114-118`'s `Reflex { skill: PathBuf }` is required, and `main.rs:1276-1278` asserts
     bare `drovr reflex` errors. `--gate` forces `Option<PathBuf>`, a clap arg-group rule (`--gate`
     xor `--skill`), and an updated test.
  3. Card const lives in `reflex.rs`, not markdown-extracted (see above).
- **Subagents**: the card carries its own subagent-stop line unconditionally, because §7.3/§7.4's
  probe subagents and drovr's own read-only reviewers launch from a gate-on session and must not
  be contaminated. Step 1 of the build order (§0 above) empirically verifies whether
  `UserPromptSubmit` fires for Agent-tool subagents; the answer is recorded in
  `docs/skill-evidence/per-turn-gate.md`.
- **Config**: new `[reflex] per_turn` bool in `ReflexConfig` (`cli/src/config.rs:39-64`), **default
  true** [tier 4], suppressible per-user, via a **named default fn** (not bare
  `#[serde(default)]` — the trap documented at `config.rs:108-110`).
- **Asymmetric suppression**: the full `SessionStart` reflex still suppresses inside phases
  (`DROVR_PHASE` set — a phase agent runs on its injected briefing). The per-turn gate does **not**
  suppress in phases — a phase is exactly where the discipline must hold.
- `README.md:70-94` updated with the new key.

**Out of scope for fix 2:** `PreToolUse` hard-denial (e.g. blocking an `Edit` that skipped
`drovr:tdd`, or a `git commit` with no verification evidence) — enforcement rather than
persuasion, a larger design with real false-positive risk.

## 4. Fix 3 — bind checklists to tracked task state

Harness-agnostic binding directive (some sessions expose `TaskCreate`/`TaskUpdate`/`TaskList`, not
`TodoWrite`; stable Claude Code exposes `TodoWrite`):

> When a skill or briefing gives you a numbered checklist, create **one tracked item per step**
> using whatever task tool this harness exposes — `TodoWrite`, or `TaskCreate`/`TaskUpdate` —
> before you start step 1. Mark each in-progress when you start it and complete when its evidence
> is in hand. If the harness exposes no task tool, write the checklist to
> `~/.local/share/drovr/runs/<run>/checklist.md` when inside a run, or `CHECKLIST.md` at the repo
> root otherwise, and tick items there.

**Applied at four sites:**

1. `skills/using-drovr/SKILL.md` — gate function's checklist branch (§3.1 step 5 above).
2. Each discipline skill's numbered procedure — one binding-directive line above it.
3. `skills/pipeline/phase-prompts/*.md` — `## Do` lists (`implement-task.md:14-64`, 7 steps, plus
   `brainstorm.md`, `plan.md`, `review.md`, `review-angle.md`) gain the directive as step 0. Pure
   text change — these files are agent-assembled markdown, not compiled into the binary.
4. `skills/handoff/SKILL.md` and `skills/handoff/HANDOFF-template.md` — the 7-section handoff gets
   the same treatment.

No CLI change required for this fix.

## 5. Fix 4 — armor on the four discipline skills

`tdd`, `systematic-debugging`, `verification-before-completion`, `code-review` restructure to a
fixed section order [tier 3 — order is superpowers' convention, adopted wholesale]:

```
   REQUIRED — all four skills
1. description:      trigger, not summary (fix 1)
2. Overview          core principle + spirit-vs-letter line + the WHY, ≤6 lines
3. Unity line         "the next phase agent is you, with your context gone"
4. The Iron Law       one fenced all-caps line + "No exceptions:" bullets closing named loopholes,
                      each bullet pairing the prohibition with the required action
5. Announce           exact sentence to emit when invoking the skill (commitment device)
6. The procedure      numbered, preceded by fix 3's task-binding directive
8. Red flags — STOP   inner-monologue fragments, closed by a catch-all bullet
9. Rationalizations   thought → reality; the reality column is an INSTRUCTION, not a rebuttal
10. Worked example    one ✅/❌ pair of actual utterances — one good example, not five
11. Cross-refs        bare skill names with REQUIRED markers; never @-links (they force-load)

   CONDITIONAL — only where named
7. Requirements       claim → required evidence → not sufficient
                      ONLY: verification-before-completion, code-review
6b. Cycle flowchart   fenced dot graph of the loop
                      ONLY: tdd, systematic-debugging
```

**Announcement strings** (template `Using drovr:<skill> to <purpose>.`):

- `tdd` — *"Using drovr:tdd — writing the failing test before the implementation."*
- `systematic-debugging` — *"Using drovr:systematic-debugging — reproducing before fixing."*
- `verification-before-completion` — *"Using drovr:verification-before-completion — running the
  checks before claiming done."*
- `code-review` — *"Using drovr:code-review — dispatching read-only reviewers before calling this
  done."*

**Placement rule, stated precisely so it isn't mis-cited:** sections 2–5 are top-loaded because of
the position-effects prior; sections 8–9 sit late for *proximity to the point of temptation*
[tier 4], not the U-shape finding; section 6 (the procedure) deliberately sits mid-document — it's
what the agent actively re-reads while working, so it's least dependent on single-pass recall. Do
not cite the position-effects finding for sections 6–9.

**Per-skill content:**

- **`tdd`** — Iron Law: no implementation code before a test you have watched fail. Loophole
  closures: "I'll keep the code as reference," "the test is obvious so I'll write it after," "it's
  a refactor so TDD doesn't apply," "the harness makes it hard to run one test."
- **`systematic-debugging`** — Iron Law: no fix before a reproduction and a mechanistic cause. Adds
  a numeric escalation trigger: after 3 failed fixes, stop and question the design before
  attempting fix #4.
- **`verification-before-completion`** — Iron Law: no completion claim without fresh evidence
  produced in this message. Requirements table covers tests / build / linter / bug-fixed /
  subagent-reported-success. Catch-all red flag for any wording implying success.
- **`code-review`** — Iron Law: no change is done until a read-only reviewer has looked at it and
  every Critical/Important finding is resolved or recorded as deferred. Loophole closures: "the
  change is too small," "I already reviewed it myself," "the pipeline's review phase will catch
  it." The existing FOREGROUND rule (`code-review/SKILL.md:19-23`) is promoted into the
  no-exceptions list.

**Size:** current bodies are 39–51 lines; expected rewrite is ~120–180 lines each. The binding
constraint is the byte budget (§6 below), not a line count.

## 6. Fix 5 — `drovr:writing-skills` and the empirical loop

### 6.1 New skill: `skills/writing-skills/SKILL.md`

Pass criteria, four-part closure, and scenario-construction rules are **[tier 3]** convention-follows,
ported from superpowers' `testing-skills-with-subagents.md:182-275` in drovr's own wording.

- **Mapping**: pressure scenario ↔ test case; `SKILL.md` ↔ production code; RED ↔ agent violates
  the rule without the skill; GREEN ↔ complies with the skill; REFACTOR ↔ close each new loophole.
- **Loop** (fenced `dot` — a stop-too-early loop): build scenario set → run baseline → transcribe
  every excuse **verbatim** → write minimal counter-text → re-run on held-out scenarios → apply
  four-part closure to each new rationalization → repeat **until a run produces no new
  rationalization, or the §6.3 REFACTOR ceiling is reached, whichever first.**
- **Four-part closure** (all four, every time): explicit negation inside the rule; a row in the
  rationalization table; a bullet in red flags; a `description:` update adding the symptom of being
  about to violate.
- **Scenario construction**: real file paths, concrete numbers/deadlines, a forced A/B/C choice,
  "what do you do" not "what should you do," no escape hatch to "I'd ask the human," ≥3 combined
  pressure types (time, sunk cost, authority, economic, exhaustion, social, pragmatic).
- **Pass criteria** (all four): correct option under maximum pressure; agent cites a specific
  section; names the temptation and complies anyway; meta-test ("how should this have been
  written?") returns "it was clear." Not-bulletproof signals: new rationalizations, agent arguing
  the skill is wrong, invented hybrid approaches, asking permission while arguing for the
  violation.
- **drovr-specific constraints**: scenario subagents run in the FOREGROUND; single-writer applies;
  §1's no-fabricated-measurements rule applies.
- Reference files: `references/pressure-scenarios.md`, `references/testing-with-subagents.md` (keep
  `SKILL.md` under the byte cap).

### 6.2 Evidence corpus (new files)

- `skills/writing-skills/scenarios/<skill>-<n>.md` — checked-in scenario prompts, each tagged `dev`
  or `holdout`.
- `docs/skill-evidence/<skill>.md` — per skill: scenarios used, verbatim baseline rationalizations,
  counter-text, re-test results with dates.
- `docs/skill-evidence/voice.md` — the §6.4 probe record.
- `docs/skill-evidence/per-turn-gate.md` — §3.2's unmeasured-bet record and subagent-firing answer.
- `docs/skill-evidence/transcripts/` — raw transcripts; the only source drovr skill text may cite
  for a numeric claim.

### 6.3 Acceptance test (runs in this run)

**Held-out design.** Per skill: 3 scenarios — 1 development, 2 held-out. RED transcription and
counter-text authoring use only the development scenario. Pass bar is pre-registered and scored on
the held-out pair, never read while writing arm B.

**Arms (three, so fix 1 and fix 4 are separable):**

| Arm | Text |
|---|---|
| **A** | Current `SKILL.md` at pre-fix `HEAD` (captured in build step 2) |
| **A′** | Fix-1-only: descriptions un-scoped, no armor — isolates fix 4's contribution, since arm A's phase-scoped descriptions would otherwise handicap it for unrelated reasons |
| **B** | Full rewrite (fixes 1 + 3 + 4) |

**Budget table — hard ceilings; a ceiling hit halts and records a null in `docs/skill-evidence/`,
never silently extends:**

| Stage | Scope | Runs | Ceiling |
|---|---|---|---|
| RED / baseline on dev set | 5 skills × 1 dev × 2 samples | 10 | 10 |
| Arm A on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| Arm A′ on held-out | 4 discipline skills × 2 × 2 | 16 | 16 |
| Arm B on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| REFACTOR re-tests | failing skills only, ≤2 iterations each | ≤20 | 20 |
| Voice probe (§6.4) | 4 variants × 2 scenarios × 3 samples | 24 | 24 |
| `using-drovr` no-skill-applies class | 2 scenarios × 3 arms × 2 samples | 12 | 12 |
| **Total** | | **≈122** | **122 hard ceiling** |

**Execution shape:** 122 foreground subagent runs with verbatim transcription won't fit one
implement-task context. Decomposition: one dedicated phase per skill, `ab-<skill>` (5 phases),
each writing `docs/skill-evidence/<skill>.md` plus raw transcripts and exiting; `ab-voice` is a
sixth phase for the voice probe. Driver aggregates. No phase holds more than ~25 runs.

**Scoring:**

- Rubric: binary compliant/non-compliant on the scenario's forced choice, plus the four §6.1 pass
  criteria as separate booleans.
- Scorer: a read-only reviewer subagent, given transcript + rubric only — never arm B's author.
- Blinding: arm labels stripped, transcripts shuffled before scoring; mapping restored only after
  all scores recorded.
- Model: `sonnet` for probe subagents and the scorer.

**Pre-registered bars:**

- **Arm A "already passes"**: compliant on ≥3 of 4 held-out runs (2 scenarios × 2 samples).
- **Arm B bar**: compliant on ≥3 of 4 held-out runs AND strictly more compliant runs than both A
  and A′.
- **Failure consequence**: a skill whose B fails after its REFACTOR ceiling does not ship its armor
  — reverts to A′, failure recorded in `docs/skill-evidence/<skill>.md`. Fix 1 ships regardless
  (defect repair); fix 4 must earn its bytes.
- **Falsifiability**: if arm A already passes, that skill's rewrite isn't justified and reverts to
  A′ — guard against length-for-its-own-sake.
- If A′ ≈ B for a skill, the armor isn't carrying weight there — reverts to A′ even if B passes its
  own bar.

Null and negative results are recorded alongside positive ones.

### 6.4 Voice probe

Three register questions (authority, unity, moral framing) have no published study isolating them
for procedural adherence and are all reachable as text variants of one probe.

- **Probe skill**: `verification-before-completion` (sharpest binary outcome, shortest scenarios).
- **Model**: `sonnet` — a stated limitation, since drovr sessions run Opus-class.
- **Four variants**, identical structure (same Iron Law, procedure, tables, placement), each adding
  exactly one register device to baseline:

| Variant | Register |
|---|---|
| **V0** | Baseline: plain imperative; no all-caps, no absolutist "no exceptions"; operational consequence only |
| **V1** | V0 + unity line |
| **V2** | V0 + full authority register (`MUST`/`NEVER`, all-caps Iron Law, no-exceptions bullets) |
| **V3** | V0 + moral framing, in superpowers' register |

4 variants × 2 scenarios × 3 samples = 24 runs, 6 per variant.

**Decision rule** (each variant vs. V0, 6 runs/side, separation margin ≥3 of 6):

1. Variant beats V0 by ≥3 → ships across all five documents.
2. V0 beats variant by ≥3 → device dropped, baseline register ships.
3. No separation (likeliest outcome) → tier 3: follow superpowers. Authority ships, moral framing
   ships, unity ships anyway on the 2026 published ranking (tier 1 outranks tier 3). Recorded in
   `docs/skill-evidence/voice.md` as convention-or-prior with the null attached.
4. Winning variant applies to the other four documents without re-testing each — stated limitation:
   measured on one skill, one model, generalised to five documents.

**Unity exception**: unity's arm is reported, not decisive (6 runs cannot overturn N=126,000). If
V1 loses to V0 by ≥3, that is recorded as a genuine prior-vs-data conflict and **escalates to the
human** rather than auto-resolving in either direction.

## 8. Scope boundaries

**In scope:**

- All 8 `skills/*/SKILL.md`: five get `description:` changes (§2); four discipline skills get the
  §5 rewrite; `handoff`, `pipeline`, `worktrees` get **only** the fix-3 task-binding directive.
- `skills/handoff/HANDOFF-template.md`; the 5 files under `skills/pipeline/phase-prompts/`.
- New: `skills/writing-skills/` tree; `docs/skill-evidence/`.
- One `docs/known-issues.md` entry, plus the review-UI flowchart follow-up note.
- Hooks: `hooks/hooks.json`, new `hooks/user-prompt`.
- Rust: `cli/src/reflex.rs` (`--gate`, `envelope()` parameterization), `cli/src/config.rs`
  (`per_turn`), `cli/src/main.rs` (arg-group wiring).
- Tests: `cli/tests/skills_valid.rs`, `cli/tests/reflex_hook.rs`, `main.rs:1276-1278`.
- `README.md:70-94`.

**Out of scope:**

- Rewriting `handoff` / `pipeline` / `worktrees` as full documents (task-binding line only).
- Any `PreToolUse` enforcement (hard-denial of skipped steps) — a larger design, not this run.
- Any change to the phase state machine, the review gate, or `drovr code-review` itself.
- Rendering `dot` blocks in the review UI, or pairing a flowchart with the plan as a progress
  display — recorded as a `docs/known-issues.md` follow-up, not built here.

**Deployment note:** these skills ship via the nix flake; nothing here takes effect in a running
session until the flake pin is bumped. The probe harness (§6) therefore feeds skill text to
subagents explicitly rather than relying on ambient injection.
