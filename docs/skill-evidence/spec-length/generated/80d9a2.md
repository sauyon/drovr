# Spec: skill stickiness

Make drovr's skill docs bind under context pressure instead of merely describing correct
practice. Five fixes, one new meta-skill (`drovr:writing-skills`), and an empirical acceptance
test run inside this same run.

---

## 0. Build order

Section numbers below are not the build order.

1. `drovr:writing-skills` + the scenario corpus (§9.1–9.2) — build first; nothing else is
   testable until the harness exists.
2. Capture arm A / RED per skill (§9.3), at the pre-fix `HEAD`, before any skill file is touched.
   Hard gate: once fix 1 lands, arm A is unrecoverable without a checkout.
3. Fixes 1 + 3 (§5, §7): descriptions, phase-framing demotions, task-binding directives.
4. Fix 4 (§8), using the RED wording captured in step 2 for the rationalization tables.
5. Held-out arm B + the voice probe (§9.3–9.4).
6. Fix 2's hook layer (§6.2) — the only Rust work; independently orderable, no dependency on
   steps 1–5. Fix 2's doc layer (§6.1) belongs with step 4.

---

## 1. Problem being fixed

drovr's four discipline skills (`tdd`, `systematic-debugging`, `verification-before-completion`,
`code-review`) scope themselves to "a drovr phase" in both `description:` and body, while
`using-drovr` makes inline work the default mode — so the trigger text tells an agent working
inline that the skill does not apply. None of drovr's skills carry the compliance devices (Iron
Laws, rationalization tables, loophole closures, announcement strings, checklist→task binding)
that superpowers' equivalents do; drovr's discipline skills run 39–51 lines against superpowers'
139–371. No checklist anywhere binds to durable task state (`TodoWrite`/`TaskCreate` appear
nowhere in `skills/`). drovr's only re-assertion mechanism is a one-shot `SessionStart` hook that
no-ops inside phases; nothing re-asserts discipline after turn one, though Claude Code exposes
`UserPromptSubmit` and `PreToolUse` for exactly that and neither is used.

Root cause: superpowers has `writing-skills`, a meta-skill that runs RED/GREEN/REFACTOR against
the skill text itself — RED: a subagent without the skill, its rationalizations transcribed
verbatim; GREEN: minimal countering text; REFACTOR: close each loophole and re-run. Every
compliance device in superpowers' corpus is recorded output of that loop. drovr has none, so its
skills describe correct practice without binding it. Fixes 1–4 are assertions about what an agent
rationalizes; fix 5 — the same loop, run against drovr's own skills — is what turns them into
evidence. That is why fix 5 must exist and why §0 orders it around the others.

## 2. Authoring precedence (binds every decision below)

Every decision below that is not settled by direct citation is labeled with the tier of this rule
that produced it:

1. **Published evidence exists** → the evidence decides; the citation stays in the text.
2. **No published evidence, but the question is answerable by this run's own RED/GREEN loop or
   voice probe within the §9.3 budget ceiling** → measure it. Cost may discharge a tier-2
   obligation only when measurement would exceed the ceiling, never because it "doesn't seem
   worth it."
3. **Not reachable, or measurement inconclusive, and superpowers has a convention** → follow
   superpowers, marked as a convention-follow, not an evidence-backed choice.
4. **No superpowers analogue** → engineering judgement, marked **[tier 4]**. Applies to: the
   gate's byte budget, the card length, `per_turn`'s default, the reflex-marker boundary, the
   probe's model choice, §4's caps. None of these may be defended as evidence-backed.

Two standing rules, independent of tier:

- **No fabricated measurements.** No number, duration, frequency, or comparative is stated as
  measured unless drovr measured it or a citation supports it. `docs/skill-evidence/` is the only
  source for drovr-measured numbers.
- **No copied text.** Both projects are MIT; drovr still writes its own sentences — mechanisms
  are ported, expression is drovr's, under the `drovr:` namespace. Any verbatim line surviving
  review gets the MIT notice and credit added.

## 3. Voice and structural devices (bind §8's rewrite and §9.4's probe)

**Decided by citation (tier 1):**

- **Commitment devices ship as primary, unconditionally.** Commitment ranks top-two in both cited
  Meincke studies (2025, N=28,000; 2026 replication, N=126,000). The announcement string and
  checklist→task binding are commitment devices, the cheapest and best-evidenced in this spec —
  they ship via fix 3 and fix 4's "Announce" section, not gated behind §9.4's probe.
- **Top-loading binding content.** Liu et al. ("Lost in the Middle") measures retrieval accuracy
  as U-shaped by position — highest at start/end, lowest mid-document — for document retrieval,
  not instruction-obedience mid-document, on three-generations-old models. Basis for placing
  Overview/Unity/Iron-Law/Announce at the top of each discipline skill (§8's section order), not
  proof that mid-document rules are ignored.
- **Give the reason, say what to do.** Per Anthropic's prompting guidance, every prohibition in
  the rewritten skills pairs with the required action in the same breath, and every rule carries
  its why. The rationalization table's second column is written as an instruction ("Confidence is
  not evidence; run the command"), never a bare rebuttal.
- **Social proof ships only in its true form.** Named failure modes come only from
  `docs/skill-evidence/` observations; the invented-frequency form ("Every time.") is prohibited
  by the no-fabricated-measurements rule.

**Decided by tier-2 measurement, run as part of this spec (§9.4):**

- **Authority register** (`MUST`/`NEVER`/"no exceptions") — no published isolation for procedural
  adherence; measured as variant V2 against baseline V0.
- **Unity register** ("the next phase agent is you, with your context gone") — ranks top-two in
  the 2026 replication, above authority; drovr applies it to discipline skills as a deviation from
  superpowers (which withholds it there). Measured as variant V1. Unity's published rank is
  treated as a prior the local 6-run arm cannot overturn — see §9.4's exception clause for what
  happens if the local result conflicts with it.
- **Moral framing** — treated as untested, not rejected: the EmotionPrompt null (corrected:
  +4.42% BIG-Bench / +2.58% all-benchmark from Li et al.'s re-analysis; the replication's own
  measurement found no significant effect, χ²=0.11, p=.74) measures benchmark accuracy under
  emotional stimuli, not moral characterization of a rule violation, so it does not settle this
  construct. Measured as variant V3.

§9.4 specifies the full probe design and a decision rule that resolves all three into
shipped/dropped/convention-follow outcomes for every possible result — that procedure is itself
the decision here, not an open question.

**Decided by tier-3 convention-follow (superpowers' choice, adopted wholesale, unmeasured):**

- Iron Law (one fenced all-caps line, "No exceptions:" bullets pairing prohibition with required
  action).
- Spirit-vs-letter line, placed before the rules.
- Rationalization table (thought → reality, reality phrased as instruction).
- Red flags section (the agent's own inner-monologue fragments).
- Claim → required evidence → not-sufficient table.
- Numeric escalation trigger (stop after 3 failed fixes).
- ✅/❌ paired worked example.
- Fenced `dot` flowcharts for genuine branching / stop-too-early loops only — never for linear
  procedure. Applies to: `using-drovr`'s gate function (§6.1), `writing-skills`' RED/GREEN/REFACTOR
  loop (§9.1), `tdd`'s red-green-refactor cycle, `systematic-debugging`'s loop. No published
  comparison against a numbered list exists, and the variant is not reachable by the probe (it
  changes document structure, not text register).
- `using-drovr`'s 1% rule and instruction-priority ladder (human > drovr skills > default
  behaviour), ported from `using-superpowers/SKILL.md:11-29`.

**Decided by tier-4 engineering judgement:**

- Rendering the review-UI flowchart is a different artifact for a different audience (a person
  orienting mid-run) with no superpowers analogue — judged a better fit than prose for "where in a
  procedure the agent currently is," but out of scope here (§10) and tracked as a
  `docs/known-issues.md` follow-up rather than built.
- Load-degradation figures for formatting compliance under concurrent task load come from
  secondary summaries of unread 2026 preprints — consistent with but not establishing the
  redundancy rule (§4) or the per-turn gate (§6.2), never quoted as a measured drovr number.
- Generic rule-wrapper ablation (arXiv:2601.22025) is non-monotonic (hurts extraction/RAG, helps
  instruction-following +13%, n=50, Llama/Qwen) — read as "untested at drovr's scale," not as
  license to claim the per-turn card helps or hurts.
- Persuasion effects generally are extrapolated from the 2026 replication's Haiku/GPT-5-mini/
  Gemini-Flash-scale models to the Sonnet-probe / Opus-class-session models drovr actually runs —
  a stated, unverified assumption, not a finding.

## 4. Length budget (binds §8's rewrite and the CI check)

Rule: teaching content stays terse and is cross-referenced, never restated. Binding content — the
prohibition an agent will try to talk itself out of — is deliberately redundant, stated 3–4 times
per skill (Iron Law, red flag, rationalization row, checklist item), because redundancy is the
mechanism.

- `cli/tests/skills_valid.rs`'s `BODY_BUDGET` constant (currently 2200 bytes, `:17`, checked over
  the four discipline skills only, `:20-25`) rises to **12000 bytes** [tier 4 — no superpowers
  analogue, no evidence sets a correct length].
- `using-drovr` gets its own budget and joins the checked list at **9000 bytes** — it is injected
  in full on every `SessionStart` (currently 5087 B / 775 words / 93 lines; §6.1 adds six blocks)
  and is currently exempt only by accident of history.
- `cli/tests/skills_valid.rs`'s byte check is the single authoritative size check. `wc -l`/`wc -w`
  are author guidance only and are never asserted in §11's verification.
- Above either cap, split into `references/`.

Both new numbers are tier-4 judgement calls, not cited or measured, and are marked as such rather
than justified as evidence-backed.

## 6. Fix 2 — using-drovr as a per-turn gate

### 6.1 Doc layer — `skills/using-drovr/SKILL.md`

New content, in this order (position per §3's top-loading decision):

1. `<SUBAGENT-STOP>` — unchanged, kept at `:8-11`.
2. **The 1% rule** [tier 3, ported from `using-superpowers/SKILL.md:11-29`], placed above the H1
   inside the existing `<EXTREMELY_IMPORTANT>` block: even a 1% chance a drovr skill applies means
   invoke it, paired with the cost-lowering clause (if it turns out not to fit, drop it — invoking
   costs almost nothing).
3. **The per-turn rule**: check before any response, including before a clarifying question and
   before any read-only exploration.
4. **Instruction-priority ladder** [tier 3]: human's explicit instructions > drovr skills >
   default behaviour. This is the safety counterweight to the MUST language and is not optional.
5. **Gate function** — a fenced `dot` flowchart (branching, per §3's placement rule): message
   received → does any skill apply (≥1%) → invoke → announce → does it have a checklist → create
   one tracked item per step → follow it → only then respond.
6. **Red-flag table for the router's own failure mode** (invoking nothing at all — drovr currently
   has zero coverage of this). Candidate rows, finalized by fix 5's RED pass rather than fixed
   here: *"this is a one-line change," "I'll just look at the file first," "they asked a question,
   not for work," "I'm already mid-task, the router was for turn one," "escalating to a phase would
   be overkill so no skill applies."*
7. Existing sections (single-writer, always-review, methodology, escalation) are retained
   unchanged.

Items 2–5 sit outside every `<!-- reflex:section:NAME -->` marker [tier 4 — superpowers has no
sectioned-reflex analogue]: `[reflex.sections]` may subtract advisory sections but must not be
able to silently delete the routing core; only `[reflex] enabled = false` removes it. A
half-disabled router produces an agent that believes it is running drovr and is not, whereas a
master-switch-off is an informed choice.

### 6.2 Hook layer — new `UserPromptSubmit` hook

Every decision in this subsection is tier 4: superpowers is `SessionStart`-only, so there is no
convention, and no study covers per-turn re-injection. It ships as an explicit, unmeasured bet,
recorded as such in `docs/skill-evidence/per-turn-gate.md`.

- `hooks/hooks.json` gains a `UserPromptSubmit` entry running a new, thin `hooks/user-prompt`
  script that `exec`s `drovr reflex --gate`. `UserPromptSubmit` takes **no** `matcher` — the
  existing `SessionStart` entry's `startup|clear|compact` matcher is not copied across.
- **Byte budget: ≤600 bytes per injection, and a cumulative ceiling of ~60 KB over a 100-turn
  session.** `additionalContext` is appended every turn and stays in the window, so the cost is
  cumulative, not a rate — both numbers are stated because of that.
- **Suppression rule** (bounds the cumulative cost): the card is emitted only when no `drovr:*`
  skill was invoked in the previous turn. A session already running the discipline is not
  re-told; a drifted session is.
- **Byte budget, not tokens** — the CLI has no tokenizer. The assertion is rendered
  `additionalContext` ≤ 600 bytes, checked in `cli/src/reflex.rs`'s test module.
- **Card content:** the 1% rule, the per-turn check, the announcement string, the
  checklist-binding line, a `<SUBAGENT-STOP>` line, and a pointer to `Skill drovr:using-drovr`.
- **Three required API changes** (verified against source):
  1. `reflex.rs:143-152`'s `envelope()` hardcodes `"hookEventName": "SessionStart"` —
     parameterize it to take the event name.
  2. `main.rs:114-118` declares `Reflex { skill: PathBuf }` required, and `main.rs:1276-1278`
     asserts bare `drovr reflex` errors. `--gate` makes it `Option<PathBuf>` with a clap arg-group
     rule (`--gate` xor `--skill`); that test is updated accordingly.
  3. Card text lives as a `const` in `reflex.rs`, not extracted from `SKILL.md` — extraction would
     need markers inside the region §6.1 deliberately places outside all `reflex:section` markers.
     The resulting drift risk between card and skill is mitigated by a test asserting the card's
     key phrases appear in `using-drovr/SKILL.md`.
- **Subagents:** the card carries its own unconditional subagent-stop line, because §9's
  foreground probe subagents and drovr's own read-only reviewers all launch from a gate-on session
  and would otherwise get contaminated by the injection. Whether `UserPromptSubmit` actually fires
  for Agent-tool subagents in this harness is verified empirically as build step 1 (§0), and the
  answer is recorded in `docs/skill-evidence/per-turn-gate.md`.
- **Config:** new `[reflex] per_turn` bool in `ReflexConfig` (`cli/src/config.rs:39-64`), default
  `true` [tier 4], suppressible per-user, via a named default fn (not bare `#[serde(default)]`,
  per the existing trap at `config.rs:108-110`).
- **Asymmetric suppression, deliberate:** the full `SessionStart` reflex stays suppressed inside
  phases (`DROVR_PHASE` set), because a phase agent runs on its injected briefing. The per-turn
  gate does **not** suppress inside phases — a phase is exactly where the discipline must hold.
- `README.md:70-94` gets the new key documented.

### 6.3 Out of scope

`PreToolUse` hard-denial (e.g., blocking an `Edit` that skipped `drovr:tdd`, or a `git commit`
with no verification evidence) is enforcement rather than persuasion, carries real
false-positive risk, and is not part of this run.

## 7. Fix 3 — bind checklists to tracked task state

Stated harness-agnostically because harnesses differ (some expose
`TaskCreate`/`TaskUpdate`/`TaskList` with no `TodoWrite`; stable Claude Code exposes `TodoWrite`).

Directive text, inserted verbatim at each site below:

> When a skill or briefing gives you a numbered checklist, create **one tracked item per step**
> using whatever task tool this harness exposes — `TodoWrite`, or `TaskCreate`/`TaskUpdate` —
> before you start step 1. Mark each in-progress when you start it and complete when its evidence
> is in hand. If the harness exposes no task tool, write the checklist to
> `~/.local/share/drovr/runs/<run>/checklist.md` when inside a run, or `CHECKLIST.md` at the repo
> root otherwise, and tick items there. An untracked checklist decays with the context window;
> that decay is the exact failure drovr exists to fight.

Applied at four sites:

1. `skills/using-drovr/SKILL.md` — the gate function's checklist branch (§6.1 item 5).
2. Each of the four discipline skills' numbered procedure — one binding line directly above it.
3. `skills/pipeline/phase-prompts/*.md` — the `## Do` lists (`implement-task.md:14-64`, 7 steps,
   and the equivalents in `brainstorm.md`, `plan.md`, `review.md`, `review-angle.md`) gain the
   directive as step 0. Pure text change — these files are agent-assembled markdown, not compiled
   into the binary.
4. `skills/handoff/SKILL.md` and `skills/handoff/HANDOFF-template.md` — the 7-section handoff is a
   checklist and gets the same treatment.

No CLI change required for this fix.

## 8. Fix 4 — move the armor onto the discipline skills

`tdd`, `systematic-debugging`, `verification-before-completion`, `code-review` are restructured to
a fixed section order [tier 3 — order is superpowers' convention, adopted wholesale]:

```
   REQUIRED — all four skills
1. description:      trigger, not summary (fix 1)
2. Overview          core principle + spirit-vs-letter line + the WHY, ≤6 lines
3. Unity line        "the next phase agent is you, with your context gone"
4. The Iron Law      one fenced all-caps line + "No exceptions:" bullets closing named loopholes,
                     each bullet pairing the prohibition with the required action
5. Announce          the exact sentence to emit when invoking the skill (commitment device)
6. The procedure     numbered, preceded by the task-binding directive (fix 3)
8. Red flags — STOP  inner-monologue fragments, closed by a catch-all bullet
9. Rationalizations  thought → reality; the reality column is an INSTRUCTION, not a rebuttal
10. Worked example   one ✅/❌ pair of actual utterances. One good example, not five
11. Cross-refs       bare skill names with REQUIRED markers; never @-links (they force-load)

   CONDITIONAL — only where named below
7. Requirements      claim → required evidence → not sufficient
                     ONLY: verification-before-completion, code-review
6b. Cycle flowchart  a fenced dot graph of the loop
                     ONLY: tdd, systematic-debugging   (§3 placement rule)
```

**Announcement strings** (template `Using drovr:<skill> to <purpose>.`):

- `tdd` — *"Using drovr:tdd — writing the failing test before the implementation."*
- `systematic-debugging` — *"Using drovr:systematic-debugging — reproducing before fixing."*
- `verification-before-completion` — *"Using drovr:verification-before-completion — running the
  checks before claiming done."*
- `code-review` — *"Using drovr:code-review — dispatching read-only reviewers before calling this
  done."*

**Placement rationale.** Sections 2–5 sit at the top per §3's position-effects decision. Sections
8–9 sit late for proximity to the point of temptation [tier 4 judgement — not the position
finding]. The procedure (6) sits mid-document deliberately: it's the section the agent actively
re-reads while executing, so it's least dependent on single-pass recall — the position finding is
not cited for sections 6–9.

**Per-skill Iron Laws and loophole closures:**

- **`tdd`** — Iron Law: no implementation code before a test you have watched fail. Closures:
  "I'll keep the code as reference," "the test is obvious so I'll write it after," "it's a refactor
  so TDD doesn't apply," "the harness makes it hard to run one test."
- **`systematic-debugging`** — Iron Law: no fix before a reproduction and a mechanistic cause.
  Adds the numeric escalation trigger: after 3 failed fixes, stop and question the design before
  attempting fix #4.
- **`verification-before-completion`** — Iron Law: no completion claim without fresh evidence
  produced in this message. Requirements table covers tests / build / linter / bug-fixed /
  subagent-reported-success. Catch-all red flag for any wording implying success.
- **`code-review`** — Iron Law: no change is done until a read-only reviewer has looked at it and
  every Critical/Important finding is resolved or explicitly recorded as deferred. Closures: "the
  change is too small," "I already reviewed it myself," "the pipeline's review phase will catch
  it." The existing FOREGROUND rule (`code-review/SKILL.md:19-23`) is promoted into the
  no-exceptions list — backgrounding a reviewer is the known way this skill silently fails.

Expected result: 39–51 lines each today → roughly 120–180 lines; the binding constraint is §4's
12000-byte `BODY_BUDGET`, not line count.

## 9. Fix 5 — the meta-skill and the empirical loop

### 9.1 New skill: `drovr:writing-skills`

New file `skills/writing-skills/SKILL.md`, in drovr's own voice. The pass criteria, four-part
closure, and scenario-construction rules below are tier-3 convention-follows, ported from
`testing-skills-with-subagents.md:182-275` in drovr's own wording — and independently convergent
with Anthropic's own skill-authoring guidance (build evaluations first, baseline without the
skill, minimal instructions, iterate).

- **Mapping** the skill teaches: pressure scenario ↔ test case; `SKILL.md` ↔ production code; RED
  ↔ agent violates the rule without the skill; GREEN ↔ complies with the skill; REFACTOR ↔ close
  each new loophole.
- **Loop** (fenced `dot` flowchart, a stop-too-early loop per §3): build the scenario set → run
  the baseline → transcribe every excuse verbatim → write the minimal counter-text → re-run on
  held-out scenarios → apply the four-part closure to each new rationalization → repeat until a
  run produces no new rationalization **or** the §9.3 REFACTOR ceiling is reached, whichever comes
  first. The ceiling is not optional — an uncapped loop is the same unbounded-cost defect this
  spec exists to fix elsewhere.
- **Four-part closure**, all four every time: explicit negation inside the rule; a
  rationalization-table row; a red-flags bullet; a `description:` update adding the symptom of
  being about to violate.
- **Scenario construction rules:** real file paths, concrete numbers and deadlines, a forced
  A/B/C choice, phrased "what do you do" not "what should you do," no escape hatch to "I'd ask the
  human," and ≥3 combined pressure types (time, sunk cost, authority, economic, exhaustion,
  social, pragmatic) — single pressures are resisted, combined ones break agents.
- **Pass criteria**, all four required: correct option under maximum pressure; the agent cites a
  specific section; it names the temptation and complies anyway; the meta-test ("how should this
  have been written?") returns "it was clear." Signals of not-bulletproof: new rationalizations,
  the agent arguing the skill is wrong, invented hybrid approaches, asking permission while
  arguing for the violation.
- **drovr-specific constraints:** scenario subagents run in the FOREGROUND; the author remains
  single writer; the no-fabricated-measurements rule (§2) applies.
- Reference files: `references/pressure-scenarios.md`, `references/testing-with-subagents.md` —
  keeps `SKILL.md` itself under the §4 cap.

### 9.2 Evidence corpus — new paths

- `skills/writing-skills/scenarios/<skill>-<n>.md` — checked-in scenario prompts, each tagged
  `dev` or `holdout` (§9.3). Live with the skill as tests.
- `docs/skill-evidence/<skill>.md` — per skill: scenarios used, verbatim baseline
  rationalizations, the counter-text written, re-test result with dates.
- `docs/skill-evidence/voice.md` — the §9.4 probe record.
- `docs/skill-evidence/per-turn-gate.md` — §6.2's unmeasured-bet record and the subagent-firing
  answer.
- `docs/skill-evidence/transcripts/` — raw transcripts; the corpus any drovr skill text cites when
  making a numeric claim.

### 9.3 The acceptance test — runs inside this run

Answers: did stickiness improve, or did the docs just get longer.

**Held-out design.** Per skill: 3 scenarios, 1 development + 2 held-out. RED transcription and
counter-text authoring use the development scenario only. The pass bar is pre-registered and
scored on the held-out pair, which is never read while writing arm B — authoring B from the
scenarios that grade it would fit the text to the test.

**Arms:**

| Arm | Text |
|---|---|
| A | Current `SKILL.md` at the pre-fix `HEAD` (captured in §0 step 2) |
| A′ | Fix-1-only: descriptions un-scoped, no armor |
| B | Full rewrite (fixes 1 + 3 + 4) |

A′ isolates fix 4's contribution: arm A's descriptions are phase-scoped (the §5 defect), so
without A′ a non-phase-framed scenario handicaps A for reasons unrelated to the armor, and B > A
would prove nothing about fix 4 specifically.

**Budget table — hard ceilings.** When a ceiling is hit, work halts and records a null in
`docs/skill-evidence/`; it does not silently extend.

| Stage | Scope | Runs | Ceiling |
|---|---|---|---|
| RED / baseline on dev set | 5 skills × 1 dev scenario × 2 samples | 10 | 10 |
| Arm A on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| Arm A′ on held-out | 4 discipline skills × 2 × 2 | 16 | 16 |
| Arm B on held-out | 5 skills × 2 held-out × 2 samples | 20 | 20 |
| REFACTOR re-tests | failing skills only, ≤2 iterations each | ≤20 | 20 |
| Voice probe (§9.4) | 4 variants × 2 scenarios × 3 samples | 24 | 24 |
| `using-drovr` no-skill-applies class | 2 scenarios × 3 arms × 2 samples | 12 | 12 |
| **Total** | | **≈122** | **122 hard ceiling** |

`using-drovr`'s extra scenario class checks the router's own failure mode (invoking nothing)
without inducing the opposite failure (invoking everything reflexively); it is budgeted, not
free.

**Execution structure.** 122 foreground subagent runs with verbatim transcription do not fit in
one implement-task context. Decomposition: one dedicated phase per skill, `ab-<skill>` (5 phases),
each running its own stages, writing `docs/skill-evidence/<skill>.md` plus raw transcripts, then
exiting. The voice probe is a sixth phase, `ab-voice`. The driver aggregates results. No phase
holds more than ~25 runs.

**Scoring** — pre-registered, not scored by arm B's author:

- Rubric: binary compliant/non-compliant on the scenario's forced choice, plus the four §9.1 pass
  criteria recorded separately as booleans.
- Scorer: a read-only reviewer subagent given the transcript and rubric only.
- Blinding: arm labels stripped and transcripts shuffled before scoring; mapping restored only
  after all scores are recorded.
- Model: `sonnet` for both probe subagents and the scorer.

**Pre-registered bars:**

- Arm A "already passes": compliant on ≥3 of 4 held-out runs (2 held-out scenarios × 2 samples).
- Arm B passes: compliant on ≥3 of 4 held-out runs for that skill, AND strictly more compliant
  runs than both A and A′.
- **Consequence of B failing after its REFACTOR ceiling:** that skill's armor does not ship — it
  reverts to arm A′ (fix-1-only), and `docs/skill-evidence/<skill>.md` records the failure and the
  reverted state. Fix 1 ships regardless (it repairs a defect); fix 4 must earn its bytes.
- **If arm A already passes** for a skill, that skill's rewrite is not justified and reverts to A′.
- **If A′ ≈ B** for a skill, the armor is not carrying its weight there and that skill reverts to
  A′ even if B independently clears its own bar.

Null and negative results are recorded alongside positive ones in `docs/skill-evidence/`.

### 9.4 Voice probe

Probe skill: `verification-before-completion` — sharpest binary outcome (claimed done without
running the command), shortest scenarios. Model: `sonnet`, matching §9.3; this is explicitly not
the Opus-class model drovr sessions run on, a stated limitation alongside §3's Haiku/mini/
Flash-to-Sonnet/Opus extrapolation.

Four variants, identical structure (same Iron Law, procedure, tables, placement), each adding
exactly one register device to the baseline:

| Variant | Register |
|---|---|
| V0 | Baseline: plain imperative; no all-caps, no absolutist "no exceptions"; operational consequence only |
| V1 | V0 + unity line |
| V2 | V0 + full authority register (`MUST`/`NEVER`, all-caps Iron Law, no-exceptions bullets) |
| V3 | V0 + moral framing, in superpowers' register |

4 variants × 2 scenarios × 3 samples = 24 runs, 6 per variant, each compared against V0's 6 runs.

**Decision rule** (pre-registered, separation margin ≥3 of 6 — chosen to match stated power
rather than sit below it):

1. Variant beats V0 by ≥3 → that device ships across all five documents.
2. V0 beats the variant by ≥3 → that device is dropped; the baseline register ships for it.
3. No separation ≥3 (the likeliest outcome, given expected small register effects on frontier
   models) → tier-3 fallback: authority ships (superpowers uses it), moral framing ships
   (superpowers uses it throughout), unity ships anyway on the strength of the 2026 published
   ranking (tier 1 outranks tier 3). Each outcome is recorded in `docs/skill-evidence/voice.md` as
   convention-or-prior, with the null attached.
4. Whichever register wins applies to all five documents without re-testing each — a stated
   limitation (measured on one skill, one model, generalized to five documents).

**Exception:** if V1 (unity) loses to V0 by ≥3, that is a genuine conflict between the published
prior and drovr's own data. It is not auto-resolved by the rule above — it escalates to the
human, and unity's shipping decision for the affected skill(s) waits on that answer.
