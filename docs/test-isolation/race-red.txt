WHAT IT PROVES — AND WHAT IT DOES NOT
  Proves: `XDG_DATA_HOME` is a single process-global slot, so two concurrent
  redirections share it and one thread resolves the other thread's data root.
  It is a race by construction, and it loses, in the open, thousands of times
  per run.

  Does NOT prove: that this is the cause of any particular observed flake.
  T2's baseline recorded 8/8 green parallel runs — the documented flake did not
  reproduce. That ruling stands. This file demonstrates the MECHANISM; it does
  not license a later claim that removing the mechanism fixed a flake that was
  never watched failing.

  Between 1% and 17% of all reads were stolen; the two threads lose at about
  the same rate, which is what a symmetric race looks like. The spread between
  runs 3/6 and run 10 is an order of magnitude — scheduling luck decides how
  much of the window the two threads actually share. That spread is exactly why
  the iteration count is not at the plan's floor; see the tuning table.

  Runtime: 0.04-0.07s. The count is not a performance concern.

ITERATION-COUNT TUNING (all on this machine, 10 invocations each, final form)
    ITERATIONS =  1_000  ->  10/10 failed
    ITERATIONS =  5_000  ->  10/10 failed
    ITERATIONS = 20_000  ->  10/10 failed   <- shipped

  1_000 (the plan's floor) already saturates here. 20_000 was kept anyway: the
  overlap window is what makes the race observable, and a machine with fewer
  cores, a slower allocator, or a busier scheduler — the nix sandbox, or CI —
  has a narrower one. Run 6 above stole only 515 reads out of 40,000 even at
  20_000 iterations; at 1_000 that same run would have had ~13 chances, which
  is not a margin. The cost of the headroom is ~0.03s, and at T13 this same
  count becomes the strength of the PASSING assertion rather than of a failure.
  Do not lower it at T13 to make the test cheap; the count IS the evidence.

--------------------------------------------------------------------------------
§4  THE DELIBERATE FAILURE DOES NOT DAMAGE THE REST OF THE SUITE
--------------------------------------------------------------------------------

  A test that is *meant* to fail takes its failure path on every single run, so
  that path had to be made as clean as the passing one. The review panel's
  first iteration found two Important defects in the first draft, both of the
  same shape: a panic taken while `ENV_LOCK` was still held. `ENV_LOCK` is a
  plain `Mutex`, and a panic under its guard POISONS it — which would turn one
  honest, intended failure into a cascade of meaningless `PoisonError`s across
  every other test in the process. The second was worse: a worker-thread panic
  would short-circuit `XDG_DATA_HOME` restoration entirely, leaking a foreign
  data root into whatever ran next.

  Fixed by pushing every panic past the end of the critical section — threads
  are joined into `Result`s rather than unwrapped in place, the variable is
  restored, the guard is dropped explicitly, and only then is anything
  asserted. The claim is verified, not asserted:

  $ cargo test --bin drovr -- --include-ignored
    test result: FAILED. 708 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out
    (the 1 failure is this test, by design)
    occurrences of "PoisonError" or "poisoned" in the output: 0

  708 of 708 other tests pass in the same process as the deliberate failure.
  That is the property, measured.
