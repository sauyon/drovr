--------------------------------------------------------------------------------
§4  MUTATION CHECKS — IS THE GREEN LOAD-BEARING?
--------------------------------------------------------------------------------

  A rewritten test that passes is worth exactly as much as its ability to still
  fail. Two checks.

  (a) THE OBSERVATION IS LIVE. Redirect each thread to a root other than the one
      its expectation was derived from — `env.set(DATA_KEY, root.join("elsewhere"))`
      — and every single read is counted as stolen:

        panicked at src/run.rs:2030:9:
          left: 40000
         right: 0

      40000 = 2 threads x 20_000 iterations. So the loop really does compare
      `data_dir()` against this thread's root on every iteration; nothing is
      being skipped, short-circuited or optimised away.

  (b) THE SHARED-SLOT SHAPE IS NOT MERELY ABSENT, IT IS UNEXPRESSIBLE. The
      intended mutation was to put both threads back on ONE overlay — the exact
      analogue of the process-global slot that failed in race-red.txt. It does
      not compile:

        error[E0277]: `*const ()` cannot be sent between threads safely

      `TestEnv` is `!Send` by construction (`cli/src/test_env.rs`, the
      `const _: () = { ... }` Send/Sync probe block), and the `EnteredEnv` a
      spawned thread CAN obtain has no setter at all. So a worker thread cannot
      write another thread's overlay, and two threads cannot share one writable
      one.

      This is a stronger result than a red test and is recorded as such: the
      defect race-red.txt demonstrates cannot be reintroduced by editing this
      test, only by removing the `!Send` bound — which is itself guarded by the
      compile-time probe.
