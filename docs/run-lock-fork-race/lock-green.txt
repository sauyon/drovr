WHAT THIS IS
  The other half of `lock-red.txt`. That file recorded drovr#80 failing, on the
  record, before the fix existed: a deterministic mechanism test that failed
  10/10, and ten parallel suite runs that emitted `acquire_run_lock`'s refusal
  307 times and failed 18 tests. This file records the same two measurements,
  same commands, same machine, after it.

  Read the two together or neither is worth much: a green test nobody watched
  fail proves nothing, and a red one nobody watched go green proves only that a
  defect was once real.

  The fix is one line — release is an explicit `flock(LOCK_UN)` in
  `crate::flock::FileLock`'s `Drop`, never a bare drop of the `File`. §5 removes
  that line again and watches the red come back, so the green below is shown to
  be load-bearing rather than merely present.

WHAT IT PROVES — AND WHAT IT DOES NOT
  Proves (§1): a drovr advisory file lock is released when its guard drops, even
  while a second fd shares the open file description. `LOCK_UN` names the
  description itself, so it does not care how many fds still point at it. The
  test that failed 10/10 in `lock-red.txt` §1 now passes 10/10, with its body
  unchanged and its `#[ignore]` removed.

  Proves (§2): in ten parallel runs of the whole suite, the two `pane_close`-
  counting tests pass in 10/10, and `acquire_run_lock`'s refusal message appears
  ZERO times. Red side: 22-41 occurrences per run, 307 total, mean 31. That is
  the criterion with real statistical power — ~310 expected occurrences going to
  0 — and it is the one that cannot pass by luck, which is why it counts the
  MESSAGE and not the failures (`lock-red.txt` §2's ⭐).

  Does NOT prove: that the parallel suite is deterministic in general. It was
  fully green in all ten runs here, but the stub-exec/`ETXTBSY` defect on
  `with_stub_herdr` (`cli/src/herdr.rs:2108`, panicking at `:2133` — `lock-red.txt`
  says `:2131`, drifted; see §6b) is a
  SEPARATE defect in the same fork-window family and is untouched by this work.
  It is intermittent: zero occurrences in `lock-red.txt`'s final ten and zero in
  these ten, but two in the earlier set (`lock-red.txt` WHEN / WHERE). NO LOCK IS
  INVOLVED IN IT — that clause is about the stub-exec defect, not about drovr#80,
  which is nothing but a lock — so `File::unlock()` does nothing for it and this
  fix cannot have closed it.

  `docs/test-isolation/race-green.txt:113-124` is the same disclaimer with the
  roles swapped, and is worth reading beside this one: that file recorded ITS
  green while naming the still-red parallel suite as someone else's defect —
  drovr#80, this one. Now drovr#80 is fixed and the remaining doubt is the other
  member of the fork-window family. Note the asymmetry, though, and do not
  over-read the symmetry: race-green's ten runs were visibly red (25 failures),
  whereas these ten are green and the residual risk is only that ETXTBSY did not
  happen to fire. Ten quiet runs are not a claim that it is gone.

  Does NOT prove: anything about the SIGKILL residual. A holder killed without
  unwinding between a `fork` and that child's `exec` still leaves the lock held
  until the child execs. `Drop` runs on every ordinary exit and on panic-unwind,
  so that is the only gap left; it is documented in `cli/src/phase.rs`'s
  `acquire_run_lock` doc comment and deliberately NOT closed here — closing it
  would need the bounded retry this design rejects (plan.md q4=no).

  Does NOT prove: any production frequency, and this run re-measured none. The
  standalone fork-based reproducer's 3949 / 24000 (~16%) is the TRACKER's number
  (forge.ko.ag/drovr/drovr#80); the brainstorm phase's re-run, 4582 / 24000
  (~19%), is `spec.md:25-37`'s. Neither belongs to this repo and neither was
  taken here. Attribute them accordingly; never to this run.

  Does NOT prove: that the lock still EXCLUDES — not on its own. §1's test only
  asserts that a re-claim succeeds, so it would pass against a lock that had
  stopped locking altogether. Exclusion is asserted by
  `flock::tests::a_live_holder_is_reported_as_none` and
  `phase::rehydrate_tests::two_rehydrates_of_one_run_cannot_both_launch`, both
  green in all ten runs (§2). Read them as a pair; neither is sufficient alone.
  §5's mutation check is what makes the pair meaningful.
