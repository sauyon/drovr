WHAT IT PROVES — AND WHAT IT DOES NOT
  Proves (§1): an advisory lock released by DROPPING its `File` is not released
  while a second fd shares the open file description. The lock belongs to the
  description, not to either fd, and `close(2)` releases it only when it closes
  the LAST fd. Dropping the holder therefore leaves the lock standing and the
  next `try_lock` refuses with `WouldBlock` while no other process claims it.
  10 invocations, 10 failures, every one `WouldBlock`. `try_clone` stages the
  second fd; `fork()` is what produces it in production, and `O_CLOEXEC`
  removes the child's copy at `exec`, not before.

  Proves (§2): this is not a rare corner. `acquire_run_lock`'s refusal message
  is emitted 22–41 times PER PARALLEL SUITE RUN (307 across ten runs, mean 31),
  spread over 9–14 distinct run names, while only 1–3 tests fail per run. FIVE
  distinct tests failed on it across the ten (§3 a–e).

  Every one of those 307 is spurious, and that is a property of the fixtures
  rather than a judgement call: each test mints its own `TestEnv`, whose
  `XDG_DATA_HOME` is a private `TempDir` (`cli/src/test_env.rs:246-263`), and
  `run_dir` is `data_dir()/runs/<name>` (`cli/src/run.rs:906-915`). No two test
  threads can therefore reach the same `run.lock` inode, so genuine contention
  is impossible by construction and every refusal is the fork window. This is
  what makes T7's criterion (b) — ZERO — a reachable bar rather than a hope.

  Does NOT prove: anything about the SIGKILL residual — a holder killed with
  SIGKILL still leaves the lock to the kernel, and nothing here exercises that.

  Does NOT prove: that the lock still EXCLUDES. §1's test only asserts that a
  re-claim succeeds, so on its own it would pass against an `acquire_run_lock`
  that had stopped locking altogether. Exclusion is asserted by
  `phase::rehydrate_tests::two_rehydrates_of_one_run_cannot_both_launch`
  (`cli/src/phase.rs:11615`), which is why T3 must keep BOTH green and must not
  edit either. Read them as a pair; neither is sufficient alone.

  Does NOT prove: any production frequency. Two standalone measurements exist
  and they are NOT this run's:
    - forge.ko.ag/drovr/drovr#80's own reproducer: 3949 / 24000 (~16%);
    - the brainstorm phase's re-run of that harness, recorded in `spec.md:25-37`:
      4582 / 24000 (~19%) with 4 forker threads, and 0 / 24000 both with no
      forkers and with `file.unlock()` before the drop.
  Neither figure was re-measured by this task, and neither belongs to this
  repo — `grep -rn "3949" .` matches only inside THIS file. Attribute them to
  the tracker and to `spec.md` respectively; never to this run.

  Does NOT prove: that every parallel failure in this repo is drovr#80. A
  DIFFERENT defect in the same fork-window family exists — stub-exec on
  `with_stub_herdr` (`cli/src/herdr.rs:2108`, panicking at `:2131`). It did NOT
  fire in the ten runs below, but it fired twice in the earlier ten (see
  WHEN / WHERE), so it is intermittent rather than gone. No lock is involved
  and `File::unlock()` does nothing for it. Out of scope for this run, by the
  plan, deliberately. See §5's ⚠ on criterion (c).
