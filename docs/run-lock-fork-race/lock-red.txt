WHAT IT PROVES — AND WHAT IT DOES NOT
  Proves (§1): an advisory lock released by DROPPING its `File` is not released
  at all while a second fd shares the open file description. The lock belongs
  to the description, not to either fd, and `close(2)` releases it only when it
  closes the LAST fd. Dropping the holder therefore leaves the lock standing
  and the next `try_lock` refuses with `WouldBlock` while no other process
  claims it. `try_clone` stages the second fd; `fork()` is what produces it in
  production, and `O_CLOEXEC` removes the child's copy at `exec`, not before.

  Proves (§2): this is not a rare corner. `acquire_run_lock`'s refusal message
  is emitted 26–40 times PER PARALLEL SUITE RUN (320 across ten runs, mean 32),
  spread over 10–16 distinct run names, while only 1–3 tests fail. It is fatal
  in exactly the places that COUNT `pane_close` calls; everywhere else a
  best-effort reap swallows it into a warning. Two further failures (§3) are
  the same `WouldBlock`, hitting `phase_rehydrate` directly.

  Does NOT prove: anything about the SIGKILL residual — a holder killed with
  SIGKILL still leaves the lock to the kernel, and nothing here exercises that.

  Does NOT prove: any production frequency. The tracker's own standalone
  reproducer measured 3949 failures in 24000 attempts (~16%) with 4 forker
  threads. That figure lives in forge.ko.ag/drovr/drovr#80, NOT in this repo
  (`grep -rn "3949" .` finds nothing here), and was NOT re-run by this task.
  Attribute it to the tracker; it is not a measurement of this run.

  Does NOT prove: that every parallel failure is drovr#80. Two of the 23 are a
  DIFFERENT defect in the same fork-window family — stub-exec / `ETXTBSY` on
  `with_stub_herdr` (`cli/src/herdr.rs:2108`, panicking at `:2131`). No lock is
  involved and `File::unlock()` does nothing for it. It is out of scope for
  this run, by the plan, deliberately. See §3.
